# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An npm package (`agglomerative-clustering`) that does colour-palette extraction and image quantization using hierarchical agglomerative clustering. The algorithm is written in C++ and compiled to WebAssembly with Emscripten; a thin JS wrapper exposes an async API for Node and browsers.

## Architecture

### Build post-processing
- `scripts/patch-glue.mjs` (after `em++`): hides the glue's `node:module` import from bundlers, makes Node detection also require a `file:` `import.meta.url` (runtimes that imitate Node don't have one), turns bare `process` into `globalThis.process` (Parcel adds a polyfill for a bare one), and writes `dist/clustering.cjs`, a CommonJS copy of the glue that reaches Node through `process.getBuiltinModule`.
- `scripts/patch-cjs.mjs` (after Babel): `dist/index.cjs` requires the ES glue and falls back to `clustering.cjs` when `require()` of an ES module fails (Jest's module system). It also turns `import.meta.url` in `dist/worker.cjs` (the worker entry's CommonJS build, the `require` condition of `./worker`) into the file's own URL from `__filename`, so it finds `worker-thread.mjs`, which stays an ES module that Node runs itself, and appends an uncalled `__dirname + "/worker-thread.mjs"` so file tracers (`@vercel/nft`, used by Vercel and Netlify) ship the worker's files with a serverless function. `build:types` writes `dist/worker.d.cts`, pointing at `index.d.cts`. `test/jest.test.js` runs Jest 30 in its default CommonJS mode against `dist/`, both entries.
- The worker entry (`src/worker.js`) takes `createWorker({ script })` and `init({ script })` (shared worker only, before it starts) for bundlers that don't emit `worker-thread.mjs`; `src/worker-thread.js` falls back to `self` messaging where Node's globals exist but `parentPort` doesn't. Keep the literal `new Worker(new URL('./worker-thread.mjs', import.meta.url))` for bundlers.

### JS ↔ WASM boundary (`src/index.js`)
- The WASM module is initialised lazily with `init(options?)`: one shared load (a failed load is forgotten so it can be retried), with `wasm` choosing where the module comes from. A location goes to the glue's `locateFile`; bytes and compiled modules go through its `instantiateWasm`, because this Emscripten build reads no `wasmBinary` setting. The worker entry forwards `wasm` as the worker's first call (`createWorker({ wasm })`), repeating it until it succeeds. Each API call `_malloc`s an input buffer in the WASM heap, copies the data in, calls an exported C function, then `unpack`s the result and frees both buffers.
- All C exports return a pointer to a buffer that the C side `malloc`ed, with a **4-byte little-endian length prefix** followed by the payload (`pack_variable_size` in C++, `unpack` in JS). JS must `_free` that pointer.
- Image format is passed as an int code: `rgba = 0`, `rgb = 1`, `bgra = 2`, `rgbx = 3`, `bgrx = 4` (`codes`). Colour space likewise: `rgb = 0`, `oklab = 1` (`ColorSpace` in `src/colorspace.hpp`).
- **Premultiplied and image keys (4.0).** An image object takes `premultiplied` (true only on `rgba`/`bgra`; false anywhere; anything else throws `invalid-argument`) and only the keys `data`, `format`, `width`, `height`, `premultiplied`. `checkImageObject` in `src/shared.js` runs the checks in one order: shape (format, data length, width x height), then unknown keys (`checkImageKeys`, with near-miss hints), then `premultiplied`. Every public function starts with `imageCopy` (`shared.js`), which reads `data`, `format`, `width`, `height` and `premultiplied` once and names the other own keys; everything after uses the copy. `load` in `index.js` and the worker entry's `send` (before anything is posted, for every image object, so a function, Symbol or Proxy gets the main entry's error, not the clone error) both run `imageCopy` and `checkImageBody` (data type, detached, then `checkImageObject`), so their errors are identical: keep new image checks in them. `call` copies buffer 0 into the heap, then un-premultiplies it in place (`_unpremultiply(pointer, start, end)`, pixel indices) and, for a mapped output, premultiplies it (`_premultiply`); indexed output stays straight. On the sliced paths `convertInSlices` runs the same exports in 65,536-pixel slices and yields only once `sliceMs` has passed. Results carry the input's `premultiplied` (`getWrapper`). Both exports are in `EXPORTED_FUNCTIONS`. Never convert the caller's array: only the heap copy changes.
- Options are an optional trailing object on every function that takes an image, validated by `parseOptions` against the keys each function accepts (unknown keys throw): `colorSpace`, `precision`, `alpha` and `transparent` for clustering, `colorSpace`, `dither` and `width` for mapping, all of them for `quantize` and `quantizeToIndices` (`transparent` also maps in the `quantizeToIndices*` functions that only map). `k` in indexed output counts the transparent entry: `colours_for_entries` in C++ cuts the palette one colour smaller when the image has pixels below the cutoff. `parseDither` (in `src/shared.js`, so the worker entry reads and copies the `dither` object the same way before posting it) reads every form of `dither` (false/true, a strength, a method name, `{ method, strength, steps }`) into a strength, a method code (`floyd-steinberg` 0, `atkinson` 1, `ordered` 2) and a step count (0 when not given: C then uses 64 for a palette of two distinct colours, else 16). A dither setting given as an option of its own (`ditherMethod`, `strength`, `steps`, …) gets a hint pointing at the object form. They reach C as extra trailing arguments (`color_space`, `precision`, `weight_alpha` as 0/1, `dither` as a double strength, `dither_method`, `dither_steps`, `width`). `Clustering.quantize` and its siblings pass `color_space` -1 when the option is absent, meaning "the clustering's colour space". `readHeader` in JS reads a clustering's version and layout, checks its checksum, and rejects buffers that can't be a clustering this version reads (with an upgrade message for newer format versions).
- **Option shapes (a convention for new options):** an option is a plain value while it has one setting; one with several settings, or settings that only some of its values take, also gets an object form, with the plain values kept as shorthands (`dither: 'ordered'` is `{ method: 'ordered' }`). Unknown keys in the object throw, like unknown options. No prefixed sibling options (`ditherMix`). Options describing the image (`width`) stay top-level. Adding an object form to an existing option is additive.
- **Lists of names (a convention):** every option whose value is one of a fixed set of names has the set exported as a frozen list from both entries (`colorSpaces`, `imageFormats`, `alphaModes`, `ditherMethods`, `ditherSteps`, like `errorCodes`), defined in `src/shared.js` and typed as a list of the option's type. A new option of this kind gets its list; a new name goes into its list. The C codes for the names live in separate maps (`colorSpaceCodes`, `alphaModeCodes`, `ditherMethodCodes`, `codes` for formats).
- Every function validates its arguments and takes its bytes before it awaits anything: `Module || await acquire()` doesn't wait once the module is loaded, so pixels, clusterings and palettes go into the WASM heap before the call returns, and before the first load `held` copies them. The worker entry does the same (`own`/`take`: posting is synchronous once the worker runs; before that the bytes are copied, or with `transfer: true` moved out at once with a transferring `structuredClone`). `test/inputs.test.js` changes the arrays right after each call.
- In Node, when the glue can't load the `.wasm` from next to itself (a server bundle such as Next.js moved it), `acquire` falls back to the package's own `clustering.wasm`, resolved with `createRequire` from `process.cwd()`; the worker entry does the same for `worker-thread.mjs` (`nodeWorkerScript`). Realm-sensitive checks (`ImageData`, `WebAssembly.Module`, `URL`) go by tag as well as `instanceof`.
- WebAssembly memory never shrinks, so `retireIfLarge` discards the instance (like an abort does) after any call that leaves its heap above 256 MB; the next call loads a fresh one. It counts growth from the size the instance started at (`startSizes`; the release build starts at 32 MB), so the sanitized build, which starts at 512 MB, isn't retired after every call. The glue's `print`/`printErr` are no-ops: failures reach callers as errors. `.babelrc` targets the engines the package supports (SIMD browsers, Node 22.12), so there are no regenerator helpers.
- Every error thrown is made with `fail(code, message, argument?)` from `src/shared.js`, so it carries a `code` (`ErrorCode` in `index.d.ts`: add a code there and in the error table in `docs/api.md` if you need a new kind) and, when it is about one argument, `argument` (`'image'`, `'k'`, `'clustering'`, `'palette'`, `'options'` or `'options.<key>'`; keep `ErrorArgument` in `index.d.ts` in step). Messages keep the `Invalid <thing>: ...` form. The worker thread sends errors across as `{name, message, code, argument, stack}` and `remoteError` in `worker.js` rebuilds them with the caller's stack and the worker's as `cause`.
- **`src/shared.js`** holds what both entries and the worker thread share: `fail`, the options snapshot, `readHeader`, the `Palette` and `Clustering` types and their tags, the markers that carry them across the worker boundary, and the `version` line. Source files import `./shared.js`; `scripts/babel-import-extensions.cjs` rewrites that to `./shared.mjs` or `./shared.cjs` in each build. Typed-array checks use the realm-safe helpers there (`isUint8Array` and friends, by tag), not `instanceof`.
- **Cancelling and progress.** `parseOptions` accepts `signal` and `onProgress` on every function with an image. When either is given, the functions that cluster go through `clusterInSlices` and the functions that map through `mapInSlices` (both 10 ms slices, `yieldNow` between them, `checkAborted` and a monotonic `reporter` each time; a call that finishes in its first slice doesn't yield), instead of the one-shot exports; `quantize` and `quantizeToIndices` do both, splitting progress by `clusteringShare` (measured, by dither method). Results are identical (tested in `test/mapping-slices.test.js` and `bench/spikes/slicing-mapping/resume.mjs`). The worker entry can't send a signal or callback across, so `takeControls` strips them, sends `{cancel: id}` on abort and calls `onProgress` from `{id, progress}` messages; the thread (`worker-thread.js`) keeps an AbortController per cancellable call from the moment it arrives, injects its signal and a progress poster into the options (`optionsIndex`), and runs calls one at a time through a promise queue, so a cancel message is read between slices and a still-queued call is skipped. Aborts reject on the caller's side at once with the signal's reason; the thread then drops whatever it was making.
- `getWrapper` makes the `quantize*` return types match the input type (Uint8Array / ImageData / `{data, format}`). The `quantizeToIndices*` functions instead return `{palette, indices, indexBits, transparentIndex}` (plus the input's `width`/`height`), decoded by `unpackIndices` from `_quantize_indices`'s payload: a 12-byte header (entry count, transparent index or -1 (`null` in the result), index bytes 1/2/4), the palette, then the indices.
- **Adding or changing public API** touches several places, and `test/api.test.js` fails until they agree, naming the one that doesn't. That includes the docs: in `docs/api.md` each function's `Options:` list is compared with the options the code accepts, and names that were renamed or removed are searched for in the README and the user docs, and links and heading anchors across the README and `docs/` are checked, so prose can't drift. For a new function or option: the C export (`EXPORTED_FUNCTIONS` in `build:wasm`) if it needs one; `src/index.js` (the function, and the option lists and `parseOptions` for an option); `src/index.d.ts` and `src/worker.d.ts`, with a doc comment on every export; the worker's routing, `imageFunctions` (or the handle names) and `optionsPosition` and `argumentNames` in `src/worker.js` and `optionsIndex` and any handle method in `src/worker-thread.js`; the `docs/api.md` entry (and a row in its options table, or its error table for a new code); the CHANGELOG; tests. The test also snapshots the declarations without comments (`test/api/*.snap.txt`): after reviewing the diff of a deliberate change, update them with `npx vitest run test/api.test.js -u`. A feature slated for removal is marked `@deprecated` in the types and kept working for the rest of the major version. There are no warnings in 4.0 (PRINCIPLES "Warnings only bridge to an error in the next major"); a bare RGB, grey or grey-alpha `Uint8Array` is an `invalid-argument` error.
- If you add or rename a C export, update `EXPORTED_FUNCTIONS` in the `build:wasm` script, `src/index.js`, and `src/index.d.ts`.

### Worker entry (`src/worker.js`, `src/worker-thread.js`)
- `agglomerative-clustering/worker` is an ES module only (the CJS build skips these files). `worker.js` runs on the caller's thread: `createWorker()` starts `worker-thread.mjs` with `new Worker(new URL('./worker-thread.mjs', import.meta.url), {type: 'module'})` in browsers (written out literally so bundlers find it), or with `worker_threads` in Node (`execArgv: []`, unref'd whenever no call is pending), and sends `{id, method, args}` messages. `worker-thread.js` runs the main entry (it imports `./index.mjs`, which exists only in `dist/`) and transfers every result buffer back. It must not use top-level await: bundlers build workers as classic scripts by default.
- ImageData crosses as a plain `{data, format, width, height}`, and mapped results are turned back into ImageData on return; other inputs cross as they are, so the worker's own validation gives the usual errors. `cluster(image)` keeps the image and its clustering in the worker under a handle id, and the `handle*` methods in `worker-thread.js` serve the handle's calls. `load(clustering)` keeps only a stored clustering (a `LoadedClusteringHandle`, whose mapping methods take the image), and both kinds of handle have `chooseFrom` (the `Clustering` method of the same name; main entry only as a method, no function form). The `…FromClustering` and `get…` function forms (3.x) are gone from both entries since 4.0: `test/removed-names.test.js` checks that no export, wire name or doc mentions them, and a 3.x worker script gets `worker-failed` for the renamed wire names. The routing lists in `src/worker.js` are `imageFunctions`, `optionsPosition` and `argumentNames` (which names the argument a value that can't be cloned came from).

### C++ pipeline (`src/clustering.cpp`, `src/clustering.hpp`)
1. **`ClusteringJob`** (`_get_clustering` runs it to completion): builds a colour histogram (`AgglomerativeHistogram`, an open-addressing table on packed 8-bit RGB that keeps colours in first-seen order; cluster ids follow that order). Colours become 16-bit clustering coordinates (`ColorCoordinates` in `src/colorspace.hpp`) so that weighted-average merges keep precision: RGB is upscaled from 8 bits, OKLab is scaled by one factor on all three axes so squared coordinate distances stay proportional to OKLab distances. With `alpha: 'weight'` (default, RGBA only) each pixel adds its alpha (units of 1/255 of a pixel) and alpha-0 pixels are skipped; if no pixel is partially transparent the weights are divided back to whole pixels, so opaque images and binary-alpha images cluster exactly as with alpha ignored. Histogram totals are 64-bit; if the total weight would overflow the grid's 32-bit counts (partly transparent images above ~16.8 MP) all weights are shifted down to fit, keeping each visible colour at least 1. With `precision` < 8, colours are then grouped by their top bits (a second histogram keyed on the masked colour) and each group enters as one cluster at its count-weighted mean. Records are converted back to 8-bit sRGB on output (each cluster once, by id), so the clustering format doesn't depend on the colour space. It then builds the exact Ward hierarchy: the clustering you get by always merging the pair with the lowest Ward cost, `n_a·n_b/(n_a+n_b)·‖a−b‖²` (the increase in total squared error). Merged centroids are count-weighted averages (floored to integers).
   - **Slices.** `ClusteringJob::step(budget_ms)` runs the stages (scan pixels, build the grid, merge, write records) until the time budget is spent, checking the clock between small units of work (every 65,536 pixels or colours, every 4 merge iterations); every stage is interruptible (since 3.6.0, also building, the grid's size reviews (`WardGrid::reindex(timed, deadline)`, during which nothing may query the grid), the histogram growing its table (`make_room` before each block of pixels), writing and the checksum), so on millions of colours no slice runs past a few tens of ms. An infinite budget never reads the clock, which is what `_get_clustering` uses, so the one-shot path is exactly the old one. Slicing never changes output: the steps and their order are the same. The C exports `clustering_job_start/step/result/free` drive it from JS; the image must stay allocated until the scan stage is done.
   - It uses a **nearest-neighbour chain**: follow each cluster to its cheapest partner until two clusters are each other's cheapest, merge them, and continue from the rest of the chain. Ward is reducible, so this gives the same hierarchy as the greedy global-minimum loop without a heap or cached partners.
   - The chain finds merges out of cost order. Each merge gets a height `max(cost, children's heights)` (centroid flooring can make a parent slightly cheaper than a child), and merges are sorted by height (ties by merged id, so in chain order; a small merge sort, since `std::sort`'s instantiation was 14 KB) before records are written, so every record comes after the ones that formed its clusters.
   - Partner ties break by cost, then the pair's (packed colour, cluster id) values. Every cluster ranks partners the same way, which keeps the chain acyclic and the output deterministic. Clusters are identified by id, so two clusters can share a colour (they merge next, at cost 0, as an `[m, m, m]` record).
2. **`WardGrid`**: the spatial index behind `nearest(id)`, the exact cheapest partner of a cluster. Nearly all clustering time is spent in its `search`, so check changes with instruction counts (callgrind on a native build) as well as the harness: wall-clock time on shared machines is noisy.
   - Cells are a dense uniform grid of `dimension`³ cells, with `dimension` taken from `dimensions` (1…128, each step about doubling the cell count); coordinate v is in cell `(v·dimension)>>16`, and `boundaries[k]` is the first coordinate of cell k. Image colours fill a small part of the RGB cube, so `reindex()` picks the finest size whose *occupied* cells average at least `target_occupancy` (24) clusters, counting each candidate size's occupied cells in a bitmap, from the current size down (clusters only merge). It runs after the initial adds and whenever the cluster count halves. The target was tuned in WASM on Kodak, OKLab and `precision: 6`: coarse cells with SIMD scans beat fine cells with more stepping. Each occupied cell (`Bucket`) stores its clusters in `Chunk`s of four lanes (colours as float vectors, counts, ids) so `search` computes four exact Ward costs at once with GCC/Clang vector extensions, which become WASM SIMD128 through `-msimd128` in `build:wasm`. The double-precision cost uses the same operations as `get_weight`, so it matches the scalar cost bit for bit. Unused lanes have id `none`, count 1 and a far-away colour, so their cost is huge. Each lane also holds its count as a float (`weight`), since unsigned→float converts are slow on x86 and in V8. Removal moves the cell's last lane into the hole. `bucket_bounds` holds, as two float vectors, the colour box of everything ever linked into each cell and (in `high` lane 3) the smallest count ever linked into it; removals only loosen them, so they stay valid bounds. `columns` has one bit per cell for each (x, y) column, set when the cell has a bucket.
   - `search` scans rings of cells outward, visiting only cells whose `columns` bit is set (the ring's z range and its two end cells are bit masks computed once per ring). The chain passes the cluster below `a` as a `hint`: a live partner whose cost bounds the search from the start. A cell is skipped when its lightest possible member, at the nearest point of its colour box, can't beat the bound; otherwise its chunks' costs are computed four at a time and only lanes that beat the bound are offered. Both the cell test and each chunk first use a division-free float test (`n_a·n_b·d² ≤ bound·(n_a+n_b)`, bound widened by 1e-4 to cover float rounding, infinite until the bound is), so most chunks never reach the exact double-precision cost. All of these are conservative, so they change speed only, never output. The ring loop stops once even a one-pixel partner past the searched cube (cost ≥ `n/(n+1)·d²`) can't beat the bound.
   - Large clusters search far, and the cluster at the base of the chain is queried again after every merge above it. So a cluster whose search examined more than `cache_after` clusters twice gets a `Cache`: its `cache_size` cheapest candidates plus a threshold that no unlisted cluster can beat. Live clusters never change, so a later query drops dead candidates, offers clusters created since (`seen`), and only searches again if the best remaining candidate isn't strictly below the threshold.
   - Changes here alter clustering output, so check them with `npm run quality` (MSE on Kodak), not just the tests.
**`Palette` and `Clustering`** (`src/shared.js`, used by both entries) are constructor functions that return an ordinary `Uint8Array` with hidden non-enumerable tags (a `Symbol.for` property, and `colorSpace` on a palette), not subclasses: a subclass breaks `toEqual(new Uint8Array(...))` in users' tests (constructors differ). They answer `instanceof` through `Symbol.hasInstance` (so they must stay plain functions, not `class`es, or Babel's class-call check rejects `new`). Anything that returns a palette goes through `markPalette`, a clustering through `markClustering`; `matchingSpace` picks a palette's own space for mapping. A structured clone drops the tags, so values crossing the worker boundary travel as `{__agglomerativeClustering: 'palette'|'clustering', ...}` markers (`pack` in worker.js, `serialise` and `revive` in worker-thread.js).
- **Methods on `Clustering`** (`getPalette`, `getSwatches`, `getClusteringInfo`, `quantize`, `quantizeToIndices`, and from 3.8 `chooseFrom`, which has no function form) are added by `markClustering` as non-enumerable own properties. Each checks its receiver (`readHeader`), then forwards to its function form through an engine slot in `shared.js` that only `index.js` fills (`setEngine`), so a change to a function form changes its method; with the slot empty (worker entry alone, or the other module system's copy) they reject with `wasm-load-failed`. Methods never throw synchronously. A new cut-or-search function is a method plus a handle method, with no `…FromClustering` form (that family was removed in 4.0; PRINCIPLES "Settled decisions"): add it to `methods` and `methodNames` in `shared.js` and to the engine, declare it on `class Clustering`, and document it under "Clustering methods" in `docs/api.md` (`test/api.test.js` checks all three agree). Name it by PRINCIPLES "Names follow their family".

3. **Clustering format** (the `Uint8Array` returned to users), version 3, little-endian: a 22-byte header `[0xAC, 3, header length, record length, colour space, precision, weight unit (0 = pixels, 1 = 1/255 pixel), weight shift, total weight (u32), transparent cutoff (0 = none: the alpha cutoff it was made with, the default for a stored clustering's `quantizeToIndices`), grouped error (f32), checksum (u32), 1 zero byte]` (the grouped error is what `precision` < 8 discards before clustering, in the cost units, and `getClusteringInfo` adds it to the costs; a 13-byte header from before the field reads as 0; 22 keeps a header-only clustering at 4 mod 9), then `[root rgb (3 bytes)]`, then one 21-byte record `[merged rgb, heavier rgb, lighter rgb, parent (u32), lighter weight (u32), cost (f32)]` per merge, then 0, 3 or 6 zero bytes so the length is 7 mod 9. Records are in *reverse* merge order (split order), so record `i` splits the palette of size `i+1` into size `i+2`. `parent` is the split cluster's index in split order (root 0; record `i`'s lighter child is `i+1`, the heavier keeps the parent's index). Palettes are built by colour, but different clusters can share an 8-bit colour, so weights follow clusters by index and are summed per palette colour (`_get_palette_weights`). Weights are the grid's 32-bit counts; times `2^shift`, in the weight unit, they are pixels. `cost` is the merge's Ward cost (increase in squared error) in weight units times squared 8-bit RGB (or squared OKLab units); `getClusteringInfo` sums them into the per-k error curve in JS. Readers use the stored header and record lengths and ignore fields past the ones they know. Version 2 (2.x) had a 4-byte header `[0xAC, 2, colour space, precision]` and 9-byte records of colours only; version 1 (1.x) had no header. `read_clustering` and `readHeader` go by the magic byte and the version byte only; headerless 1.x clusterings, recognised by length, were dropped in 3.0 because other byte strings (palettes) share their lengths and were accepted as clusterings. An empty or fully transparent image gives a header-only clustering.
   - **Integrity.** The checksum (bytes 17–20, from 3.0.0-beta.2) is the CRC-32 of the whole clustering with those 4 bytes read as zeros, written by `ClusteringJob::take()` (`clustering_crc`) and checked in JS by `readHeader` (`crc32` in `shared.js`) the first time an array is used; arrays that passed, and those the library made (`markClustering`), are remembered in a `WeakSet`. 0 means no checksum (3.0.0-beta.1 wrote zeros) and is read unchecked. Independently, `_get_palette_from_clustering` checks the records as it replays them (each must split a colour in the palette at that point, and from v3 the cluster its parent index names) and the exports that read a stored clustering return a null pointer when they don't fit, which `call` in JS reports as `invalid-clustering`; so even a damaged unchecked clustering can't cut to more than k colours. `test/integrity.test.js` flips every bit of a small clustering, with and without the checksum.
   - Any format change follows the versioning rules in `docs/ROADMAP.md` ("Clustering format versioning"): readers decide by the version byte, writers pad to 4 or 7 mod 9 (a leftover of keeping out of 1.x's lengths, kept so v3 bytes stay stable), fields are added by lengthening the header or records without a new version, readers reject newer versions with an upgrade message (`readHeader`), and each version gets a fixture.
   - `_get_palette_from_clustering` keeps the palette as the colours of the current clusters, each with a count of clusters that have it (clusters can share an 8-bit colour, kodim14 at k > 50271; a plain set lost colours there, and beta.2's record check then rejected valid clusterings). `test/large-k.test.js` covers it. It replays the first `k-1` records in **split order**: the palette starts as the root; each record's parent keeps its index for the heavier child and the lighter child is appended. As a set this equals replaying into an unordered set, which is what 1.x did.
4. **`MappingJob`** (in a `MappingTask`, which owns the output buffer and a copy of the palette; `_quantize` and `_quantize_indices` run one to completion, and `mapping_job_start/step/result/free` drive it in slices, taking a palette or a clustering and `k`): its constructor builds a nearest-colour index over the palette in the matching space (returns a palette index; exact ties go to the smaller packed RGB key, so results don't depend on palette order) and maps each pixel to its nearest palette colour (through a direct-mapped memo of recent colours, so repeated colours skip the lookup), writing straight into the length-prefixed output buffer. `step(timed, deadline)` resumes from a cursor counting pixels in visiting order: it reads the clock every 16,384 pixels undithered, every 1,024 dithered, and ordered also after every 64 recipes built, so a slice can end mid-row (everything carried between pixels, the error rows, recipe table and memos, is a member, so slicing never changes output; slices measured 10–16 ms, up to 39 ms at ordered 64 steps and 4096 colours, `bench/spikes/slicing-mapping/`); `timed` false never reads the clock. The pixel loops read the job's members through `const` locals, since output written through `uint8_t*` could alias them; `emit` stays a reference (a local copy got inlined at every call site, 4 KB), and `scan_nearest`/`pick_recipe` are `always_inline` (left out of line in the big `step`, ordered dithering at 16 colours was 7% slower than 3.6.0). For palettes up to 1024 colours the index is a `PaletteIndex`: a 16³ (RGB) or 32³ (OKLab) grid whose cells are built on first use, each listing the entries whose least distance to the cell is at most the smallest greatest distance of any entry, so a lookup compares exact distances over a short list. Building a cell is a pass over the palette, so larger palettes use the `KDTree` (subtrees at exactly the best distance are still visited, for the tie-break). Both give identical answers: exact ties go to the smaller key, then (for a repeated entry) the first index. RGB matching uses the raw 8-bit values, so it is exactly the pre-colour-space behaviour. With `dither` > 0 it runs serpentine Floyd–Steinberg, scaled by the strength, carrying the error in the matching coordinates (8-bit RGB, or OKLab) so the chosen colour is the one that cancels it: error diffused in sRGB but matched in OKLab piles up into streaks; fully transparent pixels neither take nor pass on error. The error a pixel receives is limited in length to the coordinate range (a vector bound, not per channel: a per-channel clamp pins the target in a corner where several entries tie). A target within 1/8 of the range outside the cube is clamped to it and matched through the index; one further out (a palette that can't reach the image's colours, like saturated cyan with a 7-colour e-ink palette) is matched exactly by a pass over the palette, so the error moves later pixels to other entries instead of being thrown away. On extracted palettes this matches the old clamp-everything output at 64–256 colours and beats it at 4–16; on fixed palettes (e-ink, grey levels, black and white) it is better throughout. Dithering in OKLab memoises each pixel's OKLab coordinates too (the conversion takes three cube roots). Every method picks colours through one `pick` lambda (the in-cube and out-of-cube rule above). **Atkinson** (`dither_method` 1) is the same serpentine loop with 1/8 of the error to each of six neighbours (two ahead, three on the next row, one two rows down), the rest dropped. **Ordered** (2) is Knoll pattern dithering: each distinct colour gets a recipe of `steps` picks (the colour nearest the target plus the carried error times an internal strength, which the strength maps to through `knot_internal`, a table per step count measured so ordered dithering changes about the same share of pixels as Floyd–Steinberg at each strength, the error left uncapped: capping it was measured and made e-ink much worse), sorted by brightness (integer luma in RGB, L in OKLab, ties by key), and a pixel takes `recipe[bayer8[y&7][x&7] * mix / 64]`, so its colour depends only on its colour and position. Recipes are memoised per colour in a direct-mapped table (about 8 MB up to 16 steps, at least 2^17 slots above, and never more than twice the image's pixels, so tiny images don't pay for it). For RGB palettes up to 96 colours (measured: faster than the index up to about 128, slower above), recipe steps search with an exact four-wide (`i32x4`) scan instead of the index, also for whole-number targets outside the cube (exact: they match nearest_outside's double distances); `test/dither-methods.test.js` checks both paths against a plain JavaScript reference. It hands each pixel's palette index to a sink (one `PixelSink` type with a mode, not a template parameter, so the pixel loops are compiled once; a second copy cost 19 KB of WebAssembly): `_quantize` writes the colour (black for an empty palette) and preserves alpha for RGBA input; `_quantize_indices` writes the index, turns an empty palette into one black entry, and with `transparent_slot` gives alpha-0 pixels an extra entry after the palette.

C++17 is required (the header enforces it). Keep `std::sort` and `std::unordered_map` out of the C++: each instantiation costs kilobytes of WebAssembly (3–4 KB per sort, about 4 KB for the maps). Use `insertion_sort`/`radix_sort` in `clustering.hpp` and `AgglomerativeHistogram`'s `add`/`find` as a colour table. Keep the default allocator: `MALLOC=emmalloc` saves 6.7 KB but runs out of memory sooner (ROADMAP "Smaller WebAssembly, further").

## Design review

The reviewers in `.claude/agents/` (read-only; `user-advocate` may also run commands, writing only to its scratchpad) check a design against the project's written intent, so a proposal is not checked only by the agent that wrote it. Three stewards argue for keeping the library small; `user-advocate` argues the users' side, so the maintainer hears both. They run on Sonnet (`model:` in each file's frontmatter), chosen by the maintainer on 2026-11-24 to spend less of the usage quota; exploratory-round agents (outside users building projects against the package) also run on Sonnet, with their reports written to files. `docs/PRINCIPLES.md` is their ground truth (the charter, API principles and settled decisions), together with `docs/ROADMAP.md` and `docs/stability.md`.

| Agent | Question |
|---|---|
| `roadmap-steward` | Does this fit the roadmap and the settled decisions? Does it close off anything planned, 4.0 especially? |
| `api-steward` | Is the public surface consistent, compatible, and what a well-made library would ship? |
| `scope-steward` | Is this the library's job, or bloat? Would a smaller version or a recipe do? |
| `user-advocate` | What do users lose with only a recipe: would they find it, copy it right, and how much slower or worse is it? |

- **Value brief first, for a new capability.** Before writing a spec for something users couldn't do before, write a one-page value brief (`docs/superpowers/briefs/`, whose README has the sections): who asked, quoted; the user's symptom in their words; **the best recipe, built and measured through `dist/`**; and what a built-in adds over that recipe, with numbers, against what the recipe costs every user who needs it (PRINCIPLES test 1: its length, dependencies, internals, speed and traps). The maintainer's request with a use case passes "who asked" (test 2): don't count it as nobody asking. Run `scope-steward` and `user-advocate` on it, in parallel, then ask the maintainer: recipe, build or wait, with both verdicts. Only "build" goes on to a spec. Don't claim in a spec that a recipe can't do something without the measurement that shows it: the linear-light spec did, and a recipe then matched it (ROADMAP "Considered"). Fixes, speed work and internal changes skip the brief.
- **A cold-read user, for a new option or function:** with the proposed docs text, run a fresh `general-purpose` agent that knows only the README and `docs/` (not `src/`, specs or the ROADMAP), playing a user with the use case. Ask what it guesses the name does before reading the explanation, where it would look for it, and which rules it would get wrong. It found the naming problem in the linear-light review that the three stewards missed. Run it once, with the spec stewards.
- **Numbers in the docs have a source.** A new measured figure in `docs/` or the README comes from a script and results file in the repo (`bench/`, or `bench/spikes/<topic>/`), named in an HTML comment next to it. Don't write an estimate as a measurement.
- **One review round per stage.** Combine questions into the stewards' prompts rather than running a second round on the same document; a second round is for a changed document.
- **When:**
  - **On every written spec,** before it goes to the maintainer for approval: run the three stewards and `user-advocate`, in parallel, on the spec file.
  - **Before each major version,** run `user-advocate` and `scope-steward` over the recipes and ROADMAP "Considered" (PRINCIPLES "Recipes are reviewed again").
  - **In the final branch review,** alongside the code reviewer: write `git diff master...HEAD` to a file and run the three stewards on it (and `user-advocate` when the branch adds a capability or a recipe). This catches drift during implementation.
  - **Changes without a spec** that touch the public API, the docs' promises or the ROADMAP still get `api-steward`, and `roadmap-steward` for the ROADMAP. Internal fixes, speed work and tests skip review.
- **Each call gives:**
  - the proposal's path;
  - the stage (`spec` or `final review`);
  - any question to answer (for example, which of two options fits the roadmap).
- **Reporting:**
  - Their verdicts and findings go into the message that asks the maintainer to approve. Summarise them, with each finding's evidence line.
  - Don't drop findings you disagree with. Give your rebuttal next to them.
  - A `conflict` must be resolved in the spec, or explicitly accepted by the maintainer, before approval.
  - They advise; the maintainer decides.
- **Before recommending an option** in a design question, check it against the ROADMAP's 4.0 section and the settled decisions yourself. Additive now isn't enough if it leaves 4.0 with two ways to do one thing.
- **Keep the ground truth current, in the same change:**
  - a question the maintainer settles goes into PRINCIPLES.md "Settled decisions";
  - a deferral goes into the ROADMAP's 4.0 section;
  - a rejected feature goes into ROADMAP "Considered", with its reason.

## Releasing

**Version copies.** `package.json` is the source of the version. `src/shared.js` (`export const version`, which both entries re-export) and `src/version.hpp` (which the `.wasm` reports, and the JS checks at load: a mismatch is `wasm-load-failed`) are generated by `scripts/sync-version.mjs`, which `npm version` runs before committing. Don't edit them by hand: `npm run build` fails if they differ from `package.json`. `formatVersion` is different: it is the stored-data format (the clustering header's version, 3), so it changes only when the format does.

CI (`.github/workflows/ci.yml`) builds and tests every push to `master` or a `patch/*` branch and every PR. Publishing (`.github/workflows/publish.yml`) runs when a GitHub Release is published, using npm trusted publishing (no token; the package's npm settings link it to `publish.yml` and the `npm` environment). To release: `npm version <x.y.z | prerelease --preid beta>`, `git push --follow-tags`, then `gh release create vX.Y.Z --generate-notes` (add `--prerelease` for betas). The workflow fails unless the tag is `v` + the `package.json` version. `scripts/dist-tag.mjs` picks the dist-tag: versions containing `-` go to `next`, a version above the current `latest` to `latest`, and anything else (a patch to an older line) to `v<major>.<minor>-latest`. Both workflows pin the Emscripten version (`version:` on `setup-emsdk`), so the shipped `.wasm` is reproducible; bump it deliberately.

## Branches and releases

- **`master` is the next version** (and its betas). Branch features and fixes off an up-to-date master: `git switch master && git pull --prune && scripts/prune-branches.sh && git switch -c <type>/<short-name>`, then open a PR; the user merges. Tags (`vX.Y.Z`) are the record of each release.
- **Pruning.** `.github/workflows/prune-stale-branches.yml` runs `scripts/prune-stale-branches.sh` on every branch push (not on a schedule, so a quiet repo keeps its branches as a record): it deletes branches on GitHub that are done (merged into master, or with their tip in a `v*` release tag) and whose last commit is over a week old. It never touches master, tags or unfinished branches; `--dry-run` (or the workflow's manual run, dry by default) lists what would go. A deleted branch can be restored from its PR page. `scripts/prune-branches.sh` then removes the local copies whose remote is gone.
- **Protection.** A GitHub ruleset ("Protect master") blocks deleting or force-pushing `master`, for everyone. It doesn't require PRs or checks, because releases push the version commit and tag straight to master. To change it, go to Settings → Rules.
- **Patching an older line** (say 3.1.2 while master is on 3.2), with no long-lived branch: the line lives in its tags. Only the latest minor gets patches; older ones only on request.
  1. Branch from the line's last tag and push it: `git switch -c patch/3.1.2 v3.1.1`.
  2. Fix it through a PR into `patch/3.1.2`, or fix master first and `git cherry-pick -x` the fix across.
  3. On the patch branch: add the CHANGELOG section, `npm version patch`, `git push --follow-tags`.
  4. `gh release create v3.1.2 --target patch/3.1.2 --latest=false --generate-notes` (`--latest=false` keeps GitHub's "Latest" badge on the newest line). It publishes to the `v3.1-latest` dist-tag, not `latest`.
  5. Bring the fix to master if it isn't there (cherry-pick the fix, not the version bump), and add the 3.1.2 CHANGELOG entry there too.
  6. Nothing to clean up: once `v3.1.2` holds the branch's commits, the prune workflow deletes `patch/3.1.2` a week later. A 3.1.3 starts again from `v3.1.2`.
