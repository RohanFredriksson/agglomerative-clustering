# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An npm package (`agglomerative-clustering`) that does colour-palette extraction and image quantization using hierarchical agglomerative clustering. The algorithm is written in C++ and compiled to WebAssembly with Emscripten; a thin JS wrapper exposes an async API for Node and browsers.

## Commands

- `npm run build`: builds everything into `dist/`. Needs Emscripten (`em++`) on PATH for the WASM step.
  - `npm run build:wasm`: compiles only `src/clustering.cpp` → `dist/clustering.js` + `.wasm`. The full `em++` flag set (it must be `em++`, not `emcc`: current Emscripten no longer links libc++ for `emcc`) (exported functions, memory limits) lives in this script in `package.json`.
  - `npm run build:js`: Babel-transpiles `src/index.js` to `dist/index.cjs` and `dist/index.mjs`, and copies `index.d.ts`.
- `npm test`: runs vitest over everything under `test/`.
- Single test file: `npx vitest run test/smoke.test.js`. Single test: `npx vitest run -t "<name pattern>"`.
- `npm run bench`: quick vitest bench (`bench/speed.bench.js`): palette time at k=64 and for k=16/64/128/256, on two Kodak photos and noise, against the other libraries.
- `npm run bench:full`: the full harness (`bench/run.js`, options documented at the top of the file). For each image (Kodak + synthetic in `bench/lib/images.js`), library and k it records palette time, quality of that palette under one shared nearest-colour mapping (MSE, PSNR, mean CIEDE2000), and the library's own quantize time/quality. Results go to `bench/results/<label>.json` (gitignored) and a summary is printed. A full run takes about 20 minutes; use `--libs none`, `--kodak-limit`, `--k` and `--sets` to narrow it.
  - `--ac name=path/to/dist/index.mjs` (repeatable) benchmarks other builds of this library side by side, e.g. a build of `master`. Append `#key=value,...` to pass options, e.g. `--ac oklab=dist/index.mjs#colorSpace=oklab` (dither gets the image width automatically).
  - `npm run bench:compare -- a.json b.json` compares results files (before/after a change).
  - `bench/COMPARISON.md`: a written-up run of the full harness against the other libraries (quality and speed). Regenerate it when the algorithm or its speed changes materially.
  - `npm run quality`: the harness without the own-quantize timings.
- `npm run demo`: serves the repo root (`demo/serve.mjs`, no dependencies) so `demo/index.html` can load `dist/index.mjs`; build first. The page clusters once and re-cuts on a palette-size slider.
- Other libraries live behind adapters in `bench/lib/quantizers.js` (image-q NeuQuant/Wu/RgbQuant, MMCQ via `quantize`, libimagequant via `libimagequant-wasm`). They are dev dependencies used only for benchmarking.

**Tests and benches import from `dist/index.mjs`, not `src/`.** Rebuild (`npm run build`, or `build:wasm` after C++ changes) before you run them, or they will exercise stale code. `src/index.js` imports `./clustering.js`, which exists only in `dist/` after the WASM step.

The Kodak tests (`test/visual/kodak.test.js`), the benchmarks and `fixtures/kodak.js` download images on first run into `fixtures/images/` (gitignored), so they need network access. Node's `fetch` ignores `HTTPS_PROXY`, so behind a proxy, pre-download them with `curl` from one of the URLs in `fixtures/kodak.js`, saved as `fixtures/images/kodimNN.png`. Visual test output goes to `test/visual/output/` (also gitignored). `test/setup.js` polyfills `ImageData` from `canvas` so the ImageData code paths can be tested in Node.

## Architecture

### JS ↔ WASM boundary (`src/index.js`)
- The WASM module is initialised lazily with `init()`. Each API call `_malloc`s an input buffer in the WASM heap, copies the data in, calls an exported C function, then `unpack`s the result and frees both buffers.
- All C exports return a pointer to a buffer that the C side `malloc`ed, with a **4-byte little-endian length prefix** followed by the payload (`pack_variable_size` in C++, `unpack` in JS). JS must `_free` that pointer.
- Image format is passed as an int code: `rgba = 0`, `rgb = 1`. Colour space likewise: `rgb = 0`, `oklab = 1` (`ColorSpace` in `src/colorspace.hpp`).
- Options are an optional trailing object on every function except `getPaletteFromClustering`, validated by `parseOptions` against the keys each function accepts (unknown keys throw): `colorSpace`, `precision` and `alpha` for clustering, `colorSpace`, `dither` and `width` for mapping, all five for `quantize`. They reach C as extra trailing arguments (`color_space`, `precision`, `weight_alpha` as 0/1, `dither` as a double strength, `width`). `quantizeWithClustering` passes `color_space` -1 when the option is absent, meaning "the clustering's colour space". `checkClustering` in JS rejects buffers whose length or header can't be a clustering.
- `getWrapper` makes the `quantize*` return types match the input type (Uint8Array / ImageData / `{data, format}`).
- If you add or rename a C export, update `EXPORTED_FUNCTIONS` in the `build:wasm` script, `src/index.js`, and `src/index.d.ts`.

### C++ pipeline (`src/clustering.cpp`, `src/clustering.hpp`)
1. **`_get_clustering`**: builds a colour histogram (`AgglomerativeHistogram`, an open-addressing table on packed 8-bit RGB that keeps colours in first-seen order; cluster ids follow that order). Colours become 16-bit clustering coordinates (`ColorCoordinates` in `src/colorspace.hpp`) so that weighted-average merges keep precision: RGB is upscaled from 8 bits, OKLab is scaled by one factor on all three axes so squared coordinate distances stay proportional to OKLab distances. With `alpha: 'weight'` (default, RGBA only) each pixel adds its alpha (units of 1/255 of a pixel) and alpha-0 pixels are skipped; if no pixel is partially transparent the weights are divided back to whole pixels, so opaque images and binary-alpha images cluster exactly as with alpha ignored. Histogram totals are 64-bit; if the total weight would overflow the grid's 32-bit counts (partly transparent images above ~16.8 MP) all weights are shifted down to fit, keeping each visible colour at least 1. With `precision` < 8, colours are then grouped by their top bits (a second histogram keyed on the masked colour) and each group enters as one cluster at its count-weighted mean. Records are converted back to 8-bit sRGB on output (each cluster once, by id), so the clustering format doesn't depend on the colour space. It then builds the exact Ward hierarchy: the clustering you get by always merging the pair with the lowest Ward cost, `n_a·n_b/(n_a+n_b)·‖a−b‖²` (the increase in total squared error). Merged centroids are count-weighted averages (floored to integers).
   - It uses a **nearest-neighbour chain**: follow each cluster to its cheapest partner until two clusters are each other's cheapest, merge them, and continue from the rest of the chain. Ward is reducible, so this gives the same hierarchy as the greedy global-minimum loop without a heap or cached partners.
   - The chain finds merges out of cost order. Each merge gets a height `max(cost, children's heights)` (centroid flooring can make a parent slightly cheaper than a child), and merges are stable-sorted by height before records are written, so every record comes after the ones that formed its clusters.
   - Partner ties break by cost, then the pair's (packed colour, cluster id) values. Every cluster ranks partners the same way, which keeps the chain acyclic and the output deterministic. Clusters are identified by id, so two clusters can share a colour (they merge next, at cost 0, as an `[m, m, m]` record).
2. **`WardGrid`**: the spatial index behind `nearest(id)`, the exact cheapest partner of a cluster. Nearly all clustering time is spent in its `search`, so check changes with instruction counts (callgrind on a native build) as well as the harness: wall-clock time on shared machines is noisy.
   - Cells are a dense uniform grid of `dimension`³ cells, with `dimension` taken from `dimensions` (1…128, each step about doubling the cell count); coordinate v is in cell `(v·dimension)>>16`, and `boundaries[k]` is the first coordinate of cell k. Image colours fill a small part of the RGB cube, so `reindex()` picks the finest size whose *occupied* cells average at least `target_occupancy` (24) clusters, counting each candidate size's occupied cells in a bitmap, from the current size down (clusters only merge). It runs after the initial adds and whenever the cluster count halves. The target was tuned in WASM on Kodak, OKLab and `precision: 6`: coarse cells with SIMD scans beat fine cells with more stepping. Each occupied cell (`Bucket`) stores its clusters in `Chunk`s of four lanes (colours as float vectors, counts, ids) so `search` computes four exact Ward costs at once with GCC/Clang vector extensions, which become WASM SIMD128 through `-msimd128` in `build:wasm`. The double-precision cost uses the same operations as `get_weight`, so it matches the scalar cost bit for bit. Unused lanes have id `none`, count 1 and a far-away colour, so their cost is huge. Each lane also holds its count as a float (`weight`), since unsigned→float converts are slow on x86 and in V8. Removal moves the cell's last lane into the hole. `bucket_bounds` holds, as two float vectors, the colour box of everything ever linked into each cell and (in `high` lane 3) the smallest count ever linked into it; removals only loosen them, so they stay valid bounds. `columns` has one bit per cell for each (x, y) column, set when the cell has a bucket.
   - `search` scans rings of cells outward, visiting only cells whose `columns` bit is set (the ring's z range and its two end cells are bit masks computed once per ring). The chain passes the cluster below `a` as a `hint`: a live partner whose cost bounds the search from the start. A cell is skipped when its lightest possible member, at the nearest point of its colour box, can't beat the bound; otherwise its chunks' costs are computed four at a time and only lanes that beat the bound are offered. Both the cell test and each chunk first use a division-free float test (`n_a·n_b·d² ≤ bound·(n_a+n_b)`, bound widened by 1e-4 to cover float rounding, infinite until the bound is), so most chunks never reach the exact double-precision cost. All of these are conservative, so they change speed only, never output. The ring loop stops once even a one-pixel partner past the searched cube (cost ≥ `n/(n+1)·d²`) can't beat the bound.
   - Large clusters search far, and the cluster at the base of the chain is queried again after every merge above it. So a cluster whose search examined more than `cache_after` clusters twice gets a `Cache`: its `cache_size` cheapest candidates plus a threshold that no unlisted cluster can beat. Live clusters never change, so a later query drops dead candidates, offers clusters created since (`seen`), and only searches again if the best remaining candidate isn't strictly below the threshold.
   - Changes here alter clustering output, so check them with `npm run quality` (MSE on Kodak), not just the tests.
3. **Clustering format** (the opaque `Uint8Array` returned to users), version 2: a 4-byte header `[0xAC, 2, colour space, precision]`, then `[root rgb (3 bytes)]`, then one 9-byte record `[merged rgb, a rgb, b rgb]` per merge, with `a` the heavier child. Records are written in *reverse* merge order, so record `i` splits the palette of size `i+1` into size `i+2`. Version 1 (1.x) had no header; `read_clustering` tells them apart by length (v1: 0 or 3 mod 9; v2: exactly 4, or 7 mod 9) and treats v1 as RGB. An empty or fully transparent image gives a header-only clustering.
   - `_get_palette_from_clustering` replays the first `k-1` records in **split order**: the palette starts as the root; each record's parent keeps its index for the heavier child and the lighter child is appended (v1 records don't order children, so the child nearer the parent, their weighted mean, counts as heavier). As a set this equals replaying into an unordered set, which is what 1.x did.
4. **`_quantize`**: builds a nearest-colour index over the palette in the matching space (returns a palette index; exact ties go to the smaller packed RGB key, so results don't depend on palette order) and maps each pixel to its nearest palette colour (through a direct-mapped memo of recent colours, so repeated colours skip the lookup), writing straight into the length-prefixed output buffer. For palettes up to 256 colours the index is a `PaletteIndex`: a 16³ (RGB) or 32³ (OKLab) grid whose cells are built on first use, each listing the entries whose least distance to the cell is at most the smallest greatest distance of any entry, so a lookup compares exact distances over a short list. Building a cell is a pass over the palette, so larger palettes use the `KDTree` (subtrees at exactly the best distance are still visited, for the tie-break). Both give identical answers. RGB matching uses the raw 8-bit values, so it is exactly the pre-colour-space behaviour. With `dither` > 0 it runs serpentine Floyd–Steinberg, scaled by the strength, carrying the error in the matching coordinates (8-bit RGB, or OKLab) so the chosen colour is the one that cancels it: error diffused in sRGB but matched in OKLab piles up into streaks; fully transparent pixels neither take nor pass on error. Dithering in OKLab memoises each pixel's OKLab coordinates too (the conversion takes three cube roots). Alpha is preserved for RGBA input.

C++17 is required (the header enforces it).

## Releasing

CI (`.github/workflows/ci.yml`) builds and tests every push to `master` and every PR. Publishing (`.github/workflows/publish.yml`) runs when a GitHub Release is published, using npm trusted publishing (no token; the package's npm settings link it to `publish.yml` and the `npm` environment). To release: `npm version <x.y.z | prerelease --preid beta>`, `git push --follow-tags`, then `gh release create vX.Y.Z --generate-notes` (add `--prerelease` for betas). The workflow fails unless the tag is `v` + the `package.json` version, and publishes versions containing `-` under the `next` dist-tag instead of `latest`. Both workflows pin the Emscripten version (`version:` on `setup-emsdk`), so the shipped `.wasm` is reproducible; bump it deliberately.
