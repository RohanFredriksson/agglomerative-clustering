# Changelog

## 3.0.0 (unreleased)

Every 2.x function and default is unchanged except one rename (`quantizeWithClustering` is now `quantizeFromClustering`, below), and palettes and quantized images are byte-identical to 2.0.0 for the same inputs and options (the golden tests pin this, and 2.0 clusterings still load and cut to the same palettes). New: a worker entry, cancellation and progress, indexed output, swatches, an error curve, error codes, and a new clustering format. See [Migrating](docs/migrating.md).

### Added
- **`IndexedImage.colors`:** the palette without the transparent entry (the same as `palette` when there is none), tagged with its colour space, so an indexed result's colours can be passed back to `quantizeToIndicesWithPalette` without the entry being added twice.
- **A clustering records its `transparent` cutoff** (`getClusteringInfo(c).transparent`, `false` for none), and `quantizeToIndicesFromClustering` uses it as the default cutoff, so clustering and mapping agree. Handles (`worker.cluster(image, { transparent })`) get the same.
- **Clearer errors for the usual wrong inputs:** a string, plain array, `ArrayBuffer`, canvas, `ImageBitmap`, image element or `Blob` passed as an image is named, with the one-line fix. `new Palette(...)` checks its source like any palette argument instead of coercing it.
- **`Palette` and `Clustering` types.** Palettes and clusterings are returned as ordinary `Uint8Array`s that carry a hidden tag (their `constructor` is still `Uint8Array`, so `toEqual(new Uint8Array(…))` in a test passes, and `slice`, `subarray` and structured clones give plain bytes). A palette knows the colour space it was made in, and a clustering can't be passed as a palette or the other way round, in TypeScript or at run time, with no guessing about bytes. `new Palette(bytes, 'oklab')` and `new Clustering(bytes)` (which checks the bytes, and is how stored clusterings get their type back) make them by hand. Exported from both entries, recognised across copies of the library (ES module, CommonJS, the worker entry), and carried across the worker boundary.
- **Encoded image files are recognised and rejected.** A bare `Uint8Array` that starts like a PNG, JPEG, GIF, WebP, BMP, TIFF, AVIF or HEIC file used to pass as RGBA pixels (when its length was a multiple of 4) and give a nonsense palette; it is now an `invalid-argument` error naming the format and how to decode it. Only bare arrays are inspected, so `{ data, format }` and `ImageData` are never second-guessed. Decoding files is on the roadmap.
- **`version` and `formatVersion`:** the library's version string and the integer version of the data it stores (clusterings), exported from both entries. And the WebAssembly module now reports its own version, so a `.wasm` left over from another version (a stale cache or CDN copy) fails with `wasm-load-failed` and names both versions instead of misbehaving. `npm version` keeps all the copies in step (`scripts/sync-version.mjs`), and the build fails if they differ.
- **Worker entry, `agglomerative-clustering/worker`.** The same functions, run in a Web Worker (browsers) or worker thread (Node) so clustering doesn't block the calling thread. `createWorker()` starts a worker of its own. Its `cluster(image)` returns a handle that keeps the image and its clustering in the worker, so re-cutting (`getPalette`, `getSwatches`) and re-mapping (`quantize`, `quantizeToIndices`) copy nothing across. Results are transferred rather than copied, inputs too with `createWorker({ transfer: true })`. An idle worker never keeps a Node process alive. Handles can also map their kept image with a palette of your own (`quantizeWithPalette`, `quantizeToIndicesWithPalette`), in the colour space the handle was clustered in unless you pass one, so mapping the handle's own palette gives the same image as `handle.quantize`. Handles release with `release()` or `await using`, and are freed on garbage collection if dropped. The shared worker behind the direct exports can be stopped with `terminate()`. Calls to a worker run one at a time, in the order they were made. It works with `import` and `require`.
- **Cancelling and progress.** Every function that takes an image accepts `signal` (an `AbortSignal`) and `onProgress` (called with 0 to 1). With either, the clustering runs in slices of about 10 ms, so an abort takes effect within a slice and a page stays responsive. Aborting rejects with the signal's reason, like `fetch`, and the result of a call is the same with or without these options. Without them nothing changes; slicing adds about 5% when used. Pixel mapping can't be interrupted. In the worker entry the worker itself stops working on a cancelled call, and a call still queued behind another never runs.
- **Indexed output:** `quantizeToIndices`, `quantizeToIndicesFromClustering` and `quantizeToIndicesWithPalette` return `{ palette, indices, indexBits, transparentIndex }` instead of a mapped image: one palette index per pixel (`Uint8Array` up to 256 entries, `Uint16Array` up to 65536, else `Uint32Array`, with `indexBits` saying which), for palette PNGs, GIFs, pixel art and pattern generators. The indices pick out exactly the colours the matching `quantize*` call gives.
- **`transparent` option** for indexed output: `true`, or an alpha cutoff from 1 to 255 (`true` means 128). RGBA pixels with alpha below the cutoff get their own entry, appended after the palette (`transparentIndex` is its index, or `null` if there is none); every other pixel is shown fully opaque in its nearest colour, as GIFs and palette PNGs need. Where the palette is built from the image, pixels below the cutoff are left out of it and the rest count whole; they also take no part in dithering.
- **Swatches:** `getSwatches(image, k)` and `getSwatchesFromClustering(clustering, k)` return `{ palette, weights, shares }` from one cut of one clustering, so the three arrays line up by construction: the palette, each colour's weight in pixels (opacity-weighted, as in clustering) and its share of the image (they sum to 1). One call gives swatches with percentages, and the worker handle has `handle.getSwatches(k)`.
- **Clustering info:** `getClusteringInfo(clustering)` gives a clustering's format version, colour space, precision, number of colours and total weight, plus the error curve for choosing a palette size: `mse[k - 1]`, the mean squared error per channel of the k-colour clustering (`mse[0]` is the image's variance, also with a lower `precision`, whose discarded error is recorded), and `explained[k - 1]`, the unitless share of that variance it keeps (the same in `'rgb'` and `'oklab'`).
- **`init({ wasm })`** says where the WebAssembly module is, for CDNs, strict CSPs and runtimes that can't load it from next to the script: a URL or path, its bytes, or a compiled `WebAssembly.Module`. `createWorker({ wasm })` and `worker.init({ wasm })` pass it to a worker. The package also exports the file as `agglomerative-clustering/clustering.wasm`.
- **Running out of memory is a clear, recoverable error.** An image too big for WebAssembly's 2 GB used to fail with an unhelpful `RuntimeError: Aborted()` and leave the module unable to handle normal images afterwards (the aborted call's memory is never freed). It now rejects with an `out-of-memory` error that suggests `precision: 6`, and the module is replaced so later calls work.
- **Errors carry a `code`** (`invalid-argument`, `invalid-clustering`, `unsupported-version`, `out-of-memory`, `wasm-load-failed` (the WebAssembly module could not be loaded or compiled, with advice on what to check), plus `worker-terminated`, `worker-failed` and `invalid-handle` in the worker entry), typed as `ErrorCode`. Messages are unchanged. In the worker entry, errors keep their `name`, `message` and `code`, show the stack of your call, and carry the worker's stack as `cause`.
- **README recipes for using the output** ("Using the output"): flat palettes to `[[r, g, b]]`, CSS and `0xRRGGBB`, swatches with shares, a GIF with gifenc and a palette PNG with fast-png, both with a transparent background, and heaviest-first ordering for a palette and for an indexed image. A test runs them against the real encoders, so they can't drift from the API.
- **TypeScript declarations are tested as a consumer sees them** (`npm run test:types`, in CI): strict mode, `skipLibCheck` off, `nodenext` (ES module and CommonJS importers), `bundler` resolution, and a Node-only project without the DOM lib. The types don't need `ImageData` or `WebAssembly` globals, and `quantize`, `quantizeFromClustering` and `quantizeWithPalette` are generic over the input (`ImageResult<I>`), so a value typed `ImageLike` is accepted. CommonJS importers get their own `index.d.cts`. The worker entry's declarations need TypeScript 5.2 or `skipLibCheck` (for `await using`).

### Changed
- **`alpha` together with `transparent` is an error.** A cutoff replaces opacity weighting, so naming both used to leave `alpha` silently ignored; it is now `invalid-argument`. Either one alone, or `transparent: false` with `alpha`, is fine.
- **`quantizeWithPalette` and `quantizeToIndicesWithPalette` match in a `Palette`'s own colour space** unless you name one, so an OKLab palette is mapped the way it was made. Before, every palette was matched in RGB unless you passed `colorSpace` (plain bytes still are, and a worker handle uses its clustering's space for them). In TypeScript the clustering parameters are typed `Clustering`, so stored bytes need `new Clustering(bytes)`; plain bytes are still accepted at run time.
- **`onProgress` only where there is progress.** The functions that only map pixels (`quantizeFromClustering`, `quantizeWithPalette` and their indexed forms, and the worker handle's methods) take `signal` (checked before the call starts, and in the worker it cancels a call still queued) but no longer accept `onProgress`, which could only ever report 1. It is an `invalid-argument` error there. The abort rejection is the signal's own `reason`, so it has no `ErrorCode`: documented, and typed as such (`CancelOptions`).
- **`getClusteringInfo` fields renamed:** `version` is now `formatVersion` (it is the format of the clustering's bytes, and `version` is the library's own version, a different thing) and `colors` is now `maxColors` (the largest palette it can be cut to). Same values, new names. This is in the unreleased 3.0 info object, so nothing shipped changes.
- **In indexed output `k` counts the transparent entry,** so `quantizeToIndices(image, 256, { transparent: true })` gives at most 256 entries (255 colours and the transparent one) with 8-bit indices, the limit of a GIF or palette PNG, instead of 257 entries and 16-bit indices. At least one colour is always kept. With `quantizeToIndicesWithPalette` there is no `k`, so the entry is still added to the palette you give.
- **`transparent` is a clustering option too** (`getClustering`, `getPalette`, `getSwatches`, `quantize`, `quantizeToIndices`): pixels with alpha below the cutoff are left out of clustering and the rest count whole, so `getPalette(image, k, { transparent: true })` is the palette `quantizeToIndices` uses (it used to be chosen differently inside the indexed functions).
- **Options objects are read once, as a plain copy.** Every function (and the worker entry, `init` and `createWorker`) copies the options it is given before validating them, so what is checked is what is used even for a getter, options layered with `Object.create(defaults)` are honoured everywhere including through the worker (structured cloning used to drop inherited properties), and an inherited unknown key is rejected like an own one.
- **A `width` option that disagrees with the image's own width is now an error.** Before, `options.width` silently won over `ImageData.width` (or `RawImage.width`), so a wrong value that divided the pixel count dithered with the wrong row length and no error. Passing the same width twice, or a width for an image that has none, works as before.
- **Documentation: choosing a colour space.** `'rgb'` stays the default (so palettes remain byte-identical to 2.0). The README now has a use-case table (swatches, PNG-8, dithered GIF, graphics, gradients, noisy images) from measurements on the Kodak photos, and no longer says `'oklab'` is generally more perceptual: on photos RGB is better at low colour counts, for PSNR and with dithering; OKLab is better at 256 colours, on smooth gradients and on noisy images.
- **`quantizeWithClustering` is now `quantizeFromClustering`,** so one word means "the colours come from a clustering": the `…FromClustering` functions (`getPaletteFromClustering`, `getSwatchesFromClustering`, `quantizeFromClustering`, `quantizeToIndicesFromClustering`) derive them from one you hold, and `…WithPalette` functions take colours you supply. Before, the `get*` family said `From` and the `quantize*` family said `With`. The arguments and behaviour are unchanged: replace the name in your calls. (`quantizeToIndicesFromClustering` is new in 3.0, so only `quantizeWithClustering` needs migrating.)
- **Clustering format version 3.** A self-describing 22-byte header (magic byte, version, header and record lengths, colour space, precision, weight unit, total weight and the error discarded by a lower `precision`), then 21-byte records that add each split's parent, lighter-half weight and Ward cost to its colours. Clusterings are about 2.3 times larger than 2.x's. 2.x clusterings still load, **1.x clusterings are no longer read** (see below), a clustering from a newer format version is rejected with an error asking for an upgrade, and **2.x cannot read 3.x clusterings**. Future versions follow the rules in `docs/ROADMAP.md`, so their clusterings can never be mistaken for older formats.
- **1.x clusterings are no longer read.** They had no header and could only be recognised by their length, which many other byte strings share: a palette of 1, 3, 4, 6, 7, 9 … colours passed where a clustering was expected was accepted as one and returned nonsense without an error. A buffer must now carry the clustering header, so a swapped palette is always rejected with `invalid-clustering`, and the message for a headerless buffer says that 1.x clusterings need clustering again. The 1.x fixture stays as a test that it is rejected.
- **`engines: { node: "^20.19.0 || >=22.12.0" }`.** The CommonJS build loads the WebAssembly glue through `require()` of an ES module, which older Node versions don't support. CI tests Node 20, 22 and 24.
- **`init()` takes an optional options object, and concurrent first calls share one load.** Before, each of several simultaneous first calls instantiated the module; a load that fails is now forgotten, so it can be retried.
- **The published WebAssembly is built with Emscripten 6.0.12** (was 4.0.10), the version the benchmarks use. Output is identical. Speed is close to 2.0: on the Kodak photos (interleaved against the published 2.0.0) a palette or a dithered `quantize` takes 0 to 6% longer, because clustering now records more per merge (hence the 2.3 times larger clustering), and pixel mapping is unchanged. The module grows from 75 KB to 88 KB, from indexed output, cancellable clustering and the larger format.

### Fixed
- **A wide-gamut `ImageData` lost its colour space.** `quantize*` on an `ImageData` in `display-p3` returned one labelled `srgb`, from both entries and from worker handles, so drawing it on a wide-gamut canvas shifted the colours. The result keeps the input's `colorSpace`.
- **TypeScript results narrow.** `IndexedImage` is a union on `indexBits` (checking it narrows `indices` to the right array type), `ClusteringInfo` a union on `formatVersion` (3.x fields are non-null once narrowed, and `precision` is never null), and the palette parameters of `quantizeWithPalette` and `quantizeToIndicesWithPalette` accept a `Uint8ClampedArray` or a plain number array as the runtime always did (`PaletteLike`).
- **Documentation: index 0 is not always the heaviest colour.** The 2.x docs said index 0 is the dominant colour. That holds at two colours; at larger sizes index 0 keeps its place as the palette grows (each split keeps the heavier half in the parent's slot and appends the lighter), but a heavier colour can sit elsewhere (in a check of 24 images, 12 Kodak photos and 12 synthetic, index 0 was the heaviest entry in half of them at 8 colours, in 5 at 64 and in none at 256). The palettes did not change, and 3.0's are byte-identical to 2.0's. If you need heaviest first, sort the palette with the weights from `getSwatches` (see "Using the output"); that gives up the stable order across sizes.
- **Inputs that were accepted but misread are now rejected.** An `options` argument that wasn't an ordinary object (a `Map`, `Date`, `ArrayBuffer`, typed array) had no own keys, so it passed as `{}` and its settings were silently ignored. A `RawImage` `width` or `height` of `1.5`, `-3` or `'x'`, or a width and height that didn't match the data, was accepted and copied into the result. Both now throw `invalid-argument`.
- **A plain-array palette was never checked beyond its length.** An array of three `[r, g, b]` colours (the shape gifenc and fast-png use) has length 3, passed, and became an all-black palette without an error; strings were coerced and out-of-range values wrapped (300 became 44). Plain arrays must now be integers from 0 to 255, or they are rejected with `invalid-argument`.
- **A worker that failed left every later call hanging.** If the worker could not start (a blocked or missing worker script, a strict CSP, a misconfigured bundler) or crashed, the calls waiting on it were rejected with `worker-failed`, but later calls were posted to a thread that would never answer. A failed worker is now dropped: later calls start a fresh one, and either work or fail the same clear way. A start that fails is no longer cached, and a cancelled `cluster()` releases whatever the worker kept for it. The shared `init` export also ignored its options; it now passes them on.
- **The worker entry hung on Bun.** Inside a Bun worker thread both Node's `parentPort` and the browser's `self.postMessage` exist, and the thread script listened on `self` while the parent wrote through `parentPort`, so no call ever completed. The thread now picks its channel the way the parent does (Node-style where Node's APIs exist). Deno and Bun are checked by hand.
- **Bundling with webpack 5 failed.** The Emscripten glue's Node-only `import("node:module")` stopped webpack with `UnhandledSchemeError` for a browser target (and made Vite warn that the module was externalized). esbuild, and so Wrangler for Cloudflare Workers, failed the same way on it and on the worker entry's `node:worker_threads` import. Those imports now build their specifier at run time, which no bundler tries to resolve (`scripts/patch-glue.mjs` does it for the Emscripten glue, and fails the build if the glue changes shape), and CI bundles the test app with Vite and webpack and the entries with esbuild. Checked by hand in Parcel 2 and in Miniflare (workerd).
- A `Uint8ClampedArray` that is a view into part of a larger buffer (such as a `subarray`) was read from the start of the whole buffer, so `RawImage` data given that way was clustered and quantized from the wrong bytes. Only the view's own bytes are read now.
- Image data whose length isn't a whole number of pixels (a multiple of 4 for RGBA, 3 for RGB) was silently truncated, giving a shorter output. It is now rejected with `Invalid image data`.
- `quantizeWithPalette` checks its palette: anything other than a `Uint8Array`, `Uint8ClampedArray` or array, or a length that isn't a multiple of 3, is rejected with `Invalid palette` instead of being truncated or failing with an unrelated error. An empty palette is still accepted.
- A palette size of 2^31 or more returned an empty palette without an error. It now means all colours, like any `k` above the number of colours.
- The README gave 2.0's WebAssembly module size as 65 KB; it was 75 KB.

## 2.0.0

The same functions and defaults (`rgb`, no dithering, `precision: 8`), with these changes. See [Migrating](docs/migrating.md).

### Performance
- **Faster clustering, with identical output.** On the Kodak photos (WASM, Node 22), one palette takes about 100 ms instead of 155 ms, and with `colorSpace: 'oklab'` about 110 ms instead of 250 ms, so OKLab now costs no more than RGB. `precision: 6` takes about 30 ms. The partner search's grid comes in sizes between powers of two with coarser cells, steps over empty cells with per-column occupancy bits, tests cells with a division-free float bound, and starts each search from a known partner.
- **Faster pixel mapping, with identical output.** For palettes up to 256 colours, lookups go through a grid whose cells (built on first use) list the palette entries that can be nearest there, instead of the KD-tree, and dithering in OKLab memoises colour conversions. `quantizeWithPalette` at 64 colours takes about 6 ms per photo instead of 15 ms; a dithered `quantize` about 150 ms instead of 250–325 ms.
- Every clustering, palette and quantized image is byte-identical to before.
- The WebAssembly module grows from 58 KB to 65 KB.

### Changed
- **Palettes come in split order.** Index 0 is the dominant colour, and the palette for `k + 1` is the palette for `k` with one entry refined (the heavier half of a split keeps its parent's place) and the lighter half appended. For opaque images the colours are exactly those of 1.2, in this order.
- **Alpha weighting, `alpha: 'weight'` (the new default).** RGBA pixels count in proportion to their opacity: fully transparent pixels are ignored and semi-transparent ones count partially. Opaque images, and images whose pixels are all fully opaque or fully transparent, use exact pixel counts. `alpha: 'ignore'` restores the 1.x behaviour.
- **Clusterings carry a 4-byte header:** a magic byte, the format version, the colour space and the precision. Merge records list the heavier child first. 1.x clusterings still load: they are 0 or 3 bytes more than a multiple of 9, where 2.0's are 4 or 7.
- **`quantizeWithClustering` matches in the clustering's colour space** by default. An explicit `colorSpace` overrides it.
- **Pixel mapping breaks exact ties by the smaller packed RGB value,** so results don't depend on palette order. Mapping is a few percent slower as a result.
- **Invalid clusterings** now throw `Invalid clustering` instead of giving an empty palette.
- An empty or fully transparent image gives a clustering of just the header.

## 1.2.0

**Palettes differ from 1.1.x.** Clusters are now merged by Ward's method, so results change for practically every image even with default options; see Changed. The new options are all off by default.

### Added
- **`colorSpace: 'oklab'`**: clusters and matches colours in OKLab, where distance tracks perceived difference. It gives lower ΔE2000 from about 128 colours up and on smooth gradients, but lower PSNR. The clustering format is unchanged.
- **`precision` (1–8 bits per channel)**: groups colours that share their top bits before clustering, at their mean colour. `6` is about 3× faster on photos at practically the same quality.
- **`dither`** (`true` or a strength from 0 to 1) on `quantize`, `quantizeWithClustering` and `quantizeWithPalette`: serpentine Floyd–Steinberg error diffusion. It needs the image width, from `ImageData`, `RawImage.width` or the `width` option. Fully transparent pixels are left undithered.
- Every function that takes an image accepts these as an optional trailing `options` object. Unknown option names are rejected.
- `RawImage` accepts optional `width` and `height`, which are copied to `quantize*` results.
- `npm run demo`: an interactive page that clusters once and re-cuts on a palette-size slider.

### Changed
- **Clusters merge by Ward's method.** Each merge joins the two clusters whose merge adds the least squared error, `n_a·n_b/(n_a+n_b)·‖a−b‖²`, instead of the two nearest centroids, and the hierarchy is built exactly with a nearest-neighbour chain. Palettes are more accurate (see `bench/COMPARISON.md`) but differ from 1.1.x. Code that compares stored palettes or clusterings with 1.1.x output will see changes. Clusterings saved by 1.1.x still load, since the format is unchanged.
- **Faster partner search.** A spatial grid with SIMD Ward costs, pruning by each cell's colour box and a float pre-filter make the Ward search interactive: about 150–200 ms for a 768×512 photo.
- **Faster histogram and mapping.** The colour histogram is an open-addressing table, and pixel mapping memoises recent colours.
- The WebAssembly module grows from 41 KB to 55 KB.

### Fixed
- An image with no pixels aborted the WebAssembly module and left it unusable for the rest of the process. It now gives an empty clustering and palette.
