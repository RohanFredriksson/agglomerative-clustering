# Changelog

## 4.0.0 (in beta: 4.0.0-beta.2)

Premultiplied input, stricter image objects and result types that keep the input's. This is the first part of 4.0; the removals and new errors planned for it come in later betas. Output for every input without `premultiplied: true` is unchanged. See [Migrating](docs/migrating.md#from-3x-to-40).

### Breaking
- **Node 22.12 or newer.** `engines` is `>=22.12.0` (was `^20.19.0 || >=22.12.0`), the Babel targets say `node >= 22.12`, and CI tests Node 22 and 24. Node 20 reached end of life on 2026-04-30. Node 20 users stay on 3.8, which is patched on request. See [Migrating](docs/migrating.md#from-3x-to-40).
- **Unknown keys on an image object throw.** `{ data, format }` may have only `data`, `format`, `width`, `height` and `premultiplied`; any other key is `invalid-argument` on `'image'`, with a hint for near misses (`premultiply`, `widht`) and for a decoder's result (`channels`, `size`, `depth`). Spreading a decoder's result into an image object no longer works: build `{ data, format, width, height }`. The worker entry checks before posting.
- **Result types follow the input.** `RawImage` is a union split by `format`, and a mapped `{ data, format }` image comes back as the same type with `data: Uint8Array`, no cast needed. This also covers the `Clustering` methods and both kinds of handle. A variable reused across calls with different literal inputs needs a `RawImage` annotation, `interface X extends RawImage` becomes `type X = RawImage<'rgba'>`, and `premultiplied: true` on a format without alpha is rejected at run time (`invalid-argument`; the types accept a boolean).
- **`premultiplied: true` is no longer ignored** (3.x ignored it silently), and a `premultiplied` that is neither `true` nor `false` throws `invalid-argument` (3.x ignored any value).
- **A bare `Uint8Array` that looks like RGB, grey or grey and alpha is an error** (`invalid-argument` on `'image'`), on every call, where 3.5 and 3.6 warned once (`rgb-as-rgba`, `gray-as-rgba`). Same rules as the last 3.x release: on 2,984 real RGBA images, none flagged. Pass `{ data, format: 'rgb' }` for RGB, expand grey to RGBA, or say `{ data, format: 'rgba' }` if the bytes are RGBA. The warnings, their codes and `AgglomerativeClusteringWarning` are gone. See [Migrating](docs/migrating.md#from-3x-to-40).

### Added
- **`premultiplied: true` on `'rgba'` and `'bgra'` images**, for Electron's `nativeImage`, node-canvas and `@napi-rs/canvas` raw buffers, WebGL, WebCodecs frames made from a canvas and WIC `32bppPBGRA`. The library un-premultiplies its own copy of the pixels in place in the WebAssembly heap before clustering or mapping (5 ms on an opaque 12 MP image), and premultiplies mapped output again, so it goes back where it came from. Palettes, clusterings and indexed output are straight. Mapped results carry the input's `premultiplied`. It works in the worker entry, with `signal` and `onProgress`.
- **A recipe for straight output from a premultiplied source** (`ImageData`, PNG encoders): the guides' [Straight pixels from a premultiplied source](docs/guides.md#straight-pixels-from-a-premultiplied-source), exact and under 1% of the call. Don't un-premultiply the mapped output instead: 1,171 colours for `k = 16`.

### Changed
- The hint for a format named `'argb'` points at `'bgra'` with `premultiplied: true` instead of converting first.

### Fixed
- **The worker entry gave a different error for an image it couldn't send** (a function, a Symbol, a thenable, a `Proxy` as `data`, or an image with several faults where one value can't be cloned): `Invalid argument: it cannot be sent to the worker`, with no `argument`, where the main entry says what is wrong with the image, on `argument: 'image'`. The worker now runs the main entry's image checks before it posts, so the message, `code` and `argument` are the same. Options, palettes and clusterings that can't be sent still get `Invalid argument: it cannot be sent to the worker`. 3.x behaves the same and isn't patched.
- **An image object's fields are read once.** A `data` getter that answered differently on a later read made `quantize` return empty output with no error. `data`, `format`, `width`, `height` and `premultiplied` are now read a single time, at the start, in both entries, and the copies are what is checked and used. 3.x behaves the same and isn't patched.

### Docs
- The straight-output recipe says what `createWorker({ transfer: true })` does to it (the input is empty by the time alpha is read; send a copy) and has an RGBA variant for BGRA input going to a PNG encoder or `ImageData`.
- The guides say a palette PNG can't hold soft alpha (`transparent` is on or off per pixel) and point to the RGBA PNG route.
- The migration notes say that TypeScript doesn't flag a spread decoder result (it fails at run time) and name `ImageResult<RawImage>` for a reused result variable.
- The API docs say when WebGL `readPixels` bytes are premultiplied, and that a result read back from a canvas has more than `k` colours; the Electron section says to wrap a result's `Uint8Array` in a `Buffer` for `createFromBitmap`.

## 3.8.0

Additive: output and every existing call are unchanged. The fixed-palette search is built in, workers get a handle for a stored clustering, and the `…FromClustering` functions are deprecated ahead of their removal in 4.0.

### Added
- **`clustering.chooseFrom(palette, k, options?)`** chooses the `k` entries of a fixed palette (threads, bricks, inks) that best represent the clustered image, returning their positions and colours (`{ indices, palette }`). It is the guides' `chooseThreads` + `improveThreads` recipe moved into the library, with one change: the result always has exactly `k` entries. `colorSpace` (default `'rgb'`) and `signal` are its options.
- **`handle.chooseFrom(palette, k, options?)`** on a worker handle from `worker.cluster`: the clustering method of the same name, run in the worker (`colorSpace` and `signal`). A number or an image where the wrong kind of handle expects one now says which handle it is holding.
- **`worker.load(clustering)`** keeps a stored clustering in the worker and returns a `LoadedClusteringHandle`: `getPalette(k)`, `getSwatches(k)`, `getClusteringInfo()`, `chooseFrom(palette, k, options?)`, `quantize(image, k, options?)` and `quantizeToIndices(image, k, options?)`, with `release()` and `await using`. It replaces one-off `worker.getPaletteFromClustering(clustering, k)` calls, which send the clustering every time. The mapping methods take `signal` and `onProgress`. The clustering is checked and its bytes taken at the call, so a damaged clustering, a palette or an image rejects with `invalid-clustering` before anything is posted.

### Deprecated
- **The five `…FromClustering` functions, in both entries and on workers:** `getPaletteFromClustering`, `getSwatchesFromClustering`, `getClusteringInfo(clustering)` (the function; the methods keep the name), `quantizeFromClustering` and `quantizeToIndicesFromClustering`. Use `clustering.getPalette(k)`, `getSwatches(k)`, `getClusteringInfo()`, `quantize(image, k)` and `quantizeToIndices(image, k)` on the main thread, and the same methods on `await worker.load(clustering)` off it. TypeScript marks them deprecated; nothing changes at run time and there is no warning. 4.0 removes them. See [Migrating](docs/migrating.md#deprecated-in-38-removed-in-40).

### Docs
- **The guides' fixed-palette recipe is now one `chooseFrom` call.** If you copied 3.7.2's `chooseThreads` and `improveThreads`, `chooseFrom` gives the same choice: it was compared on the 24 Kodak photos with 584- and 1000-entry charts, 6 to 40 entries, in both spaces. The one difference is that it always returns exactly `k` entries. `countThreads` stays, shorter: it now takes the result, `countThreads(image, choice, options)`.
- **The cost of a live thread-count slider is measured:** the counting pass, not the search, is what costs. The guides give its time at 12 and 1 megapixels, and advise counting a downscaled copy while the slider moves.
- **Guides, recipes and the README use the methods and `worker.load`** in place of the deprecated functions.

## 3.7.2

Output and the API are unchanged; a progress bug is fixed, two error messages are clearer, and the guides' fixed-palette recipe goes back to RGB scoring and counts stitches.

### Fixed
- **Progress while mapping stopped rising above 4.3 million pixels**, then jumped to 1 at the end: on a 6.3-megapixel photo it sat at 0.68 for the last third of the mapping. The mapping job worked out its progress in 32-bit integers, which overflowed. Results and cancelling were unaffected. Found by an exploratory round on 3.7.1.

### Changed
- **A worker started from a `data:` URL without `wasm`** (a bundled worker script in a single-file host) now fails with a `wasm-load-failed` message that says the package can't tell where `clustering.wasm` is and to pass the module, `createWorker({ script, wasm: bytes })`. Before, it said to use `init({ wasm })` and serve the file, neither of which helps there. The same applies to code running from a `blob:` URL or an `about:srcdoc` page.
- **A worker from a `blob:` URL in a sandboxed iframe** (an opaque origin, as Figma's plugin UI is) fails in Chromium, and the `worker-failed` message now says why and to use a `data:` URL instead, linking the docs' recipe. Before, it said to serve `worker-thread.mjs`. Both found by the same round.

### Docs
- **The guides' fixed-palette recipe is back to RGB scoring by default, and counts stitches.** If you copied the 3.7.1 version, the new one chooses differently and returns the threads unsorted: pass `'oklab'` for the 3.7.1 choice, and use `countThreads` for the order. OKLab scoring (the default from 3.7.1) lowers the mean ΔE2000 but can grey out small vivid areas: a parrot's pink cheek and teal feather at 16 threads (seen by eye in the exploratory round on 3.7.1), and on the Kodak photos at 12 of 584 threads the most saturated pixels came out further off (ΔE2000 10.74 against 9.85)<!-- bench/spikes/fixed-subset-oklab/accents.mjs → results-accents.txt -->. `improveThreads` now measures in sRGB values unless you pass `'oklab'`, which the guides still suggest for a few widely spaced paints or inks. It no longer claims to return the threads heaviest first (the order came from swatch weights and was often wrong by real counts); a new `countThreads` maps the image and returns `{ thread, count }` most used first, leaving out threads no pixel was mapped to, for the legend and the shopping list. Copy the new version if you use it. Found by the exploratory round on 3.7.1.
- **Gaps the exploratory round on 3.7.1 ran into, filled.**
  - **Workers guide:** `signal` and `onProgress` on `worker.cluster` too, and what an aborted call rejects with. A large-export example with progress, Cancel and the handle released in `finally`, and how many workers to create.
  - **Plugins and single-file hosts:** a tested esbuild plugin that turns the worker script into a `data:` URL; what a plugin must pass (`wasm`, and a worker's `script`); and Obsidian's `main.js` as CommonJS.
  - **GIFs:** frames must share one size. The fast-png palette PNG without transparency.

## 3.7.0

`signal` and `onProgress` now work while mapping, in every function that takes an image and in both entries. Output is unchanged; an abort during mapping now rejects instead of letting the call finish (see Changed).

### Added
- **`onProgress` on the functions that map** (`quantizeWithPalette`, `quantizeFromClustering`, `quantizeToIndicesWithPalette`, `quantizeToIndicesFromClustering`, the `Clustering` methods `quantize` and `quantizeToIndices`, and the worker entry's functions and handle methods). It was rejected with `invalid-argument`. `quantize` and `quantizeToIndices` now report through the mapping too, where they stopped at about 0.9 until the end.
- **`signal` takes effect while mapping.** With `signal` or `onProgress`, mapping runs in slices of about 10 ms, with every dither method, as clustering does, so an abort stops it within a slice. In the worker entry the thread now stops too, so calls queued behind a cancelled mapping start at once. Slices measured 10 to 16 ms on a 6.3-megapixel photo and 4 megapixels of noise, up to 39 ms with ordered dithering at 64 steps and 4096 colours<!-- bench/spikes/slicing-mapping/slices.mjs → results-slices.txt -->. The result is byte for byte the same as one call's.
- In TypeScript, `MappingOptions` (and so `MappingIndexOptions`) now extends `ProgressOptions` instead of `CancelOptions`.

### Changed
- **An abort during mapping now rejects** with the signal's reason. Before, the mapping finished and the call resolved (in the worker entry, the caller already got the rejection at once). The docs listed this as a limitation, "Mapping can't be interrupted"; docs/stability.md now says that how soon an abort takes effect can improve in a minor release.
- **Calls that pass only `signal` to a function that maps are sliced**, which yields to the event loop between slices. They take within about 3% of the time of one call from 768×512 up, and under 0.3 ms more on a 64×64 image; a call that finishes in its first slice doesn't yield<!-- bench/spikes/slicing-mapping/overhead.mjs → results-overhead.txt -->. Calls without `signal` or `onProgress` are unchanged, and as fast as in 3.6.0.

### Performance
- The WebAssembly is 3.8 KB larger: 86 KB, 41 KB gzipped (it was 82 KB and 40 KB)<!-- bench/spikes/slicing-mapping/results-size.txt -->.

### Docs
- **The guides' recipes for cancelling and showing progress while mapping are gone**: `mapCancellably` (a worker of its own) and `mapInStrips` (strips of rows). Pass `signal` and `onProgress` instead. If you copied them, you can delete them; they still work. The strips left a faint seam at each strip edge with error diffusion and made ordered dithering up to 40% slower; the built-in slices are exact and cost about 3%. For 3.6 and older, the guides link the recipes' last version.
- The guides' "Workers" section no longer says that a call already mapping finishes, and drops the render loop built around it. The API reference's "In a worker the work in the worker stops too" is now true for mapping; until now it held only for clustering.
- **Choosing N colours from a fixed palette is 5 to 25 times faster.** The guides' `improveThreads` scored every (thread, position) swap with its own pass over the swatches; it now gets every position's score for a thread from one pass. It chooses the same threads (tested against the old search), and takes 18 ms for 12 of 584 threads and 37 ms for 40 of 1000, where it took 149 and 907 ms<!-- bench/spikes/fixed-subset-speed/speed.mjs → results-speed.txt -->. Copy the new version if you use it. The guides no longer suggest a Web Worker of your own for large charts, and say that the recipe needs the main entry.

## 3.6.0

Output is unchanged; one new warning, the 3.5.0 warning is reworded and catches more, cancelling stays prompt on very large images, and the WebAssembly is a fifth smaller.

### Warning
- **Grey bytes passed as a bare `Uint8Array` now get a warning, once** (`gray-as-rgba`). fast-png's `decode()` gives a grey PNG as 1 byte per pixel and a grey PNG with alpha as 2, which a bare array reads as RGBA: the palette came out wrong with no error whenever the length divides by 4 (on opaque grey + alpha photos it mapped hundreds of times worse). The message names the layout it saw. To fix it, convert to RGBA: the guides' new `fastPngToImage` does it for fast-png, or use a decoder that gives RGBA (pngjs, or sharp with `.ensureAlpha()`). There is no grey format to pass. In Node, `--no-warnings` silences it and `--trace-warnings` shows which call made it. It is shown once per copy of the library, only for a call that passes its own checks, and in the worker entry on your side after the call succeeds. From 4.0 this is an error. Tested on 2,984 real RGBA images with no false alarms<!-- bench/spikes/bare-grey/shipped.mjs → results-shipped.txt -->; see the API reference's "Warnings". Tools that parse stderr in Node, or fail on `console.warn` in browsers, will see it for bare grey input, which was giving wrong colours.
- **`rgb-as-rgba` no longer gives grey input the wrong advice.** Many grey arrays look like RGB to that check, and its message told them to pass `{ data, format: 'rgb' }`, which misreads them too. It now says "RGB (3 per pixel), or grey" and tells grey input to convert to RGBA.
- **`rgb-as-rgba` catches RGB images with a flat left margin.** The check sampled the bytes in evenly spaced windows that, for common sizes such as 768×512, were exactly one row apart, so it only ever saw the left edge: RGB cutouts on black were caught 6 times in 24<!-- bench/spikes/bare-grey/margins.mjs → results-margins.txt -->. The windows are now staggered: 24 of 24, with no new false alarms. On 7,051 test arrays this changed 20 decisions, every one an RGB array 3.5.0 missed (two ordered-dithered photos among them); none that 3.5.0 warned about goes quiet<!-- bench/spikes/bare-grey/rgb-changes.mjs → results-rgb-changes.txt -->. Its cost is about 0.35 ms a call (it was 0.25).

### Performance
- **Cancelling and progress reports stay prompt on very large images.** With `signal` or `onProgress`, clustering runs in slices of about 10 ms, but building the grid and writing the result ran in one piece, which grows with the number of distinct colours: up to 220 ms on a 12-megapixel photo and 1.4 s on 4 megapixels of noise in OKLab. Every step is now sliced, so the longest slice measured is 25 ms on that photo and 37 ms on that noise<!-- bench/spikes/slicing-build/slices.mjs → results-slices.txt -->. Results are byte-identical, and calls without `signal` or `onProgress` are as fast as before. The WebAssembly is 6 KB larger (2.3 KB gzipped: 47 KB), and the next entry more than takes it back.
- **Smaller WebAssembly: 82 KB, 40 KB gzipped** (it was 102 KB and 47 KB). The last `std::sort` calls are smaller sorts, and colour lookups use the table the histogram already has instead of `std::unordered_map`. Output is byte-identical and speed is unchanged, except that cutting a palette or swatches from a clustering at large `k` is about twice as fast (1 ms at 16,384 colours, was 2)<!-- bench/spikes/wasm-size/speed.mjs → results-speed.txt; results-size.txt -->. Sizes in base64, for plugin hosts that embed it: 110 KB, or 53 KB gzipped first.

### Docs
- **Choosing a palette size:** the guides' recipe changes. It was the smallest `k` with `explained ≥ 0.99`, which measured up to 28 times off the size an image needs, because `explained` is relative to the image's own variance. The new `sizeForError` sets a ceiling on the error instead (5 or 8 in 8-bit units), within a factor of 1.3 to 1.5 on average<!-- bench/spikes/palette-size/rules.mjs → results-rules.txt -->, and `sizeForScore` searches for the smallest size whose mapped image meets a score you supply, such as mean ΔE2000. Both are tested in `test/recipes.test.js`.
- **Keeping fast-png:** the guides' decoding section has `fastPngToImage`, which turns fast-png's RGBA, RGB, grey and grey + alpha results into images and refuses palette PNGs (which come back as indices plus a `palette`, and look like grey), 16-bit files and packed rows. `test/recipes.test.js` runs it.
- The API reference's "Warnings" lists both codes and says to match on `code`, not the text; stability.md and the API reference say grey, which has no format, is silenced by converting it.

## 3.5.0

Output is unchanged; one new warning (and one error message is reworded).

### Warning
- **RGB bytes passed as a bare `Uint8Array` now get a warning, once** (`rgb-as-rgba`). A bare array is read as RGBA, so RGB from a decoder (sharp's plain `.raw()`, without `.ensureAlpha()`) gave a wrong palette with no error whenever its length divides by 4. The library now checks a sample of the bytes (well under a millisecond at any size) and warns through `process.emitWarning` in Node, Bun and Deno, or `console.warn` elsewhere (browsers, Cloudflare Workers). No result changes. To silence it, say what the bytes are: `{ data, format: 'rgb' }`, or `{ data, format: 'rgba' }` if they really are RGBA; in Node, `--no-warnings` also works, and `--trace-warnings` shows which call made it. It is shown once per copy of the library, only for a call that passes its own checks, and in the worker entry on your side after the call succeeds. From 4.0 this is an error. Tested on 2,103 real RGBA images with no false alarms<!-- bench/spikes/bare-rgb/measure.mjs → results.txt -->; see the API reference's "Warnings". Tools that parse stderr in Node, or fail on `console.warn` in browsers, will see it for bare RGB input, which was giving wrong colours.

### Docs
- **Decoding image files:** a new guides section with a tested recipe for each environment, since the library takes decoded pixels and won't decode files itself (a settled decision: no decoders, no dependency on one; decoding is no longer on the roadmap): sharp in Node, `createImageBitmap` in browsers, and jsquash with omggif on edge runtimes such as Cloudflare Workers (PNG, JPEG, WebP and GIF, orientation applied). Each gives straight 8-bit RGBA whatever the file holds. It lists the traps found in testing: RGB passed bare, decoders such as fast-png that return palette indices, grey, packed or 16-bit rows as stored, animations giving their first frame, colour profiles ignored on the edge, and `createImageBitmap` options that block the page. `docs/environments.md` no longer points Workers users at fast-png, the README's sharp example applies the EXIF orientation (`.rotate()`), and the error for an encoded file names a decoder per environment.
- **Swatches heaviest first, hex strings and a dominant colour:** the guides' "Heaviest first" now has one tested recipe, `rankSwatches`. It turns swatches into `{ color, hex, share }` objects with the largest share first, and a dominant colour is its first entry. Built-in helpers were measured and not added (ROADMAP "Considered"). The dominant colour depends on `k`: going from 5 colours to 8 changed it by more than ΔE 10 on 11 of 24 Kodak photos, and the guides now say so. Other changes in the guides:
  - A ranked palette to map with is rebuilt as a `Palette` (`rankPalette`), because plain bytes are matched in RGB and an OKLab palette would quietly map in the wrong space.
  - An indexed image can be ranked heaviest first in two ways. Mapping to the ranked palette costs nothing extra. Renumbering by pixels mapped (`rankIndices`) keeps the transparent entry last and `colors` correct; it now takes about 40 ms at 12 megapixels, down from 250 ms.
  - The migration table and the README's swatches example link to the recipe.
  - The API reference now says what `quantizeToIndicesWithPalette` already did: the result's palette is the one you give, in its order, so each index is a position in it.

## 3.4.2

Output and the API are unchanged (one error message is reworded); the golden tests pin it.

### Performance
- **Ordered dithering with 65 to 96 colours is 10–23% faster** (RGB): recipe steps now use the exact four-wide scan up to 96 colours (it was 64), where it beats the palette index; above that the index stays faster. Measured on video frames at 480×270 and 160×90 (`bench/spikes/recipe-reuse/sizes.mjs`). New goldens at 96 colours, made before the change, pin that the output is the same.
- **Smaller WebAssembly:** `clustering.wasm` went from 127 KB to 96 KB (52 to 45 KB gzipped; as base64, for plugin hosts that take one file, 170 to 128 KB). Pixel mapping is compiled once instead of once per kind of output (colours or indices), and merges are sorted with a small merge sort instead of `std::sort`. Output is identical and mapping speed is unchanged.

### Docs
- **Faster ordered dithering for animations:** the guides' "Animated GIFs" section shows how to map frames in batches (`mapFramesInBatches`): frames stacked into one call, each padded to a multiple of 8 rows, give the same indices as one call per frame, and build each colour's recipe once. Batches of 12 took 0.36 to 0.78 of the time on film clips and 0.12 to 0.29 on screen recordings and pans. `test/recipes.test.js` runs it and checks it matches the guides. It rests on a property now promised through 3.x (API reference and stability.md): with ordered dithering, for a given palette and options, a pixel's result depends only on its own colour and its position modulo 8 from the image's top-left pixel. Which colours it picks can still change between releases, like any output. A built-in (a prepared palette or frame mapper) was measured and not added: the ROADMAP has why.
- **Cancelling or showing progress while mapping a large image:** a new guides section. The functions that map pixels run in one piece, which on a 6-megapixel photo at 256 colours is 2.6 s with Floyd–Steinberg and 7.5 s with ordered dithering. To cancel, map in a worker of its own and terminate it on abort (`mapCancellably`; exact, any dither method). To show progress, map in strips of rows (`mapInStrips`): the same indices as one call without dithering and with ordered dithering, a faint seam at strip edges with error diffusion. `test/recipes.test.js` runs both. The message for `onProgress` on a mapping function no longer says those functions finish in milliseconds; it points to the guides. A built-in (sliced mapping) is kept for later: the ROADMAP says what would bring it forward.

### Internal
- **Native fuzzing:** the C++ also builds natively (`scripts/native.sh`), and CI fuzzes it with libFuzzer, AddressSanitizer and UBSan, once on stored clusterings and once on images with random options. `scripts/native.sh profile` gives callgrind instruction counts. The first run found three `memcpy` calls on empty vectors, which is undefined behaviour though harmless in WebAssembly; they are now skipped. `scripts/asan-test.sh` runs the test suite against a sanitized WebAssembly build.
- **Browser smoke test with Parcel 2,** alongside Vite and webpack.
- **Contributor setup:** `scripts/setup-emsdk.sh` installs the Emscripten version CI pins, and `npm run build` says how when `em++` is missing.

## 3.4.1

Docs and tests only: output and the API are unchanged; the golden tests pin it.

### Docs
- **Dithering to a few inks, in light:** the recipe in the API reference is now a function, `ditherInLight`, a drop-in for `quantizeToIndicesWithPalette` when dithered photos come out too light on an e-ink panel or in black and white. ## 3.4.0

Output is unchanged; the golden tests pin it.

### Added
- **`buildClustering`, `buildPalette` and `buildSwatches`:** the functions that cluster an image now have verb names, in both entries and on `createWorker()` workers, so that a name starting with `get` reads or cuts what it is given (`clustering.getPalette(k)`, `getPaletteFromClustering`). Same arguments, options, results and errors.

### Deprecated
- **`getClustering`, `getPalette` and `getSwatches`** are the same functions under their old names (`getPalette === buildPalette`). They keep working through 3.x and are removed in 4.0; [Migrating](docs/migrating.md#deprecated-in-34-removed-in-40) has the table. The methods on clusterings and worker handles keep their names.
  - **Lint:** rules for deprecated APIs (`@typescript-eslint/no-deprecated`, `sonarjs/deprecation`) will now flag `getPalette(image, k)` and the other two.

- **The worker entry reports the same mistake as the main entry when a call has two.** It checked `signal`, `onProgress` and an object-form `dither` before the image and `k`, so `buildPalette(image, 0, { onProgress: 'x' })` gave `options.onProgress` in the worker and `k` in the main entry, and a call whose signal was already aborted rejected with the abort even when an argument was wrong. ## 3.1.0

Every 3.0 call gives the same output as before: `false`, `true` and a strength still mean Floyd–Steinberg, and the golden tests pin it.

### Added
- **Dither methods.** `dither` also takes `'atkinson'`, `'ordered'`, `'floyd-steinberg'`, or an object `{ method, strength, steps }`, which the other forms are shorthands for. `'ordered'` is pattern dithering: each colour gets a recipe of palette colours that average out to it, laid out in a fixed 8×8 pattern, so a pixel's colour depends only on its own colour and position and the still parts of an animation stay still from frame to frame. `steps` (`'ordered'` only: 2, 4, 8, 16, 32 or 64) is how many pattern cells a colour's mix is spread over, so two colours blend in `steps + 1` shades; the default is 64 for a palette of two colours and 16 otherwise. `strength` means about the same for every method: ordered dithering's goes through a table, measured for each step count, so it changes about the same share of pixels as Floyd–Steinberg's. `'atkinson'` is error diffusion that passes on 3/4 of the error, for a higher-contrast look. See "Choosing a dither method" in `docs/api.md`, which also shows how to dither to a few inks in linear light, so photos don't come out too light on e-ink and 1-bit panels. Types: `DitherMethod`, `DitherOptions`, `DitherSteps`.
- **Clearer option errors:** an invalid `dither` names the value it got, says to use `false` for `'none'`, and says to pass a number for a number given as a string (`steps: '16'`); a dither setting written as an option of its own (`ditherMethod`, `strength`, `steps`) points at `dither: { method, strength, steps }`.
- **Lists of names:** `colorSpaces`, `imageFormats`, `alphaModes`, `ditherMethods` and `ditherSteps`, frozen lists of every value of the options that take one of a fixed set of names, exported from both entries like `errorCodes`, for building a form's choices and narrowing its values (`ditherMethods.find((m) => m === value)`). Every such option has one, a rule written down in `docs/api.md` for options to come.
- **TypeScript:** `MappingOptions['dither']` now also includes `DitherMethod` and `DitherOptions`, so code that reads the option's type and handles only `boolean | number` needs a branch for them (see `docs/stability.md`).
- **An option-shape convention** (`docs/api.md`): an option is a plain value while it has one setting, and gets an object form, with its plain values as shorthands, when it has more. `dither` is the first. `docs/stability.md` now says an option may accept new values or an object form in a minor release.
- **`bench/dither.bench.js`:** mapping time for each method.

### Fixed
- **Cancelling a call queued behind a mapping call in a worker** now stops it from running. Mapping runs in one piece, so the worker read cancels only between calls, by which time the next call had already started: cancelled calls ran anyway, and a slider following the documented recipe could fall many seconds behind. The worker now takes a turn of its event loop before each call that can be cancelled (in a browser, a message to itself, which unlike a zero timeout isn't stretched to 4 ms), and skips it for a call already cancelled, so a hundred cancelled calls cost a few milliseconds.
- **Chrome and Edge 91–92 and Firefox 89–91:** the worker entry called `Object.hasOwn`, which those versions lack, so every worker call failed there. A test now checks that no built file uses it.

## 3.0.0

Every 2.x function and default is unchanged except one rename (`quantizeWithClustering` is now `quantizeFromClustering`, below). Palettes and quantized images are byte-identical to 2.0.0 for the same inputs and options, with one exception: `quantizeWithPalette` with a palette made in OKLab now matches in OKLab (below; pass `colorSpace: 'rgb'` for the 2.x result). The golden tests pin this, and 2.0 clusterings still load and cut to the same palettes. New: a worker entry, cancellation and progress, indexed output, swatches, an error curve, error codes, and a new clustering format. See [Migrating](docs/migrating.md).

### Added
- **Tested in every major browser engine.** CI runs the bundled browser checks (Vite and webpack, the worker, the `.wasm`, cancelling, transfer) in Chromium, Firefox and WebKit on Linux, and in the real Safari on macOS.
- **`error.argument`:** errors about one argument name it for programs (`'image'`, `'k'`, `'clustering'`, `'palette'`, `'options'` or `'options.<name>'`), in both entries and from the constructors, so a UI can point at the right field without parsing the message. Typed as `ErrorArgument`.
- **`IndexedImage.colors`:** the palette without the transparent entry (the same as `palette` when there is none), tagged with its colour space, so an indexed result's colours can be passed back to `quantizeToIndicesWithPalette` without the entry being added twice.
- **A clustering records its `transparent` cutoff** (`getClusteringInfo(c).transparent`, `false` for none), and `quantizeToIndicesFromClustering` uses it as the default cutoff, so clustering and mapping agree. Handles (`worker.cluster(image, { transparent })`) get the same.
- **Clearer errors for the usual wrong inputs:** a string, plain array, `ArrayBuffer`, canvas, `ImageBitmap`, image element or `Blob` passed as an image is named, with the one-line fix. `new Palette(...)` checks its source like any palette argument instead of coercing it.
- **`Palette` and `Clustering` types.** Palettes and clusterings are returned as ordinary `Uint8Array`s that carry a hidden tag (their `constructor` is still `Uint8Array`, so `toEqual(new Uint8Array(…))` in a test passes, and `slice`, `subarray` and structured clones give plain bytes). A palette knows the colour space it was made in, and a clustering can't be passed as a palette or the other way round, in TypeScript or at run time, with no guessing about bytes. `new Palette(bytes, 'oklab')` and `new Clustering(bytes)` (which checks the bytes, and is how stored clusterings get their type back) make them by hand. Exported from both entries, recognised across copies of the library (ES module, CommonJS, the worker entry), and carried across the worker boundary.
- **Encoded image files are recognised and rejected.** A bare `Uint8Array` that starts like a PNG, JPEG, GIF, WebP, BMP, TIFF, AVIF or HEIC file used to pass as RGBA pixels (when its length was a multiple of 4) and give a nonsense palette; it is now an `invalid-argument` error naming the format and how to decode it. Only bare arrays are inspected, so `{ data, format }` and `ImageData` are never second-guessed. Decoding files is on the roadmap.
- **`version` and `formatVersion`:** the library's version string and the integer version of the data it stores (clusterings), exported from both entries. And the WebAssembly module now reports its own version, so a `.wasm` left over from another version (a stale cache or CDN copy) fails with `wasm-load-failed` and names both versions instead of misbehaving. `npm version` keeps all the copies in step (`scripts/sync-version.mjs`), and the build fails if they differ.
- **Worker entry, `agglomerative-clustering/worker`.** The same functions, run in a Web Worker (browsers) or worker thread (Node) so clustering doesn't block the calling thread. `createWorker()` starts a worker of its own. Its `cluster(image)` returns a handle that keeps the image and its clustering in the worker, so re-cutting (`getPalette`, `getSwatches`) and re-mapping (`quantize`, `quantizeToIndices`) copy nothing across. Results are transferred rather than copied, inputs too with `createWorker({ transfer: true })`. An idle worker never keeps a Node process alive. Handles can also map their kept image with a palette of your own (`quantizeWithPalette`, `quantizeToIndicesWithPalette`), in the colour space the handle was clustered in unless you pass one, so mapping the handle's own palette gives the same image as `handle.quantize`. Handles release with `release()` or `await using`, and are freed on garbage collection if dropped. The shared worker behind the direct exports can be stopped with `terminate()`. Calls to a worker run one at a time, in the order they were made. It works with `import` and `require`.
- **Cancelling and progress.** Every function that takes an image accepts `signal` (an `AbortSignal`), and the ones that cluster also accept `onProgress` (called with 0 to 1). With either, the clustering runs in slices of about 10 ms, so an abort takes effect within a slice and a page stays responsive. Aborting rejects with the signal's reason, like `fetch`, and the result of a call is the same with or without these options. Without them nothing changes; slicing adds about 5% when used. Pixel mapping can't be interrupted. In the worker entry the worker itself stops working on a cancelled call, and a call still queued behind another never runs.
- **Indexed output:** `quantizeToIndices`, `quantizeToIndicesFromClustering` and `quantizeToIndicesWithPalette` return `{ palette, indices, indexBits, transparentIndex }` instead of a mapped image: one palette index per pixel (`Uint8Array` up to 256 entries, `Uint16Array` up to 65536, else `Uint32Array`, with `indexBits` saying which), for palette PNGs, GIFs, pixel art and pattern generators. The indices pick out exactly the colours the matching `quantize*` call gives.
- **`transparent` option** for indexed output: `true`, or an alpha cutoff from 1 to 255 (`true` means 128). RGBA pixels with alpha below the cutoff get their own entry, appended after the palette (`transparentIndex` is its index, or `null` if there is none); every other pixel is shown fully opaque in its nearest colour, as GIFs and palette PNGs need. Where the palette is built from the image, pixels below the cutoff are left out of it and the rest count whole; they also take no part in dithering.
- **Swatches:** `getSwatches(image, k)` and `getSwatchesFromClustering(clustering, k)` return `{ palette, weights, shares }` from one cut of one clustering, so the three arrays line up by construction: the palette, each colour's weight in pixels (opacity-weighted, as in clustering) and its share of the image (they sum to 1). One call gives swatches with percentages, and the worker handle has `handle.getSwatches(k)`.
- **Clustering info:** `getClusteringInfo(clustering)` gives a clustering's format version, colour space, precision, number of colours and total weight, plus the error curve for choosing a palette size: `mse[k - 1]`, the mean squared error per channel of the k-colour clustering (`mse[0]` is the image's variance, also with a lower `precision`, whose discarded error is recorded), and `explained[k - 1]`, the unitless share of that variance it keeps (the same in `'rgb'` and `'oklab'`).
- **`init({ wasm })`** says where the WebAssembly module is, for CDNs, strict CSPs and runtimes that can't load it from next to the script: a URL or path, its bytes, or a compiled `WebAssembly.Module`. `createWorker({ wasm })` and `worker.init({ wasm })` pass it to a worker. The package also exports the file as `agglomerative-clustering/clustering.wasm`.
- **Running out of memory is a clear, recoverable error.** An image too big for WebAssembly's 2 GB used to fail with an unhelpful `RuntimeError: Aborted()` and leave the module unable to handle normal images afterwards (the aborted call's memory is never freed). It now rejects with an `out-of-memory` error that says what to try (a smaller image, or `precision: 6`), and the module is replaced so later calls work.
- **Errors carry a `code`** (`invalid-argument`, `invalid-clustering`, `unsupported-version`, `out-of-memory`, `wasm-load-failed` (the WebAssembly module could not be loaded or compiled, with advice on what to check), plus `worker-terminated`, `worker-failed` and `invalid-handle` in the worker entry), typed as `ErrorCode`. Messages are unchanged. In the worker entry, errors keep their `name`, `message` and `code`, show the stack of your call, and carry the worker's stack as `cause`.
- **`errorCodes` and `isCodedError(value)`:** every code in one frozen list, and a type guard for the library's errors (also for an error's fields after Electron's IPC or a `postMessage`).
- **Recipes for using the output** ("Converting the output" in `docs/guides.md`): flat palettes to `[[r, g, b]]`, CSS and `0xRRGGBB`, swatches with shares, a GIF with gifenc and a palette PNG with fast-png, both with a transparent background, and heaviest-first ordering for a palette and for an indexed image. A test runs them against the real encoders, so they can't drift from the API.
- **TypeScript declarations are tested as a consumer sees them** (`npm run test:types`, in CI): strict mode, `skipLibCheck` off, `nodenext` (ES module and CommonJS importers), `bundler` resolution, and a Node-only project without the DOM lib. The types don't need `ImageData` or `WebAssembly` globals, and `quantize`, `quantizeFromClustering` and `quantizeWithPalette` are generic over the input (`ImageResult<I>`), so a value typed `ImageLike` is accepted. CommonJS importers get their own `index.d.cts`. The worker entry's declarations need TypeScript 5.2 or `skipLibCheck` (for `await using`).

### Changed
- **`alpha` together with `transparent` is an error.** A cutoff replaces opacity weighting, so naming both used to leave `alpha` silently ignored; it is now `invalid-argument`. Either one alone, or `transparent: false` with `alpha`, is fine.
- **`quantizeWithPalette` and `quantizeToIndicesWithPalette` match in a `Palette`'s own colour space** unless you name one, so an OKLab palette is mapped the way it was made. Before, every palette was matched in RGB unless you passed `colorSpace` (plain bytes still are, and a worker handle uses its clustering's space for them). In TypeScript the clustering parameters are typed `Clustering`, so stored bytes need `new Clustering(bytes)`; plain bytes are still accepted at run time.
- **`onProgress` only where there is progress.** The functions that only map pixels (`quantizeFromClustering`, `quantizeWithPalette` and their indexed forms, and the worker handle's methods) take `signal` (checked before the call starts, and in the worker it cancels a call still queued) but no longer accept `onProgress`, which could only ever report 1. It is an `invalid-argument` error there. The abort rejection is the signal's own `reason`, so it has no `ErrorCode`: documented, and typed as such (`CancelOptions`).
- **`getClusteringInfo` fields renamed:** `version` is now `formatVersion` (it is the format of the clustering's bytes, and `version` is the library's own version, a different thing) and `colors` is now `maxColors` (the largest palette it can be cut to). Same values, new names. This is in the unreleased 3.0 info object, so nothing shipped changes.
- **In indexed output `k` counts the transparent entry,** so `quantizeToIndices(image, 256, { transparent: true })` gives at most 256 entries (255 colours and the transparent one) with 8-bit indices, the limit of a GIF or palette PNG, instead of 257 entries and 16-bit indices. At least one colour is always kept. With `quantizeToIndicesWithPalette` there is no `k`, so the entry is still added to the palette you give.
- **`transparent` is a clustering option too** (`getClustering`, `getPalette`, `getSwatches`, `quantize`, `quantizeToIndices`): pixels with alpha below the cutoff are left out of clustering and the rest count whole, so `getPalette(image, k, { transparent: true })` is the palette `quantizeToIndices` uses (it used to be chosen differently inside the indexed functions).
- **Options objects are read once, as a plain copy.** Every function (and the worker entry, `init` and `createWorker`) copies the options it is given before validating them, so what is checked is what is used even for a getter, options layered with `Object.create(defaults)` are honoured everywhere including through the worker (structured cloning used to drop inherited properties), and an inherited unknown key is rejected like an own one.
- **A `width` option that disagrees with the image's own width is now an error.** Before, `options.width` silently won over `ImageData.width` (or `RawImage.width`), so a wrong value that divided the pixel count dithered with the wrong row length and no error. Passing the same width twice, or a width for an image that has none, works as before.
- **Documentation: choosing a colour space.** `'rgb'` stays the default (so palettes remain byte-identical to 2.0). The API reference now has a use-case table (swatches, PNG-8, dithered GIF, graphics, gradients, noisy images) from measurements on the Kodak photos, and no longer says `'oklab'` is generally more perceptual: on photos RGB is better at low colour counts, for PSNR and with dithering; OKLab is better at 256 colours, on smooth gradients and on noisy images.
- **`quantizeWithClustering` is now `quantizeFromClustering`,** so one word means "the colours come from a clustering": the `…FromClustering` functions (`getPaletteFromClustering`, `getSwatchesFromClustering`, `quantizeFromClustering`, `quantizeToIndicesFromClustering`) derive them from one you hold, and `…WithPalette` functions take colours you supply. Before, the `get*` family said `From` and the `quantize*` family said `With`. The arguments and behaviour are unchanged: replace the name in your calls. (`quantizeToIndicesFromClustering` is new in 3.0, so only `quantizeWithClustering` needs migrating.)
- **Clustering format version 3.** A self-describing 22-byte header (magic byte, version, header and record lengths, colour space, precision, weight unit, total weight, the error discarded by a lower `precision`, and a CRC-32 of the whole clustering), then 21-byte records that add each split's parent, lighter-half weight and Ward cost to its colours. Clusterings are about 2.3 times larger than 2.x's. 2.x clusterings still load (the palette and mapping functions read them; `getSwatchesFromClustering` and `getClusteringInfo` need the weights only 3.x records), **1.x clusterings are no longer read** (see below), a clustering from a newer format version is rejected with an error asking for an upgrade, and **2.x cannot read 3.x clusterings**. Future versions follow the rules in `docs/ROADMAP.md`, so their clusterings can never be mistaken for older formats.
- **1.x clusterings are no longer read.** They had no header and could only be recognised by their length, which many other byte strings share: a palette of 1, 3, 4, 6, 7, 9 … colours passed where a clustering was expected was accepted as one and returned nonsense without an error. A buffer must now carry the clustering header, so a swapped palette is always rejected with `invalid-clustering`, and the message for a headerless buffer says that 1.x clusterings need clustering again. The 1.x fixture stays as a test that it is rejected.
- **`engines: { node: "^20.19.0 || >=22.12.0" }`.** The CommonJS build loads the WebAssembly glue through `require()` of an ES module, which older Node versions don't support. CI tests Node 20, 22 and 24.
- **`init()` takes an optional options object, and concurrent first calls share one load.** Before, each of several simultaneous first calls instantiated the module; a load that fails is now forgotten, so it can be retried.
- **The published WebAssembly is built with Emscripten 6.0.12** (was 4.0.10), the version the benchmarks use. Output is identical. Speed is the same as 2.0 to within run-to-run variation: run side by side with the published 2.0.0 in `bench/COMPARISON.md`, palettes and `quantize` take 1.01× as long on the Kodak photos and 1.02× on the synthetic images (an earlier interleaved measurement found 0 to 6% longer), though clustering now records more per merge (hence the 2.3 times larger clustering). The module grows from 75 KB to 88 KB, from indexed output, cancellable clustering and the larger format.

### Fixed
- **A wide-gamut `ImageData` lost its colour space.** `quantize*` on an `ImageData` in `display-p3` returned one labelled `srgb`, from both entries and from worker handles, so drawing it on a wide-gamut canvas shifted the colours. The result keeps the input's `colorSpace`.
- **TypeScript results narrow.** `IndexedImage` is a union on `indexBits` (checking it narrows `indices` to the right array type), `precision` in `ClusteringInfo` is never null, and the palette parameters of `quantizeWithPalette` and `quantizeToIndicesWithPalette` accept a `Uint8ClampedArray` or a plain number array as the runtime always did (`PaletteLike`).
- **Documentation: index 0 is not always the heaviest colour.** The 2.x docs said index 0 is the dominant colour. That holds at two colours; at larger sizes index 0 keeps its place as the palette grows (each split keeps the heavier half in the parent's slot and appends the lighter), but a heavier colour can sit elsewhere (in a check of 24 images, 12 Kodak photos and 12 synthetic, index 0 was the heaviest entry in half of them at 8 colours, in 5 at 64 and in none at 256). The palettes did not change, and 3.0's are byte-identical to 2.0's. If you need heaviest first, sort the palette with the weights from `getSwatches` (see "Converting the output" in the guides); that gives up the stable order across sizes.
- **Inputs that were accepted but misread are now rejected.** An `options` argument that wasn't an ordinary object (a `Map`, `Date`, `ArrayBuffer`, typed array) had no own keys, so it passed as `{}` and its settings were silently ignored. A `RawImage` `width` or `height` of `1.5`, `-3` or `'x'`, or a width and height that didn't match the data, was accepted and copied into the result. Both now throw `invalid-argument`.
- **A plain-array palette was never checked beyond its length.** An array of three `[r, g, b]` colours (the shape gifenc and fast-png use) has length 3, passed, and became an all-black palette without an error; strings were coerced and out-of-range values wrapped (300 became 44). Plain arrays must now be integers from 0 to 255, or they are rejected with `invalid-argument`.
- **A worker that failed left every later call hanging.** If the worker could not start (a blocked or missing worker script, a strict CSP, a misconfigured bundler) or crashed, the calls waiting on it were rejected with `worker-failed`, but later calls were posted to a thread that would never answer. A failed worker is now dropped: later calls start a fresh one, and either work or fail the same clear way. A start that fails is no longer cached, and a cancelled `cluster()` releases whatever the worker kept for it. The shared `init` export also ignored its options; it now passes them on.
- **The worker entry hung on Bun.** Inside a Bun worker thread both Node's `parentPort` and the browser's `self.postMessage` exist, and the thread script listened on `self` while the parent wrote through `parentPort`, so no call ever completed. The thread now picks its channel the way the parent does (Node-style where Node's APIs exist). Deno and Bun are checked by hand.
- **Bundling with webpack 5 failed.** The Emscripten glue's Node-only `import("node:module")` stopped webpack with `UnhandledSchemeError` for a browser target (and made Vite warn that the module was externalized). esbuild, and so Wrangler for Cloudflare Workers, failed the same way on it and on the worker entry's `node:worker_threads` import. Those imports now build their specifier at run time, which no bundler tries to resolve (`scripts/patch-glue.mjs` does it for the Emscripten glue, and fails the build if the glue changes shape), and CI bundles the test app with Vite and webpack and the entries with esbuild. Checked by hand in Parcel 2 and in Miniflare (workerd).
- A `Uint8ClampedArray` that is a view into part of a larger buffer (such as a `subarray`) was read from the start of the whole buffer, so `RawImage` data given that way was clustered and quantized from the wrong bytes. Only the view's own bytes are read now.
- Image data whose length isn't a whole number of pixels (a multiple of 4 for RGBA, 3 for RGB) was silently truncated, giving a shorter output. It is now rejected with `Invalid image data`.
- `quantizeWithPalette` checks its palette: anything other than a `Uint8Array`, `Uint8ClampedArray` or array, or a length that isn't a multiple of 3, is rejected with `Invalid palette` instead of being truncated or failing with an unrelated error. An empty palette is accepted only for an image with no visible pixels (what `getPalette` gives for one); mapping visible pixels to it, which turned them all black, is an error.
- A palette size of 2^31 or more returned an empty palette without an error. It now means all colours, like any `k` above the number of colours.
- The README gave 2.0's WebAssembly module size as 65 KB; it was 75 KB.

## 2.0.0

The same functions and defaults (`rgb`, no dithering, `precision: 8`), with these changes. See [Migrating](docs/migrating.md).

### Performance
- **Faster clustering, with identical output.** On the Kodak photos (WASM, Node 22), one palette takes about 100 ms instead of 155 ms, and with `colorSpace: 'oklab'` about 110 ms instead of 250 ms, so OKLab now costs no more than RGB. `precision: 6` takes about 30 ms. The partner search's grid comes in sizes between powers of two with coarser cells, steps over empty cells with per-column occupancy bits, tests cells with a division-free float bound, and starts each search from a known partner.
- **Faster pixel mapping, with identical output.** For palettes up to 256 colours, lookups go through a grid whose cells (built on first use) list the palette entries that can be nearest there, instead of the KD-tree, and dithering in OKLab memoises colour conversions. `quantizeWithPalette` at 64 colours takes about 6 ms per photo instead of 15 ms; a dithered `quantize` about 150 ms instead of 250–325 ms.
- Every clustering, palette and quantized image is byte-identical to before.
- The WebAssembly module grows from 58 KB to 65 KB.

### Changed
- **Palettes come in split order.** Index 0 is the dominant colour, and the palette for `k + 1` is the palette for `k` with one entry refined (the heavier half of a split keeps its parent's place) and the lighter half appended. For opaque images the colours are exactly those of 1.2, in this order.
- **Alpha weighting, `alpha: 'weight'` (the new default).** RGBA pixels count in proportion to their opacity: fully transparent pixels are ignored and semi-transparent ones count partially. Opaque images, and images whose pixels are all fully opaque or fully transparent, use exact pixel counts. `alpha: 'ignore'` restores the 1.x behaviour.
- **Clusterings carry a 4-byte header:** a magic byte, the format version, the colour space and the precision. Merge records list the heavier child first. 1.x clusterings still load: they are 0 or 3 bytes more than a multiple of 9, where 2.0's are 4 or 7.
- **`quantizeWithClustering` matches in the clustering's colour space** by default. An explicit `colorSpace` overrides it.
- **Pixel mapping breaks exact ties by the smaller packed RGB value,** so results don't depend on palette order. Mapping is a few percent slower as a result.
- **Invalid clusterings** now throw `Invalid clustering` instead of giving an empty palette.
- An empty or fully transparent image gives a clustering of just the header.

## 1.2.0

**Palettes differ from 1.1.x.** Clusters are now merged by Ward's method, so results change for practically every image even with default options; see Changed. The new options are all off by default.

### Added
- **`colorSpace: 'oklab'`**: clusters and matches colours in OKLab, where distance tracks perceived difference. It gives lower ΔE2000 from about 128 colours up and on smooth gradients, but lower PSNR. The clustering format is unchanged.
- **`precision` (1–8 bits per channel)**: groups colours that share their top bits before clustering, at their mean colour. `6` is about 3× faster on photos at practically the same quality.
- **`dither`** (`true` or a strength from 0 to 1) on `quantize`, `quantizeWithClustering` and `quantizeWithPalette`: serpentine Floyd–Steinberg error diffusion. It needs the image width, from `ImageData`, `RawImage.width` or the `width` option. Fully transparent pixels are left undithered.
- Every function that takes an image accepts these as an optional trailing `options` object. Unknown option names are rejected.
- `RawImage` accepts optional `width` and `height`, which are copied to `quantize*` results.
- `npm run demo`: an interactive page that clusters once and re-cuts on a palette-size slider.

### Changed
- **Clusters merge by Ward's method.** Each merge joins the two clusters whose merge adds the least squared error, `n_a·n_b/(n_a+n_b)·‖a−b‖²`, instead of the two nearest centroids, and the hierarchy is built exactly with a nearest-neighbour chain. Palettes are more accurate (see `bench/COMPARISON.md`) but differ from 1.1.x. Code that compares stored palettes or clusterings with 1.1.x output will see changes. Clusterings saved by 1.1.x still load, since the format is unchanged.
- **Faster partner search.** A spatial grid with SIMD Ward costs, pruning by each cell's colour box and a float pre-filter make the Ward search interactive: about 150–200 ms for a 768×512 photo.
- **Faster histogram and mapping.** The colour histogram is an open-addressing table, and pixel mapping memoises recent colours.
- The WebAssembly module grows from 41 KB to 55 KB.

### Fixed
- An image with no pixels aborted the WebAssembly module and left it unusable for the rest of the process. It now gives an empty clustering and palette.
