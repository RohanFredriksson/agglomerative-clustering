# Exploratory round for the decoding brief (2026-11-23)

Fresh agents, each building one project against the published 3.4.2 from the README and `docs/` only (not `src/`, the ROADMAP or PRINCIPLES), asked about a built-in decoder only at the end.

## 1. Node CLI: dominant colours of a folder of phone and camera photos

- **Chose sharp**, because the README's first Node example uses it. From `npm install` to correct output on all 8 files (EXIF-6 JPEG, grey, palette and 16-bit PNG, half-transparent PNG, two-frame GIF, WebP, CMYK JPEG): about 70 seconds; the README snippet worked first time. 10 lines of glue (`sharp(path).rotate().toColourspace('srgb').ensureAlpha().raw().toBuffer({ resolveWithObject: true })`).
- **First instinct was `readFile()` bytes;** the `invalid-argument` message "told me exactly what to do".
- **Pitfalls:** without `ensureAlpha()` sharp gives 3 channels and a bare buffer gives "silent garbage" with no error ("That's the one that would have bitten me"); `toColourspace('rgb16').raw()` reports `uchar` and gives bytes clamped to 255 (a palette of white and black, no error; sharp's fault, the library can't tell); an animated GIF gives only its first frame silently (`pages: -1` stacks them; "a policy choice"); CMYK colours differ from ImageMagick's (profiles); orientation doesn't matter for palettes, would for `quantize`.
- **Search words:** "sharp raw buffer palette wrong colors grayscale png", "agglomerative-clustering palette garbage rgb", "sharp rgb16 raw all white".
- **On a built-in:** "for me it would matter little. The README hands you a working sharp one-liner, and the error message gets you there in under a minute." Would expect JPEG/PNG/GIF/WebP, orientation, 16-bit, grey and palette PNGs, ICC/CMYK; "That's basically sharp's job, and a half-done version (no CMYK, no profiles) would be worse than none: wrong colours with no error." sharp as an optional peer "would bother me a little" (native installs fail in CI and on Alpine); bundled decoders "would bother me more". Wanted instead: a runtime check against the silent-garbage cases. **"If it never shipped, would you mind?" No.**

## 2. Edge API: `GET /colors?url=` and `POST /colors` on Cloudflare Workers (wrangler dev / workerd)

- **Chose fast-png and jpeg-js** (pure JS; environments.md names fast-png for Workers). Rejected sharp and canvas (native), pngjs (Node streams and Buffer), Cloudflare Images (paid). Tried @jsquash/jpeg: 12 MP in about 200 ms in workerd against about 1100 ms for jpeg-js, for 166 KB of WebAssembly. **GIF, WebP and AVIF rejected with a 415.** First correct output about 15 minutes after reading the docs; testing grey variants found a bug, 10 minutes more.
- **Glue: 81 lines** (`edge-decode-glue.js`, copied from the agent's project), about 55 of them bytes to pixels, the rest a downscale.
- **Pitfalls:** 1-, 2- and 4-bit grey PNGs stay bit-packed in fast-png, so a black-and-white image came out "#000000 98%" with no error ("the API looked fine and was wrong"); palette, grey+alpha and 16-bit PNGs each need their own handling; jpeg-js RGB passed bare gives a garbage palette with no error (avoided because the README warns); the library's "decode it first … use sharp, pngjs" advice "doesn't fit here".
- **CPU** (Node `process.cpuUsage`, same code): 768×512 PNG decode 31–35 ms, cluster 29–35 ms; 12 MP JPEG decode (jpeg-js) 1.1–1.5 s, downscale 90 ms, cluster 45 ms. "Decoding, not clustering, is the cost." **Memory:** jpeg-js needs about 92 MB for the 12 MP JPEG, plus 36 MB output, near the 128 MB isolate limit (not enforced locally).
- **Bundle** (esbuild, minified / gzipped): fast-png 23.6 / 7.6 KB, jpeg-js 21.1 / 8.8 KB, mozjpeg 19 KB JS + 166 KB WebAssembly (63 KB gzipped); the library's own WebAssembly 96 / 45 KB.
- **Search words:** "decode PNG JPEG to RGBA in Cloudflare Worker without sharp", "fast-png 1 bit grayscale wrong colors", "jpeg-js too slow Cloudflare Worker CPU limit 12 megapixel".
- **On a built-in:** "that would matter a lot. The colour maths was 5 lines. Everything else was format plumbing I'll get subtly wrong (the 1-bit bug)." Would expect JPEG (baseline, progressive, CMYK), PNG at every depth, GIF first frame, WebP, AVIF nice-to-have, **decoding at reduced size** (JPEG DCT scaling, for CPU and memory) and a pixel cap read from the header. Orientation not needed for palettes. Acceptable: 150–250 KB of WebAssembly (60–100 KB gzipped), "ideally as a separate entry point so image-in-hand users don't pay for it". **"If it never shipped, would I mind?" Yes, moderately.** "every user on the edge rewrites these 80 lines and hits the same bugs."

## 3. Browser: a Vite app that takes a dropped file or URL, palette and preview in the worker entry (headless Chromium 1255)

- **Decoded with** `createImageBitmap(blob, { imageOrientation: 'from-image', premultiplyAlpha: 'none', colorSpaceConversion: 'default' })`, an `OffscreenCanvas` and `getImageData`, on the main thread, then `createWorker({ transfer: true }).cluster(...)`. A decode worker of its own would have meant passing pixels between two workers: "I wanted the library's worker to just take the Blob." First correct output in about 15 minutes; **34 lines** of glue (`browser-decode-glue.js`), most of it error messages (CORS, HEIC, size cap).
- **Orientation and profiles:** right (an orientation-6 JPEG gave exactly the upright palette). WebCodecs `ImageDecoder` does not rotate.
- **Premultiplied drift:** partly transparent pixels come back changed, orange (200,100,50) at alpha 3 as (170,85,85) ("That's not a colour in my image"), one green on an alpha ramp as 8 colours; `premultiplyAlpha: 'none'` doesn't help once drawn to a canvas, nor does `ImageDecoder`.
- **Main thread:** a 12 MP JPEG took 117–228 ms to decode against 343–470 ms of clustering in the worker; the page's long tasks (59, 69, 168 ms) were all decoding.
- **CORS** failures give only "TypeError: Failed to fetch"; **HEIC** isn't decodable in Chromium and `createImageBitmap` throws a generic error.
- **Search words:** "getImageData semi transparent pixels wrong color", "createImageBitmap premultiplyAlpha none still premultiplied", "decode HEIC in browser Chrome".
- **On a built-in:** "I'd use it immediately", if it decoded in the worker; expects File/Blob/ArrayBuffer/Response, orientation, profiles, exact straight alpha, a pixel cap before decoding, a coded error naming HEIC. Wants the browser's own decoders: "A few KB is fine; hundreds of KB of codecs would bother me more than the 34 lines did." **Would it mind if it never shipped? "Mildly. Orientation and formats are solved by the browser in one call."** What it would miss is alpha-exact decoding and decoding off the main thread; "A docs recipe showing `createImageBitmap` inside a worker would cover most of it."
