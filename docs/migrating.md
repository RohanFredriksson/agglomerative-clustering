# Migrating

Upgrading from an earlier major version, and replacing names deprecated along the way. The full list of changes in every release is in the [CHANGELOG](../CHANGELOG.md).

## From 3.x to 4.0

4.0 was built in two parts, and both are in: premultiplied input, an image object that rejects keys it doesn't know, and result types that keep the input's (part 1); the removal of the deprecated names, and errors where 3.x warned or ignored a mistake (part 2). The removed names are in [Removed names](#removed-names-34-and-38-deprecations) below. Output for every input that still works is unchanged: palettes, weights and mapped images are the same as 3.8's. What can affect any code, whatever it passes: a bare `Uint8Array` that looks like RGB or grey, `transparent` on a format with no alpha, the removed names, a worker script from another version, and Node 22.12+. The type items (a reused variable, `interface X extends RawImage`, the `data` type) and the unknown-key and `premultiplied` items are costs for code that passes `{ data, format }` objects.

- **A variable reused across calls with different inputs stops compiling.** A result now has the input's exact type, so `let image = { data, format: 'rgba' as const }` can't be assigned an object with `format: 'bgra'`, or one with `width` after one without. Annotate it as `RawImage`:

  ```ts
  import type { RawImage } from 'agglomerative-clustering';
  let image: RawImage = { data: a, format: 'rgba' };
  image = { data: b, format: 'bgra', width, height };
  ```

  A result variable reused across formats needs the same: annotate it as `ImageResult<RawImage>` (exported from the package too), as in `let result: ImageResult<RawImage> = await quantize(rgbImage, 16); result = await quantize(rgbaImage, 16);`.

- **`interface X extends RawImage` doesn't compile**, because `RawImage` is now a union split by `format` and an interface can't extend a union. Use a type: `type X = RawImage<'rgba'>` (or `RawImage<'rgba'> & { name: string }` to keep extra keys of your own). Note that a result type keeps only the image's own keys, so an extra key of yours isn't on the result.
- **A result's `data` is typed `Uint8Array`**, where 3.x typed it `Uint8Array | Uint8ClampedArray`. It always was one at run time, so code that handled the clamped case can drop it, and the casts to `Uint8Array` the 3.x docs showed can go. To build an `ImageData` from a result, `new Uint8ClampedArray(result.data.buffer, result.data.byteOffset, result.data.length)` shares the bytes.
- **Objects with other keys now throw.** An image object may have only `data`, `format`, `width`, `height` and `premultiplied`; another key is `invalid-argument` on `'image'`. The usual break is spreading a decoder's result, which carries `channels`, `size`, `depth` and more: build the object from what you need, `{ data, format: 'rgba', width: info.width, height: info.height }`. TypeScript doesn't catch this one: `{ ...info, data }` isn't a fresh object literal, so extra keys aren't checked and it compiles, then fails at run time with the unknown-key error on the first call. Search your code for spreads into image objects.
- **`premultiplied: true` used to be ignored.** In 3.x code that set it, hoping it worked, got darkened edges and no error. In 4.0 it does the conversion: palettes are of the real colours and mapped output is premultiplied again (a `nativeImage` round trip is in [Electron](environments.md#electron): `toBitmap()`, `premultiplied: true`, `createFromBitmap`), so output that went to an `ImageData` or an encoder now needs the guides' [straight-output recipe](guides.md#straight-pixels-from-a-premultiplied-source). It is for `'rgba'` and `'bgra'` only, and an error on the other formats; a value other than `true` or `false` is an error too (3.x ignored it). If you converted premultiplied pixels yourself (the loops the 3.x docs showed), delete them and set the flag instead, or keep them and leave the flag off.
- **A bare `Uint8Array` that looks like RGB or grey is an error.** 3.5 and 3.6 warned (`rgb-as-rgba`, `gray-as-rgba`); 4.0 throws `invalid-argument` on `'image'`, on every call, with the same text in the worker entry. Fix the call the way the message says: RGB bytes (sharp's plain `.raw()`) go as `{ data, format: 'rgb', width }` or after `.ensureAlpha()`; grey (fast-png's `decode()` of a grey PNG, or a palette PNG's indices) is expanded to RGBA first, since there is no grey format; and bytes that really are RGBA go as `{ data, format: 'rgba' }`, which is never inspected. The check recognises RGB and grey from how the bytes look, so it can miss flat or graphic grey and some one-channel images: always pass grey expanded to RGBA. A 3.x run with `node --trace-warnings` shows the calls that warned. The rules are the ones the last 3.x release used. `process.on('warning')` handlers for these codes can go.
- **`transparent: true` (or a cutoff) on an image with no alpha throws.** In 3.x it did nothing for `'rgb'`, `'rgbx'` and `'bgrx'`; 4.0 throws `invalid-argument` on `'options.transparent'`, since no pixel of such an image can be transparent (and for a bitmap whose fourth byte is really alpha, `'rgba'` or `'bgra'` is the format). Leave `transparent` out for those images, or pass `false`. A shared options object like `{ transparent: false, alpha: 'ignore' }` still works with every format, and mapping an `'rgb'` image with a clustering made with `transparent` is unchanged.
- **Node 22.12 or newer.** `engines` is now `>=22.12.0` (Node 20 reached end of life on 2026-04-30; 22.12 is the first 22 with `require()` of ES modules, which the CommonJS build needs). Node 20 users stay on 3.8, which is patched on request.

## Removed names (3.4 and 3.8 deprecations)

4.0 removes the names 3.4 and 3.8 deprecated, in both entries and on workers. They were deprecated in the types only, with no warning at run time. A removed name fails as soon as it is imported: Node's ES module loader stops with "does not provide an export named '…'" (a bundler says the same in its own words), and TypeScript reports the import. Under CommonJS, or as a method of a worker (`worker.getPalette(…)`), it is `undefined` instead, so the failure is `undefined is not a function` when it is called. Search your code for each name in the first column.

| Removed | 4.0 form |
|---|---|
| `getClustering(image, options?)` | `buildClustering(image, options?)` |
| `getPalette(image, k, options?)` | `buildPalette(image, k, options?)` |
| `getSwatches(image, k, options?)` | `buildSwatches(image, k, options?)` |
| `getPaletteFromClustering(c, k)` | `c.getPalette(k)`; off the thread, `(await worker.load(c)).getPalette(k)` |
| `getSwatchesFromClustering(c, k)` | `c.getSwatches(k)`; off the thread, `….getSwatches(k)` |
| `getClusteringInfo(c)` (the function) | `c.getClusteringInfo()`; off the thread, `….getClusteringInfo()` |
| `quantizeFromClustering(image, c, k, options?)` | `c.quantize(image, k, options?)`; off the thread, `….quantize(image, k, options?)` |
| `quantizeToIndicesFromClustering(image, c, k, options?)` | `c.quantizeToIndices(image, k, options?)`; off the thread, `….quantizeToIndices(image, k, options?)` |

- **The first three are renames:** same arguments, options, results and errors. Replace whole names at calls that take an image first (`getPalette(image, …)`, `worker.getPalette(image, …)`, imports and mock factories). A plain-text replace would also rename names that stay (`clustering.getPalette(k)`, `handle.getClustering()`, `handle.getSwatches(k)`), which plain JavaScript only finds at run time.
- **The five that took a clustering are now methods.** `clustering.getPalette(k)` and the rest give the same results, defaults and errors, but the clustering is the receiver, so it is checked first, and the image still comes first in the mapping methods (`c.quantize(image, k)`). A clustering read from storage has no methods until `new Clustering(bytes)`.
- **A one-off call in a worker** (`await worker.getPaletteFromClustering(c, k)`) becomes `await using loaded = await worker.load(c)` and a call on `loaded`. Here `worker` is one made by `createWorker()`: `load` is a method of such a worker (like `cluster`), not an export of `agglomerative-clustering/worker`, which has no function form of it (so `import { load } from 'agglomerative-clustering/worker'` fails). Make the worker once and keep it (see [the worker entry](api.md#worker-entry)): one copy of the clustering is sent, and you can cut it as often as you like. A loaded handle has no `…WithPalette` methods and no `getClustering()` (it holds no image, and you already have the clustering); to map with a palette use `worker.quantizeWithPalette(image, palette)` (see [the worker entry](api.md#worker-entry)).
- **Mocks and spies:** a mock of the module's `getPaletteFromClustering` doesn't see `clustering.getPalette(k)`; spy on the method of a real clustering instead. A `vi.mock` factory that lists `getPalette` needs `buildPalette` now.
- **A class that implements `AgglomerativeWorker`** (a typed fake, or a wrapper) drops `getClustering`, `getPalette`, `getSwatches` and the five `…FromClustering` methods, which the interface no longer lists. A fake that types itself as `Pick<AgglomerativeWorker, 'buildPalette' | 'cluster'>` is spared this.
- **`getClusteringInfo` as a function is gone, the method stays.** `clustering.getClusteringInfo()` and a handle's `getClusteringInfo()` are unchanged.
- **A worker script from another version (`createWorker({ script })`, `init({ script })`).** The first message the worker entry sends to a worker asks which version its script is. A `worker-thread.mjs` from 3.x (or any version other than this one, including a stale copy a bundler made) answers differently, and every call on that worker rejects with `worker-failed` ("The worker script is from another version of agglomerative-clustering (…)"). The message ends "Serve all of the package's dist/ files from this version": copy all of `dist/` of this version, not just `worker-thread.mjs`. Workers that start the package's own script are unaffected.

## From 2.x to 3.0

The code in this section uses the names of 3.0 to 3.3. From 3.4, write `buildClustering`, `buildPalette` and `buildSwatches` for them (see above).

3.0 keeps every function and default except one rename, and palettes and quantized images are byte-identical to 2.0. What changes:

- **`quantizeWithClustering` is now `quantizeFromClustering`.** The same arguments and behaviour; find and replace the name. It makes one word mean "the colours come from a clustering" (see "How it works" in the [README](../README.md#how-it-works)).

- **Clustering format.** `getClustering` writes format version 3, which records weights and merge costs: 21 bytes per distinct colour instead of 9, so clusterings are about 2.3 times larger. Clusterings saved by 2.x still load; the palette and mapping functions read them, but `getSwatchesFromClustering` and `getClusteringInfo` need a 3.x clustering (2.x recorded no weights) and reject a 2.x one with `unsupported-version`. **Clusterings saved by 1.x are no longer read.** They had no header and could only be recognised by their length, which many other byte strings share, so a palette passed in place of a clustering was accepted and returned nonsense. Cluster the image again (the README has always suggested storing the clustering next to the image). **2.x cannot read 3.x clusterings** (it rejects them as invalid), so if clusterings are stored where an older version of the package may still read them, upgrade the readers first. Code that read the header bytes itself (the colour space was `clustering[2]`) reads the wrong fields now: use `clustering.getClusteringInfo()` (the function form `getClusteringInfo(clustering)` in 3.0 to 3.7), which gives the colour space, precision and number of colours of a 3.x clustering. For a 2.x one, a palette cut from it carries its colour space (from 3.8, `(await clustering.getPalette(1)).colorSpace`; in 3.0 to 3.7, `(await getPaletteFromClustering(clustering, 1)).colorSpace`).
- **A palette made in OKLab maps in OKLab.** `getPalette` and the other functions now return a `Palette`, which remembers its colour space, and `quantizeWithPalette` / `quantizeToIndicesWithPalette` match in it unless you name another. In 2.x they matched in RGB, so `quantizeWithPalette(image, await getPalette(image, k, { colorSpace: 'oklab' }))` now gives a different (OKLab-matched) image. This is the only call whose output changes from 2.0 (checked by comparing 2.0.0 with 3.0 over 1,600 random cases); RGB palettes, plain bytes, `quantize` and `quantizeFromClustering` give byte-identical results. It applies to an OKLab palette however you got it, including one cut from a stored 2.x OKLab clustering with `getPaletteFromClustering` (which now maps as `quantizeFromClustering` always did). To get the 2.x result, pass `colorSpace: 'rgb'`.
- **If you store palettes, store their colour space too.** A palette read back from storage (JSON, a database, `slice`, `structuredClone`) is plain bytes, and plain bytes are matched in RGB. So in 3.0 an OKLab palette maps one way when it is fresh and another way when it comes from your cache (in 2.x both matched in RGB). Store `palette.colorSpace` with the bytes and restore with `new Palette(bytes, colorSpace)`, or pass `colorSpace` when you map.
- **TypeScript: clusterings are a `Clustering`.** `getClustering` returns one, and the functions that take a clustering are typed to want one, so bytes you stored and read back need `new Clustering(bytes)` (JavaScript still accepts plain bytes). Palettes come back as `Palette`, which is a `Uint8Array` as before.
- **Stricter input.** Image data that isn't a whole number of pixels, and palettes that aren't whole RGB triples, now throw instead of being truncated. A bare `Uint8Array` that is really the bytes of an image file (PNG, JPEG, …) is rejected instead of being read as pixels, and a `width` option that disagrees with the image's own width is an error.
- **Node 20.19+ or 22.12+.** The CommonJS build needs Node's `require()` of ES modules.
- **Package exports.** The package exports `.`, `./worker` and `./clustering.wasm` (and `./package.json`); deep imports into `dist/` aren't available (as in 2.x). TypeScript users get separate declarations for `import` and `require`.
- **In CommonJS, a missed rename fails late.** `require('agglomerative-clustering').quantizeWithClustering` is `undefined`, so the error is a plain "is not a function" when it is called. Search for the name rather than waiting for the error.
- **New, not breaking:** the worker entry, `signal` and `onProgress`, indexed output, swatches (weights and shares) and the error curve, the `Palette` and `Clustering` types, `version` and `formatVersion`, `transparent` for GIF and palette PNG output, `init({ wasm })`, and a `code` on every error.

## From 1.x to 2.0

2.0 keeps the same functions and defaults (`rgb`, no dithering, exact `precision`). What changes:

- **Palette order.** Palettes come in split order (index 0 is the dominant colour at two colours and keeps its place as the palette grows), rather than in an arbitrary order. For opaque images they contain exactly the same colours as 1.2.
- **Transparency.** RGBA pixels are weighted by opacity, so palettes of images with transparency change: fully transparent pixels no longer contribute. Pass `{ alpha: 'ignore' }` for the 1.x behaviour.
- **Clustering bytes.** Clusterings gain a 4-byte header recording their colour space and precision. Clusterings saved by 1.x load in 2.x but are no longer read in 3.x (cluster the image again). Anything that inspected the raw bytes needs to skip the header.
- **`quantizeFromClustering`** matches in the clustering's colour space unless you pass `colorSpace`.
- **Exact ties** in pixel mapping go to the colour with the smaller RGB value, so results don't depend on palette order. A small number of pixels that sit exactly between two palette colours may map differently from 1.2.
- **Invalid clusterings** passed to `getPaletteFromClustering` or `quantizeFromClustering` now throw instead of giving an empty palette.
