# Stability and versioning

Within a major version these don't change:
- the functions and the methods on `Clustering`, their options and defaults;
- the palettes, weights and mapped images you get for the same input and options, except where a release fixes a bug in them, which its changelog entry says (the golden tests pin them, and they are byte-identical from 2.0 to 3.0, with one exception: an OKLab `Palette` passed to `quantizeWithPalette` is now matched in OKLab, see [Migrating](migrating.md)). Don't rely on byte-identical output across releases, for example as a cache key: store the result instead;
- that copies of the package of the same version (its ES-module and CommonJS builds, or a duplicate in a bundle or in `node_modules`) recognise each other's palettes and clusterings and take them in each other's functions (see [Palette and Clustering](api.md#palette-and-clustering));
- that with `dither: 'ordered'` a pixel's result depends only on its own colour and its position modulo 8 from the image's top-left pixel, for a given palette and options ([Choosing a dither method](api.md#choosing-a-dither-method)), so images can be stacked or tiled on that grid; which colours it picks can change like any output;
- the ability to read every clustering an earlier release wrote (a 2.x clustering records no weights, so the functions that report them, `getSwatchesFromClustering` and `getClusteringInfo`, need a 3.x one). The format is versioned, and a minor release may add a format (raising `formatVersion`): from 3.0, a release that meets a clustering from a newer format rejects it with an `unsupported-version` error asking you to upgrade, rather than misreading it. (2.x predates that: it rejects a 3.x clustering as an invalid one, without a `code`.)

Releases may get faster, add functions (with their methods on `Clustering`; interfaces the library implements, `Clustering`, `AgglomerativeWorker` and `ClusteringHandle`, gain members when functions are added, so implement them yourself only in tests, and expect to add members), options, error codes, warnings, image formats and clustering formats. A warning is only for a call that the next major version will reject: it goes through `process.emitWarning` in Node and `console.warn` elsewhere, once per code, never changes a result, and is silenced by saying what the input is (`{ data, format }`). Which inputs trigger one may change in a minor release, only after measuring again for false alarms; results never do. An option may accept new values, or an object form, in a minor release, and the exported lists of names (`colorSpaces`, `imageFormats`, `ditherMethods` and the like) grow with it; the values it accepted before keep their meaning (in TypeScript its type widens, so code that reads an option's type and handles only today's values may need a new branch). Anything that would change what an existing call returns, other than a documented bug fix, waits for a new major version. Switch over error `code`s (and `ImageFormat`s) with a default branch, since new ones can appear in a minor release. (In TypeScript, an exhaustive `switch` that ends by assigning the code to `never` will stop compiling when one does, which is a way to hear about it; a default branch keeps compiling.) Anything slated for removal is first marked `@deprecated` in the types and keeps working for the rest of that major version.

The API is what the package's `exports` name (`agglomerative-clustering`, `agglomerative-clustering/worker`, `agglomerative-clustering/clustering.wasm`). The names of the other files in `dist/`, and which of them the worker script imports, can change in a minor release: when you copy files for a bundler that doesn't emit them, copy the whole `dist/` folder.
