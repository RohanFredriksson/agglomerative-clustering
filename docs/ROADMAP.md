# Roadmap

What is planned, what is only being considered, and what was decided against, with the reasons. Each release keeps output byte-identical unless it says otherwise; `test/golden.test.js` enforces that.

**The rule for what goes where.** 3.0 freezes the API: anything that would change the shape or defaults of an existing function was decided before it. Everything below only adds (a new option, a new value of an option, a new function), so it can come in any 3.x release without breaking anyone, except the "4.0" section, which collects what can't. Most items come from exploratory testing of the 3.0 betas: fresh agents building real projects from the npm package alone (Electron, a Chrome extension, Jest and Vitest suites, e-ink and embroidery tools, a static-site build, a wrapper package, CDNs, Deno, Bun, Cloudflare Workers, SvelteKit, Nuxt, Next.js, servers, animated GIFs).

## Clustering format versioning

The clustering is the only format users store, so it is the only one that needs versioning. Palettes are plain RGB bytes, and messages between the main thread and the worker never outlive one installed version of the package.

Since 2.0 every clustering starts with `[0xAC, version, …]`. Clusterings from 1.x had no header and were recognised only by their length (0 or 3 more than a multiple of 9, where 2.x lengths are 4 or 7 more). That was fragile in a way that mattered: many other byte strings, such as palettes of 1, 3, 4, 6, 7 or 9 colours, have those lengths and were accepted as clusterings, returning nonsense. 3.0 stopped reading 1.x clusterings, so a buffer is a clustering only if it carries the header. These rules hold:

1. **Readers decide by the version byte, never by shape.** Every version is identified by its header.
2. **Versions 2 and 3 pad the end with zero bytes** so the length is 4 (empty) or 7 more than a multiple of 9. The padding dates from when that kept them out of 1.x's lengths; it stays so existing bytes stay stable, and readers ignore it (it is shorter than a record).
3. **From v3 the header describes its own layout:** `[0xAC, version, header length, record length, colour space, precision, …]`. A reader finds the records from the stored lengths and ignores fields it doesn't know, so fields can be added at the end of the header or of each record without a new version. The version is bumped only when an existing field changes meaning.
4. **Readers reject versions newer than they know** with an error asking for an upgrade, and never guess. The same goes for a header field with a fixed set of meanings (the colour space, the weight unit) that holds a value they don't know: that is how a later release adds one, so it is `unsupported-version`, not "damaged".
5. **Every version from 2 on stays readable.** `fixtures/clusterings/` holds a stored clustering of each format version with the palettes (and from v3 the weights and mean squared errors) its release gave, and `test/formats.test.js` checks them. Each new version adds a fixture; existing ones are never regenerated.

## 3.0: worker, indexed output, weights and error curve (released as 3.0.0)

What was planned as 2.1 and 3.0 ships together as 3.0, since the clustering format changes anyway.

- [x] **Worker entry** `agglomerative-clustering/worker`: `createWorker()` with handles that keep an image and its clustering in the worker, and drop-in exports over one shared worker. Web Worker in browsers, `worker_threads` in Node.
- [x] **Indexed output:** `quantizeToIndices*`, with `transparent` (an alpha cutoff).
- [x] **Clustering format v3**, following the rules above. Records are 21 bytes: colours, the split's parent index, the lighter half's weight and the Ward cost. The parent index is needed because different clusters can share an 8-bit colour, which would otherwise make weights ambiguous.
- [x] **Swatches** (`getSwatches`, `getSwatchesFromClustering`: palette, weights and shares) and the **error curve** (`getClusteringInfo().mse`, and the unitless `explained`), for choosing a palette size by error.
- [x] **Cancellation and progress:** `signal` and `onProgress` on every function with an image; the clustering is a resumable job run in slices, and the worker stops working on a cancelled call.
- [x] **`init({ wasm })`** and the `clustering.wasm` export, for CDNs, strict CSPs and edge runtimes; one shared load.
- [x] **Error codes** on every error, kept across the worker boundary, with `errorCodes` and the `isCodedError` guard.
- [x] **Runs where people put it:** CDNs (cross-origin workers through a `blob:` module), Deno, Bun, Cloudflare Workers, Next.js server bundles, SvelteKit and Nuxt, Electron (packaged with asar), browser extensions, Jest's CommonJS mode, jsdom; `createWorker({ script })` for bundlers that don't emit the worker script (Angular, esbuild, Rollup).
- [x] **Tests as a consumer sees the package:** a Vite build run in headless Chromium (worker, `.wasm`, slices, aborts, `wasm` locations), strict TypeScript against the built declarations, and the full suite on Node 20, 22 and 24, in CI.

## Next: one minor release each, in this order

Each item ships as its own minor release when it is ready, rather than waiting for the others. All eleven are done (3, 6 and 7 as recipes).

1. [x] **Dither methods (released as 3.1.0).** `dither` now also takes `'atkinson'`, `'ordered'` and `{ method, strength, steps }`, the first option with an object form (see "Option shapes" in docs/api.md). Error diffusion makes each frame's pattern depend on every pixel before it, so an animated GIF's dither crawls from frame to frame even where the picture is still; ordered dithering is fixed to the pixel grid, so still areas stay still. Asked for by the hardware-palette round; the animated-GIF round showed the flicker.
   - **How ordered works:** pattern dithering after Knoll. Each distinct colour gets a recipe of `steps` palette colours (default 64 for two colours, else 16), built by repeatedly picking the colour nearest the target plus the error carried so far, sorted dark to light and laid out by an 8×8 Bayer matrix.
   - **Quality** (six Kodak photos, mean ΔE2000 after a σ 1.5 blur): at 16 colours Floyd–Steinberg 2.55, ordered 2.72, Atkinson 3.09, none 3.72; with seven e-ink inks 2.91, 8.2, 6.7 and 21.6 (in sRGB values; see below). The textbook threshold method (offset each pixel by the matrix, then take the nearest colour) was tried in a spike and dropped: 3.67 at 16 colours and 12.9 on e-ink, since one offset size can't suit an uneven palette.
   - **The roadmap used to say ordered suits e-ink.** For accuracy it doesn't: ordered is for animation and displays that need a fixed pattern. And every method mixes sRGB values, which the eye doesn't: with a few widely spaced inks, dithered photos look much lighter on the panel (blurred in light, ΔE 17–22 on the seven inks for every method). Converting to linear light first cut that to 5–7 with Floyd–Steinberg, and weighting brightness first cut it to about 4 (docs/api.md has the recipe, `ditherInLight`).
   - **Capping a recipe's carried error** (as Floyd–Steinberg caps what it passes on) was tried and dropped: it made e-ink much worse (8.2 to 14.7) for little speed.
   - **Speed** (768×512, 16 colours): 66 ms at 16 steps against 27 ms for Floyd–Steinberg, after an exact four-wide search for recipe steps (it was 89 ms). Possible later settings, each additive: other patterns (blue noise), matrix sizes, a serpentine toggle. A new pattern must keep a pixel's result depending only on its colour and position (the 3.x promise in docs/stability.md that the batching recipe for animations rests on) and state its own period; `'ordered'` itself keeps the 8×8 pattern.
   - **Changed after an exploratory round on the release candidate** (an animated-GIF maker, and e-ink, 1-bit and sprite tools): `mix` became `steps` (both testers read "16 palette colours" where it means 16 pattern cells, so two colours blend in 17 shades); the default became 64 steps for two colours (16 bands visibly on a black-and-white gradient; 64 costs 4.6× the time but changed nothing measurable on photos at 3–4 colours, so the rest keep 16); ordered's strength now goes through a table per step count, since taken as it was, 0.5 looked like 1 (a single 2.5 power fitted 16 steps but left 64 steps changing 70% of the pixels by 0.25 and 16 steps doing nothing at 0.05; ordered's response to the raw amount is smooth but very steep, a third of the full change at 0.01 with 64 steps, so the table inverts the measured response at 0.05, 0.1, 0.25, 0.5 and 0.75 to follow Floyd–Steinberg's, interpolating geometrically, and on photos it wasn't fitted on every step count stays within a few points of Floyd–Steinberg's response); the recipe table is sized to the image (a 1×1 call took 217 µs, now 16 µs); and errors echo the value and point misplaced settings at `dither: { … }`. A second round (a Vite app with live controls, the docs' recipes run as written, and a fuzz of the option in both entries) found a 3.0 bug, cancelled worker calls queued behind a mapping call still running (fixed), the worker entry not reading the `dither` object as the main entry does (fixed), the animated-GIF recipe giving frames with and without transparency different colours (fixed by cutting 255 colours once), and how slow ordered dithering gets on images of nearly all different colours (documented; since 3.7.0 `signal` and `onProgress` take effect while mapping, item 11).

The spike (`bench/spikes/fixed-subset.js`, write-up in `fixed-subset.md`, pictures from `fixed-subset-visual.js`) compared four methods on the 24 Kodak photos and synthetic images, with synthetic charts of 26 to 1000 colours, scoring the mapped image by PSNR and CIEDE2000.

[x] **Methods on `Clustering` (released as 3.3.0).** `clustering.getPalette(k)`, `getSwatches(k)`, `getClusteringInfo()`, `quantize(image, k, options?)` and `quantizeToIndices(image, k, options?)`, so "cluster once, cut anywhere" reads without the `…FromClustering` suffixes. From the naming review before 3.0.0, not a user request; spec in `docs/superpowers/specs/2026-11-21-clustering-methods-design.md`.
   - **The shape:** each method is its function form with the clustering as the receiver, named by dropping `FromClustering` (so `getClusteringInfo`, not the `getInfo` first sketched here, matching the handle), with the same results, defaults and errors. `quantizeToIndices` was added to the four first planned. [x] **Warning on RGB bytes passed bare (released as 3.5.0).** A bare `Uint8Array` is read as RGBA, so RGB from a decoder (sharp's plain `.raw()`) gave a worse palette with no error whenever its length divides by 4: the commonest silent wrong output in the decoding brief's rounds (11 of 13 test files). 3.5.0 warns once (`rgb-as-rgba`, through `process.emitWarning` or `console.warn`) and changes no result; 4.0 makes it an error (below). The library's first warning; the convention for warnings is in PRINCIPLES "Settled decisions".
   - **The check** (value brief `docs/superpowers/briefs/2026-11-23-bare-rgb-brief.md`, measurements in `bench/spikes/bare-rgb/`): real RGBA changes least between a byte and the one 4 before it, RGB between a byte and the one 3 before; grey RGB is caught by its equal byte triples. It samples 512 windows, so it costs about 0.25 ms at any size on RGBA (about 0.4 ms the one time it flags). On 2,103 real RGBA images (emoji, cutouts, alpha ramps, dithered, pixel art, premultiplied) it warned on none; it caught 1,833 of 1,884 harmful RGB cases, every one at 64×64 and above but two, and 12 of 12 in the decoding round.

[x] **Warning on grey bytes passed bare (released as 3.6.0).** fast-png's `decode()` gives grey PNGs as 1 byte per pixel and grey + alpha as 2 (and 1-, 2- and 4-bit rows still packed), which a bare `Uint8Array` reads as RGBA: the palette mapped 274–1,980 times worse on opaque grey + alpha photos and 1.4–5 times on grey photos. 3.6.0 warns once (`gray-as-rgba`, one code for both layouts, the layout named in the message), and 4.0 makes it an error (below). No person asked: the one case was the decoding round's edge agent, whose fast-png 1-bit PNG came out "#000000 98%". Value brief `docs/superpowers/briefs/2026-11-23-bare-grey-brief.md`, spec `docs/superpowers/specs/2026-11-23-bare-grey-warning-design.md`, measurements in `bench/spikes/bare-grey/`.
   - **The rules** (after the RGB rule, which decides first): grey + alpha is smooth at a step of 2 and rough at a step of 1; grey is smoothest at a step of 1, unless most changing pixels have four equal bytes (real RGBA such as grey with alpha = grey). Measured with the shipped check (`results-shipped.txt`): on the 2,984 real RGBA images it warned on none; at 64×64 and above it caught 953 of 955 harmful grey + alpha cases, and of 911 harmful grey arrays it warned on 806 (198 as `gray-as-rgba`, 608 as `rgb-as-rgba`), and on fast-png's packed rows of 17, 18 and 17 of 24 photos at 1, 2 and 4 bits (`results-packed.txt`). It misses grey photos dithered to a few levels and grey in runs of four equal bytes, and gives 4 dithered grey arrays the grey-and-alpha wording (the fix is the same).
   - **The RGB check first,** chosen over a classifier that picks the smoothest step, which called 34 of 1,690 RGB images at 64×64 and above grey (`results-rules.txt`); with the RGB check first, none of 1,714 (`results-shipped.txt`). The 611 of 1,029 harmful grey arrays that `rgb-as-rgba` already caught keep that code, and its text now covers grey: it had told them to pass `format: 'rgb'`, which misreads them too.
   - **Found while building:** the sampling windows were evenly spaced, one row apart at 768×512 RGBA, so every one saw only the left edge, and an image with a flat left margin went unflagged: 3.5.0 caught 6 of 24 RGB cutouts on black (`results-margins.txt`). The check costs about 0.35 ms a call (`results-cost.txt`).

A palette PNG comes back as `channels: 1, depth: 8` plus a `palette` (`results-palette.txt`), so an expander that ignored it turned indices into grey; the cold-read review found that.

## 4.0: breaking changes, collected

Changes that would break code written against 3.x wait here for the next major version, so 3.x stays additive and 4.0 breaks once.

- **Premultiplied alpha** (`{ data, format, premultiplied: true }`, for RGBA and BGRA): Electron's `nativeImage.toBitmap()` is premultiplied (Skia `MakeN32Premul`, in `shell/common/api/electron_api_native_image.cc`), as are GDI's `AlphaBlend` bitmaps, WIC's `32bppPBGRA` and WebGL `readPixels` by default. Pixels would be un-premultiplied on read (`min(255, round(c·255/a))`, alpha 0 as black) and `quantize*` output (and the `Clustering` methods') premultiplied again (`round(c·a/255)`); palettes and clusterings stay straight. Why not in 3.x (decided while designing 3.2.0):
  - **Reading the field changes existing calls.** Image objects carry other fields today, and one that already says `premultiplied: true` is ignored; from that release its output would change, and a non-boolean one would start throwing.
  - **Typing it well is breaking.** Making `{ format: 'rgb', premultiplied: true }` a compile error needs `RawImage` to be a union split by `format`, which breaks `interface X extends RawImage` and `RawImage`-typed variables passed in. A conditional parameter type (`image: Checked<I>`) avoids that but breaks callers' generic wrappers (`<J extends ImageLike>(img: J) => quantize(img, 4)` stops compiling), as a prototype showed.
  - **A typo (`premultiply: true`) would pass silently**, because image objects don't reject unknown keys; rejecting them is breaking too.
  - So 4.0 does all three together: `RawImage` as a union by `format`, `premultiplied` on the formats with alpha, and unknown keys on image objects rejected (or the near misses of known ones). Until then the API reference's Input section shows the conversion loops.
  - **Evidence from the 3.2.0 exploratory round:** premultiplied buffers are common, not an Electron quirk. node-canvas's `toBuffer('raw')` (BGRA) and `@napi-rs/canvas`'s `data()` (RGBA) are premultiplied, and so are WebCodecs frames made from a canvas. Skipping the conversion visibly darkened translucent edges (light bands on an icon; red #ff1d1d read as #750e0e). The JavaScript conversion costs about as much as `quantize` itself (190 ms against 210 ms on a 4K image), and runs on the calling thread even with the worker entry, so doing it in the module is worth it.
  - **Considered for 3.2 and rejected: format names** (`'bgra-premultiplied'`). They are additive and type-safe in 3.x, but with the property planned here they would leave two ways to say the same thing in 4.0.
- **Narrowed result types.** A mapped `RawImage` result is typed `RawImage`: `format: ImageFormat`, `data: Uint8Array | Uint8ClampedArray`, `width?`. Five of the six 3.2.0 testers had to cast it, though at run time `data` is always a `Uint8Array` and `format`, `width` and `height` are the input's. Results that keep the input's types (`RawImage<F>`, `data: Uint8Array`) belong with the `RawImage` union above, for the functions and the `Clustering` methods alike. A prototype showed why not in 3.x: narrowing breaks code that reuses a `let` across calls with different literal inputs (`'rgba'` then `'bgra'`, or with and without `width`). The 3.x docs show the cast.
- **The bare-image warnings become errors.** From 3.5.0 a bare `Uint8Array` that looks like RGB gives the `rgb-as-rgba` warning (Next, item 8), and from 3.6.0 one that looks like grey gives `gray-as-rgba` (item 9). 4.0 rejects both with `invalid-argument` on `'image'`:
  - RGB: "Invalid image: these bytes look like RGB (3 per pixel), or grey, not RGBA. …", leading with both fixes and saying that grey must be converted, not passed as `'rgb'`;
  - grey: "Invalid image: these bytes look like grey (1 per pixel), not RGBA. …" (or grey and alpha, 2 per pixel), naming the conversion, since there is no grey format to name.

  Each rejects exactly the inputs the last 3.x release warns about, or more after measuring again, never fewer (PRINCIPLES "Warnings"); the rule to measure is the shipped one (`bareLayout` in `dist/shared.mjs`), on the corpora in `bench/spikes/bare-rgb/` and `bench/spikes/bare-grey/` (`bare-rgb/check.mjs` is 3.5.0's sampling). The RGB rule still decides first. They run after the encoded-file and multiple-of-4 checks, and `{ data, format: 'rgba' }` stays the way to say RGBA bytes really are RGBA. Both codes then leave api.md "Warnings", which is empty unless a new bridge to 5.0 is added.
- **`alpha` and `transparent` on a format without alpha throw.** In 3.x, `'rgb'`, `'rgbx'` and `'bgrx'` accept both options and ignore them, so that one set of options can serve images of every format. But a caller who passes a `BI_RGB` bitmap as `'bgrx'` with `transparent: true` gets no transparent entry and no warning. 4.0 makes it an `invalid-argument` error on `options.alpha` or `options.transparent`, in the functions and the `Clustering` methods. Throwing in 3.x would break existing `'rgb'` calls. Raised by the API review of the 3.2.0 spec. Open question: whether a value that asks for nothing (`transparent: false`) is still accepted, so that shared option objects keep working. A 3.x warning for it under the warnings convention (PRINCIPLES) is possible, not planned.
- **Whether to deprecate the `…FromClustering` functions,** now that `Clustering` methods lead the cluster-once workflow (3.3.0), decided by how much they are used. In 4.0 the one-shot functions lead for single results, the methods for cluster-once, `…WithPalette` for palettes, and functions and handles in the worker entry. A gap to settle first: in the worker entry, `…FromClustering` is the only off-thread way to cut or map a *stored* clustering, since a handle needs an image and methods run on the calling thread. Three ways out:
  1. **Keep the worker entry's `…FromClustering`.** The entries would then mirror each other only in part.
  2. **Deprecate them in the main entry only,** and keep the worker's as its stored-clustering form; weaker against "Both entries behave alike". The guides' fixed-palettes recipe (`chooseThreads`, `improveThreads`) uses `getPaletteFromClustering` and `getSwatchesFromClustering` from either entry, so it runs with the worker entry; under this way out it would import them from `/worker` or switch to the methods.
  3. **Add a handle made from a clustering** (`worker.load(clustering)`, for example), which fits "off the main thread, the handle is the answer". It holds no image, so its `quantize` needs a shape of its own (`(image, k)`, or no mapping methods), decided before it is built. It waits for a request.

  The names spec of item 5 drafted the 4.0 name table under both outcomes. Under either one a name is kept or removed, never renamed, so no family is renamed twice:

  | Family | One-shot (main and worker) | Method on `Clustering` | Handle method | A: `…FromClustering` kept | B: deprecated in the main entry |
  |---|---|---|---|---|---|
  | Clustering | `buildClustering(image)` | — | `getClustering()` | — | — |
  | Palette | `buildPalette(image, k)` | `getPalette(k)` | `getPalette(k)` | `getPaletteFromClustering(c, k)` | the method; worker: ways out above |
  | Swatches | `buildSwatches(image, k)` | `getSwatches(k)` | `getSwatches(k)` | `getSwatchesFromClustering(c, k)` | same |
  | Info | — | `getClusteringInfo()` | `getClusteringInfo()` | `getClusteringInfo(c)` | kept or deprecated with the others, decided with this question |
  | Mapped image | `quantize(image, k)` | `quantize(image, k)` | `quantize(k)` | `quantizeFromClustering(image, c, k)` | same |
  | Indexed image | `quantizeToIndices(image, k)` | `quantizeToIndices(image, k)` | `quantizeToIndices(k)` | `quantizeToIndicesFromClustering(image, c, k)` | same |
  | With a palette | `quantizeWithPalette`, `quantizeToIndicesWithPalette` | — | the same names | — | — |
  | Worker handle | `worker.cluster(image)` | — | — | — | — |

  A `worker.load(clustering)` handle (way out 3) keeps the handle names; its mapping methods' shape is still open.
- **Remove the `get…` names of the functions that cluster an image** (`getClustering(image)`, `getPalette(image, k)`, `getSwatches(image, k)`, in both entries), deprecated from 3.4.0 in favour of `buildClustering`, `buildPalette` and `buildSwatches` (Next, item 5). 4.0 also renames the worker's wire names, which stay the old ones through 3.x.
  - In 4.0, `get…` names only calls that read or cut what they're given; they never cluster, map or search, in function and method forms alike. The maintainer decided this in 3.3.0 (PRINCIPLES "Settled decisions").
  - The 4.0 type entries above (narrowed results, the `RawImage` union) apply to the verb functions.
  - **Unaffected:** `getPaletteFromClustering`, `getSwatchesFromClustering`, `getClusteringInfo`, and every `get…` method on `Clustering` and handles.
- **Whether to version the clustering tag key,** so that `instanceof Clustering` means "has methods" and a clustering tagged before 3.3 no longer passes it ("Considered": "Telling a pre-3.3 clustering from one with methods"). The cost: 4.0 copies would stop recognising every 3.x clustering, including those with methods, and users would wrap them with `new Clustering(bytes)`. The palette key has no such reason to change. Decide by whether users report the `TypeError`.

## Engineering, alongside the releases

- **The sanitized suite in CI.** `scripts/asan-test.sh` runs the suite against an ASan/UBSan build of the WebAssembly, and the native fuzzers (`scripts/native.sh`) run in CI. The sanitized suite doesn't, yet: it takes about 9 minutes, and ten tests fail for reasons of the build, not the code (the heaviest time out at their own limits, and ASan's 512 MB starting heap is above the 256 MB at which the library discards its instance after every call, which also makes every call reload the module). A threshold the tests could raise, and timeouts that scale, would let it run clean.

## Considered, and why not (yet)

These came up in testing. Each is either covered by a recipe in the docs or not worth its permanent API yet; any can move up if users or the maintainer ask for it, and all but those settled as outside the library are weighed again before each major version under the feature test as revised on 2026-11-24 (PRINCIPLES "Recipes are reviewed again"), which counts a recipe's costs to its users. Verdicts below that say no person asked, or that test 2 fails, predate that revision: the maintainer asking now passes test 2.

- **Suggesting a palette size, built in.** The value brief (`docs/superpowers/briefs/2026-11-24-palette-size-brief.md`) measured rules on the error curve against the smallest size that reaches a mean ΔE2000 target: an absolute error ceiling is within a factor of 1.3 to 1.5 on average, and the guides ship it as `sizeForError`, with the exact search as `sizeForScore`. A Kneedle elbow on log k (up to 256) picked 2 to 9 colours on every image, so it is not built either. A built-in would only add a default threshold, which is the app's policy (PRINCIPLES), or a faster perceptual search in WebAssembly (not measured; a metric in the C++). Reopen if users ask for a perceptual target and the search's time (about 1 s a photo) is their complaint; it would map at every step, so it takes a verb name, not `get…` or `build…`.
- **Choosing N colours from a fixed palette, built in.** The spike (item 3 above) found a search over subsets that beats the recipe by about 0.4 dB at 6 to 12 colours, and the guides ship it as `improveThreads`, built on the public API. Speed is no longer a reason to build it: re-reviewed under the revised feature test on 2026-11-24 (`docs/superpowers/briefs/2026-11-24-recipe-review.md`), the guides' search was rewritten with a fast swap pass (one sweep over the swatches per thread instead of one per thread and position), which chooses the same threads in 192 of 192 cases and is 5 to 25 times faster (37 ms for 40 of 1000, was 907), and the same pass in C++ was only 1.8 times faster than that<!-- bench/spikes/fixed-subset-speed/speed.mjs → results-speed.txt -->. Weighed again on 2026-11-24 with a value brief (`docs/superpowers/briefs/2026-11-24-fixed-subset-brief.md`): scoring the search in OKLab lowers the mean ΔE2000 on three of four charts undithered, in either mapping space (4 of 26 pigments 23.3 to 18.7, 16 of 78 bricks 10.0 to 9.3, 12 of 584 threads 7.13 to 6.87; about even on a dense chart), at 0.3 to 1.7 dB less PSNR<!-- bench/spikes/fixed-subset-oklab/measure.mjs → results.txt -->. The maintainer chose the recipe: the guides' `improveThreads` now scores in OKLab by default (`'rgb'` on request), returns the threads heaviest first, and uses the function forms so it also runs with the worker entry. A built-in would add no quality over that, would have to pick a scoring default against the settled RGB default (PRINCIPLES "Settled decisions": "The default colour space stays `'rgb'`"; the gain follows the scoring space, not the mapping space, so an OKLab scoring default needs the maintainer's ruling on whether it reopens that), and would promise a heuristic search's output for the major version (`scope-steward`: trim; `user-advocate`: build smaller). Reopen for a named use case that needs the search off the calling thread, such as a live thread-count slider (21 to 56 ms for 12 to 40 threads there today<!-- bench/spikes/fixed-subset-oklab/speed.mjs → results-speed.txt -->), as the smaller shape: the clustering form, its method, the worker function and a handle method, in JavaScript (a new `…FromClustering` name, which bears on the 4.0 question about that suffix). The notes below are from the earlier reviews; where they differ, the brief and this paragraph supersede them. The shape the design reviews reached (a starting point for a spec, not a settled decision):
  - **A pair of functions, not an option.** `buildPalette(image, k, { from: threads })` would be the smaller shape, but a chosen subset doesn't nest (the best 12 aren't the best 11 plus one), so `buildPalette` would return palettes that aren't in split order, against a settled decision; and it would return colours where users need positions in their chart. So functions (since 2026-11-24, the clustering form only; no image form) with a verb name (open, since the subset is a search and `get…` names only reads; not `build…`, which means "cluster an image" since 3.4.0), for example `<verb>(image, palette, k, options?)` and `<verb>FromClustering(clustering, palette, k, options?)`, arguments in the existing order and with the existing `argument` names (`'palette'`, `'k'`). `…WithPalette` doesn't fit: it means "map to this whole palette", not "choose from it". The names are for the reviewers, following PRINCIPLES "Names follow their family".
  - **Result** (open: since `weights` and `shares` come from swatches, not from the mapped pixels, the result could be just the chart positions, heaviest first): a sibling of `Swatches`, `{ indices, palette, weights, shares }`: positions in the given palette, the chosen colours as a `Palette`, and their weights and shares, entry `i` of each describing the same colour, most used first (the order the guides' `rankSwatches` gives).
  - **Options:** the image form takes the clustering options and `signal` and `onProgress`, and scores in its `colorSpace`. The clustering form takes `{ colorSpace?, signal?, onProgress? }`, `colorSpace` defaulting to the clustering's own, as `quantizeFromClustering` does; it would be the first image-less function with options. No `dither`: scoring through dithering would be a different, much slower objective.
  - **Their cost:** the worker function, a handle method, a method on `Clustering` with a verb name sharing its function form's stem (PRINCIPLES "Names follow their family"), and the result type. No C export: C++ was only 1.8 times faster than the JavaScript search.
  - **The algorithm:** start from the recipe's choice, then best-improvement swaps over the clustering's swatches; the spike's code and numbers are in `bench/spikes/`. The scoring space and its default are open: the brief's data favour OKLab for ΔE whatever the mapping space, and RGB for PSNR.

- **Dithering in linear light, built in** (`dither: { linearLight: true }`). Every method mixes sRGB values, so with a few inks photos come out up to 2.6 times too bright on the panel. Found by the 3.1 exploratory round (an outside-user agent, which asked for docs and called an option "a nice to have"); no person has asked. A spike after 3.4.0 (`bench/spikes/linear-light/`, spec in `docs/superpowers/specs/2026-11-22-linear-light-design.md`, marked not built) measured it on the 24 Kodak photos:
  - **What matters is the matching, not the precision.** Carrying the error in linear light at full float precision gained nothing over the old 8-bit recipe. Matching in linear YCbCr with the colour axes weighted ×2 (brightness first) did: e-ink ΔE in light 19.8 (today) → 5.3 (old recipe) → 4.4 with Floyd–Steinberg, 20.6 → 8.9 → 6.0 ordered, no colour casts in greys.
  - **A recipe gets the same.** Encoding those coordinates into the three bytes makes the library's own RGB matching and error carrying act in them: 4.3 and 6.2 on e-ink, 12.2 and 12.3 in black and white, through the real package. That is `ditherInLight` in docs/api.md, so the built-in would add only convenience (no conversion on the calling thread, about 100 ms at 4K) and a small gain on palettes cut from the image (2.47 → 2.26 at 16 colours, where the recipe's 8 bits are slightly worse, 2.69). It didn't pass PRINCIPLES test 1.
  - **Measured and rejected:** matching in OKLab, or in OKLab's linear LMS stage, with error in linear light (worse than today: light adds up only in a linear space); the S-CIELAB opponent space; Atkinson in light (crushes shadows).
  - **Shapes turned down:** `colorSpace: 'linear'` (would change clustering and the stored header byte, and give 4.0 two ways to say it); a top-level option (against the option-shape convention); `light: 'srgb' | 'linear'` (respells `'rgb'`); a user-set weight (an internal constant until someone asks).
  - **If it is built** (a person asks, or the conversion's cost matters), the reviews of the spec reached this shape (a starting point for a spec, not a settled decision): `dither: { linearLight: true }`, not bare `linear` (a cold reader took it for a scan order, linear output or linear input); while dithering it sets how pixels are matched, and `colorSpace` keeps setting the clustering in `quantize` and `quantizeToIndices` (rejected only when a call that only maps names both); Atkinson allowed and documented as darker (in light it still beats today's Atkinson on every set); no effect at strength 0; and `linearLight` joins a frame mapper's recipe key, if one is built ("Reusing ordered-dithering recipes across calls, built in", below). Whether 4.0 should make it the default for small fixed palettes (a tester expected it) is a question for then.
- **Reusing ordered-dithering recipes across calls, built in** (item 6). A prepared palette or a frame-mapper object would keep recipes between calls; the guides' batching recipe already gets the same speed with the same output (item 6 has the numbers), so a built-in would add only convenience and work on frames that arrive one at a time, at the cost of state held across calls (8–32 MB in the WebAssembly heap, with a lifetime rule and a worker twin; PRINCIPLES test 4). No person asked; two exploratory-round agents (a video-to-GIF CLI and a screen-recording extension) tried both shapes: both misread `preparePalette(palette, options)` (as an index, not a dither cache) and ranked it last, and both preferred `createFrameMapper(palette, options)` with `.quantizeToIndices(frame)` and `.close()`, options fixed at creation. That is the shape to start from, though it is a second way to map with a palette beside `quantizeWithPalette`, which the 4.0 table keeps as the one. Reopen for a user whose frames arrive one at a time with a palette fixed across them and for whom a batch's latency is unacceptable, shown by a measured per-frame cost (the live-video recipe cuts a palette per frame, which no cache would survive).
- **Swatch helpers, built in: a dominant colour, heaviest-first order, swatch objects, hex strings.** Asked for by the fourth round's agents: migrating from color-thief and node-vibrant took 26 to 41 lines of glue, decoding included, and a video tool wanted the same. The value brief (`docs/superpowers/briefs/2026-11-23-swatch-helpers-brief.md`, spike in `bench/spikes/swatch-helpers/`) found that the guides already had the recipes before that round, so the agents rewrote them. It also found that every built-in shape would add only convenience. The guides now give one tested `rankSwatches` (7 lines, 105 µs for 256 swatches), a ranked `Palette` that keeps its colour space, and two ways to rank an indexed image: mapping to the ranked palette at no extra cost, or renumbering by pixels mapped (about 40 ms at 12 megapixels). The README and the migration table link to them. The three built-ins weighed:
  - **A `rankSwatches(swatches)` function:** it fails PRINCIPLES test 1, since a user can write it correctly and fast in a few lines.
  - **An ordering option** (`buildSwatches(image, k, { order: 'weight' })`): it would be the first option in `ClusteringOptions` that isn't about clustering. The three ways to cut swatches (`clustering.getSwatches(k)`, `getSwatchesFromClustering` and handles), which take no options, would all need them. And a `Swatches` result's order would mean two things, failing test 6.
  - **A one-call dominant colour:** PRINCIPLES leaves vivid dominant colours to color-thief and node-vibrant. It would also hide a choice of `k` that moves the answer: going from 5 colours to 8 changed the heaviest colour by more than ΔE 10 on 11 of 24 Kodak photos (tests 3 and 6).
  - **Reopen** for a request made after the recipes are linked from the migration table and the README, or for a need the recipes can't meet.
- **A background (matte) colour for transparent pixels** (`matte: [255, 255, 255]`), for logos sent to opaque hardware. Compositing onto a background before the call is a few lines, and it is unclear whether an option should affect clustering, mapping or both. Guides: "Fixed palettes".
- **A built-in worker pool.** Every server tester wanted one, but its queueing policy (small images behind large ones, backpressure, memory per worker) depends on the app. Performance and limits: the pool recipe in "Servers".
- **Clustering several images at once** (`buildClustering([frames])`), for one palette across an animated GIF or a set of images. Concatenating sampled frames into one image already does it in one line, with the same result. Guides: "Animated GIFs and sets of images".
- **Decoding image files, built in** (a file's bytes, a `Blob` or a `Response` as the image). Settled as not the library's job (PRINCIPLES "Settled decisions"): unlike most of this list it doesn't move up on request, and only the maintainer reopens it; the guides' "Decoding image files" has a recipe per environment. The value brief (`docs/superpowers/briefs/2026-11-23-decoding-brief.md`, spike in `bench/spikes/decoding/`) measured them on 13 files against sharp: the browser's `createImageBitmap` gives palettes within 1.03× on all of them (partly transparent pixels are rounded), jsquash on all but colour profiles (a Display P3 photo 1.47×). A built-in would wrap the same decoders, so it adds no quality or speed; bundling PNG, JPEG and WebP would add 192 KB gzipped to a 44 KB library, and one without colour management would be the "half-done decoder" a tester called worse than none. No person had asked: the old "asked for in every round" had no recorded quote, and of three exploratory-round agents the edge-runtime one minded moderately, the browser one mildly, and the CLI one not at all. What testing did find was traps after decoding: a bare RGB array read as RGBA (a worse palette with no error), and fast-png's unexpanded output.
- **Palette PNG and GIF writers.** fast-png and gifenc do it well; the guides have both recipes, which decode pixel-exactly.
- **Smoothing palettes between video frames.** Each frame is clustered on its own, so palettes flicker; matching each palette to the last and easing towards it cut the flicker about fourfold in the fourth round. It is a dozen lines with app-specific choices (weight, lag, what to do when the colour count changes), so it is a recipe in the guides ("Live video and camera frames"). A built-in would need state across calls, which nothing else here has.
- **Methods on `Palette`** (`palette.quantize(image)`). `…WithPalette` takes a `PaletteLike`, and most fixed palettes (brand colours, inks, threads) are plain arrays, so a method would need a `new Palette([...])` wrap on that path or leave two ways to map with a palette (PRINCIPLES "Methods go where losing them costs nothing"). Palette mapping stays `…WithPalette`. Item 6 ended as a recipe, so `Palette` keeps no methods (PRINCIPLES "Settled decisions").
- **Loading the main entry lazily from the worker entry**, so a `Clustering` from the worker entry has working methods in a worker-only app (considered for 3.3.0). Nobody asked for it, and it would ignore `createWorker({ wasm })` (so it would fail on the CDNs, strict CSPs and edge runtimes where users set it), pull the main entry and its `.wasm` into every worker-only bundle, and run heavy mapping on the thread the user chose the worker entry to keep free. Adding it later is additive; removing it would break code.
- **One engine slot for every copy of the package** (on `globalThis`), so a clustering marked by the CommonJS copy finds an ES-module main entry. It needs a global, a rule for which copy wins, and would send method calls to an engine of another version; the case is rare, and the error names it. Additive later if asked for: 3.3 promises that same-version copies recognise each other's values, not which engine a method uses.
- **Telling a pre-3.3 clustering from one with methods** (considered for 3.3.0). A clustering tagged by a copy older than 3.3 passes `instanceof Clustering`, because the tag key (`Symbol.for('agglomerative-clustering.clustering')`) carries no version. TypeScript then narrows it to a type with methods, and calling one throws a `TypeError` with no `code`. Two fixes were weighed. One is versioning the tag key: 3.3 copies would stop recognising 3.0–3.2 clusterings. Recognition across versions is not promised (stability.md promises it only within one version; PRINCIPLES leaves the keys open to versioning), but 3.0 shipped it. The other is making `instanceof` also require the methods: a check would start answering false for values it accepts today, while every function still takes them. Either would change existing results in 3.x for a case that only installs mixing versions reach. So it is documented instead (API reference, "Copies of the package": wrap with `new Clustering(bytes)`). Revisit if users report it; the versioned key is an open question for 4.0 (see "4.0").
- **An abort check (`isAbortError`) or a code for "this worker is gone, retry elsewhere".** An abort is the signal's own reason, so the caller's `signal.aborted` is the reliable test (API reference: "Cancelling and progress"); `worker-terminated` and `worker-failed` already separate a stopped worker from a crashed one (API reference: "Errors").
- **An idle timeout for workers** (`createWorker({ idleTimeout })`: stop the thread after some idle seconds, start it again on the next call). It would free the memory an idle worker keeps after a large image, but held clusterings live in the thread, so it could only stop with none held, and a restart costs 10 to 70 ms. A dropped worker is now stopped once collected, and `terminate()` frees memory at once; this can come later as an option if long-running services ask for it.
- **Our own error class** (`instanceof AgglomerativeError`). Errors from the worker are rebuilt on the calling side, and errors that cross Electron's IPC or a `postMessage` are plain objects, so `instanceof` would mislead; `isCodedError` works in all three.

## Later, if asked for

- **`format: 'gray'` and `'gray-alpha'`**, for 1- and 2-channel grey (fast-png's grey PNGs). The guides' `fastPngToImage` converts them in about 45–52 ms at 12 MP, against about 80 ms to cluster the image (`bench/spikes/bare-grey/results-recipe.txt`); a format would save that and 4× the memory. Not built in 3.6.0: no one asked, one known decoder returns these layouts, and it would cover only 8-bit grey (packed and 16-bit rows still need converting). Reopen if a user with grey input asks, or if the conversion's cost shows up in a report. A format would also let grey silence `gray-as-rgba` by saying what it is, which today only converting does. Spelled `gray` (PRINCIPLES "Settled decisions"). Value brief `docs/superpowers/briefs/2026-11-23-bare-grey-brief.md`.

- **Palette entries with alpha**, for palette PNGs with translucent colours. A spike (exact Ward in premultiplied RGBA, on the unmerged branch `spike/rgba-4d`) was exact and matched libimagequant on that case, but was 4-6× slower on photos with smooth alpha, needed a second engine and a format change, and lost about 6 dB against today's alpha-weighted clusters with per-pixel alpha for canvas output. Not worth it for 3.0; libimagequant is the better tool for translucent palette PNGs.
- **Very large images.** Memory is capped at 2 GB, and partly transparent images above about 16.8 MP have their weights scaled down. Streaming the histogram in chunks would remove both limits.
