# Roadmap

What is planned, what is only being considered, and what was decided against, with the reasons. Each release keeps output byte-identical unless it says otherwise; `test/golden.test.js` enforces that.

**The rule for what goes where.** 3.0 freezes the API: anything that would change the shape or defaults of an existing function was decided before it. Everything below only adds (a new option, a new value of an option, a new function), so it can come in any 3.x release without breaking anyone, except the "4.0" section, which collects what can't. Most items come from exploratory testing of the 3.0 betas: fresh agents building real projects from the npm package alone (Electron, a Chrome extension, Jest and Vitest suites, e-ink and embroidery tools, a static-site build, a wrapper package, CDNs, Deno, Bun, Cloudflare Workers, SvelteKit, Nuxt, Next.js, servers, animated GIFs).

## Clustering format versioning

The clustering is the only format users store, so it is the only one that needs versioning. Palettes are plain RGB bytes, and messages between the main thread and the worker never outlive one installed version of the package.

Since 2.0 every clustering starts with `[0xAC, version, …]`. Clusterings from 1.x had no header and were recognised only by their length (0 or 3 more than a multiple of 9, where 2.x lengths are 4 or 7 more). That was fragile in a way that mattered: many other byte strings, such as palettes of 1, 3, 4, 6, 7 or 9 colours, have those lengths and were accepted as clusterings, returning nonsense. 3.0 stopped reading 1.x clusterings, so a buffer is a clustering only if it carries the header. These rules hold:

1. **Readers decide by the version byte, never by shape.** Every version is identified by its header.
2. **Versions 2 and 3 pad the end with zero bytes** so the length is 4 (empty) or 7 more than a multiple of 9. The padding dates from when that kept them out of 1.x's lengths; it stays so existing bytes stay stable, and readers ignore it (it is shorter than a record).
3. **From v3 the header describes its own layout:** `[0xAC, version, header length, record length, colour space, precision, …]`. A reader finds the records from the stored lengths and ignores fields it doesn't know, so fields can be added at the end of the header or of each record without a new version. The version is bumped only when an existing field changes meaning.
4. **Readers reject versions newer than they know** with an error asking for an upgrade, and never guess. The same goes for a header field with a fixed set of meanings (the colour space, the weight unit) that holds a value they don't know: that is how a later release adds one, so it is `unsupported-version`, not "damaged".
5. **Every version from 2 on stays readable.** `fixtures/clusterings/` holds a stored clustering of each format version with the palettes (and from v3 the weights and mean squared errors) its release gave, and `test/formats.test.js` checks them. Each new version adds a fixture; existing ones are never regenerated.

## 3.0: worker, indexed output, weights and error curve (released as 3.0.0)

What was planned as 2.1 and 3.0 ships together as 3.0, since the clustering format changes anyway.

- [x] **Worker entry** `agglomerative-clustering/worker`: `createWorker()` with handles that keep an image and its clustering in the worker, and drop-in exports over one shared worker. Web Worker in browsers, `worker_threads` in Node.
- [x] **Indexed output:** `quantizeToIndices*`, with `transparent` (an alpha cutoff).
- [x] **Clustering format v3**, following the rules above. Records are 21 bytes: colours, the split's parent index, the lighter half's weight and the Ward cost. The parent index is needed because different clusters can share an 8-bit colour, which would otherwise make weights ambiguous.
- [x] **Swatches** (`getSwatches`, `getSwatchesFromClustering`: palette, weights and shares) and the **error curve** (`getClusteringInfo().mse`, and the unitless `explained`), for choosing a palette size by error.
- [x] **Cancellation and progress:** `signal` and `onProgress` on every function with an image; the clustering is a resumable job run in slices, and the worker stops working on a cancelled call.
- [x] **`init({ wasm })`** and the `clustering.wasm` export, for CDNs, strict CSPs and edge runtimes; one shared load.
- [x] **Error codes** on every error, kept across the worker boundary, with `errorCodes` and the `isCodedError` guard.
- [x] **Runs where people put it:** CDNs (cross-origin workers through a `blob:` module), Deno, Bun, Cloudflare Workers, Next.js server bundles, SvelteKit and Nuxt, Electron (packaged with asar), browser extensions, Jest's CommonJS mode, jsdom; `createWorker({ script })` for bundlers that don't emit the worker script (Angular, esbuild, Rollup).
- [x] **Tests as a consumer sees the package:** a Vite build run in headless Chromium (worker, `.wasm`, slices, aborts, `wasm` locations), strict TypeScript against the built declarations, and the full suite on Node 20, 22 and 24, in CI.

## Next: one minor release each, in this order

Each item ships as its own minor release when it is ready, rather than waiting for the others.

1. **Dither methods (3.1.0).** `dither` now also takes `'atkinson'`, `'ordered'` and `{ method, strength, steps }`, the first option with an object form (see "Option shapes" in docs/api.md). Error diffusion makes each frame's pattern depend on every pixel before it, so an animated GIF's dither crawls from frame to frame even where the picture is still; ordered dithering is fixed to the pixel grid, so still areas stay still. Asked for by the hardware-palette round; the animated-GIF round showed the flicker.
   - **How ordered works:** pattern dithering after Knoll. Each distinct colour gets a recipe of `steps` palette colours (default 64 for two colours, else 16), built by repeatedly picking the colour nearest the target plus the error carried so far, sorted dark to light and laid out by an 8×8 Bayer matrix.
   - **Quality** (six Kodak photos, mean ΔE2000 after a σ 1.5 blur): at 16 colours Floyd–Steinberg 2.55, ordered 2.72, Atkinson 3.09, none 3.72; with seven e-ink inks 2.91, 8.2, 6.7 and 21.6 (in sRGB values; see below). The textbook threshold method (offset each pixel by the matrix, then take the nearest colour) was tried in a spike and dropped: 3.67 at 16 colours and 12.9 on e-ink, since one offset size can't suit an uneven palette.
   - **The roadmap used to say ordered suits e-ink.** For accuracy it doesn't: ordered is for animation and displays that need a fixed pattern. And every method mixes sRGB values, which the eye doesn't: with a few widely spaced inks, dithered photos look much lighter on the panel (blurred in light, ΔE 17–22 on the seven inks for every method). Converting to linear light first cut that to 5–7 with Floyd–Steinberg (docs/api.md has the recipe).
   - **Capping a recipe's carried error** (as Floyd–Steinberg caps what it passes on) was tried and dropped: it made e-ink much worse (8.2 to 14.7) for little speed.
   - **Speed** (768×512, 16 colours): 66 ms at 16 steps against 27 ms for Floyd–Steinberg, after an exact four-wide search for recipe steps (it was 89 ms). Possible later settings, each additive: other patterns (blue noise), matrix sizes, a serpentine toggle.
   - **Changed after an exploratory round on the release candidate** (an animated-GIF maker, and e-ink, 1-bit and sprite tools): `mix` became `steps` (both testers read "16 palette colours" where it means 16 pattern cells, so two colours blend in 17 shades); the default became 64 steps for two colours (16 bands visibly on a black-and-white gradient; 64 costs 4.6× the time but changed nothing measurable on photos at 3–4 colours, so the rest keep 16); ordered's strength now goes through a table per step count, since taken as it was, 0.5 looked like 1 (a single 2.5 power fitted 16 steps but left 64 steps changing 70% of the pixels by 0.25 and 16 steps doing nothing at 0.05; ordered's response to the raw amount is smooth but very steep, a third of the full change at 0.01 with 64 steps, so the table inverts the measured response at 0.05, 0.1, 0.25, 0.5 and 0.75 to follow Floyd–Steinberg's, interpolating geometrically, and on photos it wasn't fitted on every step count stays within a few points of Floyd–Steinberg's response); the recipe table is sized to the image (a 1×1 call took 217 µs, now 16 µs); and errors echo the value and point misplaced settings at `dither: { … }`. A second round (a Vite app with live controls, the docs' recipes run as written, and a fuzz of the option in both entries) found a 3.0 bug, cancelled worker calls queued behind a mapping call still running (fixed), the worker entry not reading the `dither` object as the main entry does (fixed), the animated-GIF recipe giving frames with and without transparency different colours (fixed by cutting 255 colours once), and how slow ordered dithering gets on images of nearly all different colours (documented; slicing mapping, below, would make it cancellable).
2. **BGRA input and output (3.2.0)** (`format: 'bgra'`, and `'rgbx'`/`'bgrx'` for buffers whose fourth byte isn't alpha; straight alpha only, premultiplied waits for 4.0, see below): images are read in their own channel order and mapped images come back in it, so Electron's `nativeImage` (BGRA on Windows, macOS and Linux, per Chromium's Skia config), Windows bitmaps, WebCodecs frames and ffmpeg's raw video need no channel swapping in JavaScript. A pixel layout read at run time in the C++ (no second copy of the pixel loops); clusterings, palettes and indices are byte-identical to the same pixels as RGBA or RGB. The `x` formats came from an exploratory round on the first candidate (six outside-user projects: Electron, a BMP tool, server-side canvases, WebCodecs, an ffmpeg pipeline, a TypeScript wrapper), where four of six passed GDI screenshots, `BI_RGB` bitmaps, WebCodecs `BGRX` or ffmpeg `bgr0` frames as `'bgra'` and got an empty palette and black output with no error. The same round found three older bugs, fixed in 3.2.0: unvalidated `ImageData` layouts (skia-canvas `colorType`), the worker entry in Electron Web Workers with `nodeIntegrationInWorker`, and a docs sentence about the transparent entry. Asked for by the Electron round.
3. **Choosing N colours from a fixed palette: done as a recipe, no function** (12 threads out of 400, 40 bricks out of a full catalogue, 6 inks out of a pigment set). The spike (`bench/spikes/fixed-subset.js`, write-up in `fixed-subset.md`, pictures from `fixed-subset-visual.js`) compared four methods on the 24 Kodak photos and synthetic images, with synthetic charts of 26 to 1000 colours, scoring the mapped image by PSNR and CIEDE2000.
   - **Results:** the guides' recipe beat "the N most used" by about 3 to 4 dB at 6 to 12 of a large chart. A search over subsets (minimise the mapping error over 1024 swatches by swapping entries, starting from the recipe) added 0.4 to 0.45 dB at 6 and 12 of 584 (0.25 at 24, 0.12 at 40), was better on 22 to 24 of 24 photos and worse on none, and gained more with dithering. Snapping each merge's result to the fixed set (the other candidate) was slightly worse than the search and slower, so it was dropped.
   - **Decision:** the gain is consistent but small: on the photos it reads as a difference of taste more than a clear improvement, so it didn't meet this item's bar ("add a function only if it clearly wins"). And the search needs nothing inside the library: it runs on `getSwatchesFromClustering` in about 40 lines. So the guides have both functions, `chooseThreads` and `improveThreads`, and `test/recipes.test.js` runs them and checks that they match the guides' text. If it is ever built in, see "Choosing N colours from a fixed palette, built in" under "Considered".

4. **Methods on `Clustering`** (below), in a minor release of its own.
5. **Verb names for the functions that cluster (3.4.0).** `getClustering(image)`, `getPalette(image, k)` and `getSwatches(image, k)` get verb names in both entries. The old names are marked `@deprecated` and keep working through 3.x, and 4.0 removes them (see "4.0"). It comes before anything else that adds a name, so nothing new starts with a `get…` it would lose. Decided by the maintainer while designing 3.3.0 (PRINCIPLES "Settled decisions").
   - **Starts with a names spec** that drafts the whole 4.0 name table (one-shot, cut, method, handle method and worker export for each family) under both outcomes of the `…FromClustering` question, so 4.0 doesn't rename a family twice.
   - **A pure rename:** same arguments, options, `signal` and `onProgress`, results and errors. The deprecated name is the same function, in both entries and on `AgglomerativeWorker`, and the worker's routing tables (`optionsPosition`, `imageFunctions`, `clusteringOnlyFunctions`, `optionsIndex`) gain the new keys.
   - **Constraints on the names:**
     - not `cluster` or `load`, nor siblings of them: `worker.cluster(image)` returns a handle, and `worker.load(clustering)` is a 4.0 option for stored clusterings;
     - each shares its noun with its cut (palette, swatches), so the families still pair;
     - they read as a family with `quantize`;
     - the most common call stays plain.
   - **Types:** `@deprecated` goes on the `index.d.ts` functions and the `AgglomerativeWorker` members, never on the same-named methods (`clustering.getPalette`, `handle.getPalette`). `handle.getClustering()` keeps its name. Error codes and `ErrorArgument` don't change.
   - **The release:**
     - every message, hint and doc comment names the new names;
     - `docs/migrating.md` gets the old-to-new table then, not at 4.0;
     - the CHANGELOG warns that `no-deprecated` lint rules will flag `getPalette`, and that `AgglomerativeWorker` gains members (a hand-written implementation or typed mock must add them).
6. **Reusing ordered-dithering recipes across calls.** Every call builds a recipe for each distinct colour, so ordered dithering costs about 7× Floyd–Steinberg on small frames, and frames of an animation that share a palette and most of their colours pay for the same recipes again. Keeping them between calls (keyed on the palette, steps, strength and colour space) could bring later frames close to the cost of mapping without dithering. It changes speed only, never output, so any 3.x release. Open questions: whether it is kept implicitly by the module (no new API, but 8–32 MB held between calls and careful invalidation) or by an explicit object such as a prepared palette (clean, but new API to keep for all of 3.x). Start by measuring the gain on a real animation. If reuse is kept by an explicit object (a prepared palette), decide with it whether it has methods and how they relate to `quantizeWithPalette` in 4.0, so there is one way to map with a palette. If it is kept implicitly, `Palette` keeps no methods.
7. **Dithering in linear light**, as a setting of `dither` (for example `{ method, light: 'linear' }`): mix colours as light rather than as sRGB values, which is what the documented recipe does by hand. It matters for black and white and a few inks (on e-ink photos, ΔE in light 17–22 down to 5–7), and it can work at full precision instead of the recipe's eight bits. Found by the 3.1 exploratory round. Its own minor release, with measurements.

Each lands with tests, documentation and CHANGELOG entries, and (for 1 and 3) a quality comparison recorded here. Item 3 ended as a recipe, so it needs no release of its own.

## Larger, later

- **Decoding image files** (asked for in every round of testing, and the biggest usability gain left; its own project because of the decoders' size and dependencies). Today a PNG, JPEG, GIF, WebP, BMP, TIFF, AVIF or HEIC file passed as a bare `Uint8Array` is recognised (`sniffImageFormat` in `src/index.js`) and rejected with a message saying how to decode it. The goal is that an encoded image just works. The groundwork is in place: detection is in one function, in the one place images enter (`load`), and only bare byte arrays are inspected, so a `{ data, format }` or `ImageData` is never second-guessed. Decoding would be added at that seam, which makes `load` asynchronous. The open questions are where the decoders come from (the browser's `createImageBitmap` where there is one; in Node, an optional peer such as sharp, or small bundled decoders for PNG, JPEG and GIF, which would add dependencies and size) and what to do with animation and EXIF orientation and colour profiles.
- **Swatch helpers: a dominant colour, heaviest-first order, swatch objects, hex strings.** Moved up from "Considered" below: asked for again in the fourth round (migrating from color-thief and node-vibrant took 26 to 41 lines of glue, and a video tool wanted the same). Additive, so any 3.x. Needs a design that keeps palettes in split order by default (it is what makes them nest), for example a `getSwatches` option or a small `rankSwatches(swatches)` helper returning `{ color, hex, share }` objects heaviest first.
- **Slicing pixel mapping.** Cancellation and progress cover the clustering, which is most of the work. Mapping (a few milliseconds for a photo, more with dithering on very large images) still runs in one piece; it could be sliced by rows the same way. Clustering a 12-megapixel photo also has a couple of unsliced steps (the histogram and the precision grouping) of up to about 150 ms; on 12 megapixels of noise at full precision one takes over a second, so slicing those would help servers that cancel on hostile input.
- **A Parcel smoke test**, alongside the Vite and webpack ones.
- **Smaller WebAssembly.** Pixel mapping is compiled twice (colour and index output), which accounts for much of the growth from 75 KB to about 93 KB. Plugin hosts that take one file (Figma, Obsidian) embed it as base64 (about 122 KB, 54 KB gzipped); a smaller module, or a gzipped copy in the package for `DecompressionStream`, would help them.
- **Methods on `Clustering`** (`clustering.getPalette(k)`, `clustering.getSwatches(k)`, `clustering.quantize(image, k)`, `clustering.getInfo()`), mirroring the worker's `ClusteringHandle`, so "cluster once, cut anywhere" reads without the `…FromClustering` suffixes. Planned as a minor release of its own (item 4 above), additively: `Clustering` is already a class. From the naming review before 3.0.0, which kept the function names for 3.x (including `get…` for the functions that cluster: the cheap cuts are getters, the Promise says the heavy ones do work, it is the convention of color-thief and node-vibrant, and `getPalette` is the most-used 2.x call). Those `get…` names are renamed from 3.4.0 (item 5).
  - **The docs then lead with the methods for the cluster-once workflow:** the slider example and the cluster-once recipes use `clustering.getPalette(k)` and `clustering.quantize(image, k)`, and the README's function table gets a methods column in place of the `…FromClustering` one.
  - **What stays:** the one-shot functions (`getPalette(image, k)`, `quantize(image, k)`, `getSwatches(image, k)`) stay the first thing people see, since a single palette has no clustering to call a method on. The `…WithPalette` functions stay too (unless `Palette` gets a matching `quantize(image)`, a separate decision).
  - **The `…FromClustering` functions stay, documented as the function form, and are not deprecated in 3.x:** they take a stored clustering as plain bytes in JavaScript, and the worker entry's exports are functions that mirror the main entry's. Whether to deprecate them is a 4.0 question, settled by how much they are used.
  - **Methods are a main-entry concept; the worker has handles.** A `Clustering` from the worker entry is bytes on the calling thread, so its methods would run on that thread's module, not in the worker. Off the main thread, `worker.cluster(image)` and its handle stay the answer. The methods take the handle's names so the two read alike, and the docs have to say which to use where.
  - **Open questions:** whether the methods are synchronous (the module is loaded once a `Clustering` exists, but the handle's methods are async, and matching them may matter more), and how they behave on a stored clustering wrapped with `new Clustering(bytes)` (the same, presumably).
- **Suggesting a palette size** from the error curve (an elbow heuristic), if users ask for more than `mse` and `explained`.

## 4.0: breaking changes, collected

Changes that would break code written against 3.x wait here for the next major version, so 3.x stays additive and 4.0 breaks once.

- **Premultiplied alpha** (`{ data, format, premultiplied: true }`, for RGBA and BGRA): Electron's `nativeImage.toBitmap()` is premultiplied (Skia `MakeN32Premul`, in `shell/common/api/electron_api_native_image.cc`), as are GDI's `AlphaBlend` bitmaps, WIC's `32bppPBGRA` and WebGL `readPixels` by default. Pixels would be un-premultiplied on read (`min(255, round(c·255/a))`, alpha 0 as black) and `quantize*` output premultiplied again (`round(c·a/255)`); palettes and clusterings stay straight. Why not in 3.x (decided while designing 3.2.0):
  - **Reading the field changes existing calls.** Image objects carry other fields today, and one that already says `premultiplied: true` is ignored; from that release its output would change, and a non-boolean one would start throwing.
  - **Typing it well is breaking.** Making `{ format: 'rgb', premultiplied: true }` a compile error needs `RawImage` to be a union split by `format`, which breaks `interface X extends RawImage` and `RawImage`-typed variables passed in. A conditional parameter type (`image: Checked<I>`) avoids that but breaks callers' generic wrappers (`<J extends ImageLike>(img: J) => quantize(img, 4)` stops compiling), as a prototype showed.
  - **A typo (`premultiply: true`) would pass silently**, because image objects don't reject unknown keys; rejecting them is breaking too.
  - So 4.0 does all three together: `RawImage` as a union by `format`, `premultiplied` on the formats with alpha, and unknown keys on image objects rejected (or the near misses of known ones). Until then the API reference's Input section shows the conversion loops.
  - **Evidence from the 3.2.0 exploratory round:** premultiplied buffers are common, not an Electron quirk. node-canvas's `toBuffer('raw')` (BGRA) and `@napi-rs/canvas`'s `data()` (RGBA) are premultiplied, and so are WebCodecs frames made from a canvas. Skipping the conversion visibly darkened translucent edges (light bands on an icon; red #ff1d1d read as #750e0e). The JavaScript conversion costs about as much as `quantize` itself (190 ms against 210 ms on a 4K image), and runs on the calling thread even with the worker entry, so doing it in the module is worth it.
  - **Considered for 3.2 and rejected: format names** (`'bgra-premultiplied'`). They are additive and type-safe in 3.x, but with the property planned here they would leave two ways to say the same thing in 4.0.
- **Narrowed result types.** A mapped `RawImage` result is typed `RawImage`: `format: ImageFormat`, `data: Uint8Array | Uint8ClampedArray`, `width?`. Five of the six 3.2.0 testers had to cast it, though at run time `data` is always a `Uint8Array` and `format`, `width` and `height` are the input's. Results that keep the input's types (`RawImage<F>`, `data: Uint8Array`) belong with the `RawImage` union above. A prototype showed why not in 3.x: narrowing breaks code that reuses a `let` across calls with different literal inputs (`'rgba'` then `'bgra'`, or with and without `width`). The 3.x docs show the cast.
- **`alpha` and `transparent` on a format without alpha throw.** In 3.x, `'rgb'`, `'rgbx'` and `'bgrx'` accept both options and ignore them, so that one set of options can serve images of every format. But a caller who passes a `BI_RGB` bitmap as `'bgrx'` with `transparent: true` gets no transparent entry and no warning. 4.0 makes it an `invalid-argument` error on `options.alpha` or `options.transparent`. Throwing in 3.x would break existing `'rgb'` calls. Raised by the API review of the 3.2.0 spec. Open question: whether a value that asks for nothing (`transparent: false`) is still accepted, so that shared option objects keep working.
- **Remove the `get…` names of the functions that cluster an image** (`getClustering(image)`, `getPalette(image, k)`, `getSwatches(image, k)`, in both entries), deprecated from 3.4.0 in favour of verb names (Next, item 5).
  - In 4.0, `get…` names only calls that read or cut what they're given; they never cluster, map or search, in function and method forms alike. The maintainer decided this in 3.3.0 (PRINCIPLES "Settled decisions").
  - The 4.0 type entries above (narrowed results, the `RawImage` union) apply to the verb functions.
  - The docs' stale-name check matches call shapes (`getPalette(image`), since the methods keep the names.
  - **Unaffected:** `getPaletteFromClustering`, `getSwatchesFromClustering`, `getClusteringInfo`, and every `get…` method on `Clustering` and handles.

## Engineering, alongside the releases

- **Native build and coverage-guided fuzzing.** Sanitizers are done by hand through Emscripten's ASan/UBSan WebAssembly build (recipe in CLAUDE.md; the suite and the hostile-input fuzzers are clean), but not in CI. A native target (CMake or a short script) for the C++ would add reproducible instruction counts (callgrind) for speed work and a libFuzzer harness for `read_clustering`, `_get_palette_from_clustering` and `_get_palette_weights`: clusterings are stored by users and handed back as untrusted bytes. A CI job running the suite against the sanitized build would keep it clean.
- **Contributor setup.** Every test needs `em++`. Add a `scripts/setup-emsdk.sh` pinned to the CI version, or a devcontainer, so `npm test` works from a fresh clone, and a SessionStart hook so cloud agent sessions can build too.

## Considered, and why not (yet)

These came up in testing. Each is either covered by a recipe in the docs or not worth its permanent API yet; any can move up if users ask for it.

- **Choosing N colours from a fixed palette, built in.** The spike (item 3 above) found a search over subsets that beats the recipe by about 0.4 dB at 6 to 12 colours, and the guides ship it as `improveThreads`, built on the public API. A built-in would add speed (C++ instead of JavaScript: 150 ms for 12 of 584 threads and 1.5 s for 40 of 1000 today), the worker and cancelling, and scoring in OKLab with the library's own conversion. It isn't worth new API yet: the gain is small, and a user can do it correctly outside. Build it if users ask for it, or if large charts in browsers turn out to be too slow. The shape the design reviews reached (a starting point for a spec, not a settled decision):
  - **A pair of functions, not an option.** `getPalette(image, k, { from: threads })` would be the smaller shape, but a chosen subset doesn't nest (the best 12 aren't the best 11 plus one), so `getPalette` would return palettes that aren't in split order, against a settled decision; and it would return colours where users need positions in their chart. So two functions with a verb name (open, since the subset is a search and `get…` names only reads), for example `<verb>(image, palette, k, options?)` and `<verb>FromClustering(clustering, palette, k, options?)`, arguments in the existing order and with the existing `argument` names (`'palette'`, `'k'`). `…WithPalette` doesn't fit: it means "map to this whole palette", not "choose from it". The names are for the reviewers, following PRINCIPLES "Names follow their family".
  - **Result:** a sibling of `Swatches`, `{ indices, palette, weights, shares }`: positions in the given palette, the chosen colours as a `Palette`, and their weights and shares, entry `i` of each describing the same colour, most used first (the order the swatch helpers in "Larger, later" would rank by).
  - **Options:** the image form takes the clustering options and `signal` and `onProgress`, and scores in its `colorSpace`. The clustering form takes `{ colorSpace?, signal?, onProgress? }`, `colorSpace` defaulting to the clustering's own, as `quantizeFromClustering` does; it would be the first image-less function with options. No `dither`: scoring through dithering would be a different, much slower objective.
  - **Their cost:** both in the worker entry, a handle method, a method on `Clustering` once those exist (item 4), the result type, and a C export.
  - **The algorithm:** start from the recipe's choice, then best-improvement swaps over the clustering's swatches; the spike's code and numbers are in `bench/spikes/`. Score in the call's colour space: in RGB the search sometimes improves PSNR while making mean ΔE worse (pigments at N = 4).

- **A background (matte) colour for transparent pixels** (`matte: [255, 255, 255]`), for logos sent to opaque hardware. Compositing onto a background before the call is a few lines, and it is unclear whether an option should affect clustering, mapping or both. Guides: "Fixed palettes".
- **A built-in worker pool.** Every server tester wanted one, but its queueing policy (small images behind large ones, backpressure, memory per worker) depends on the app. Performance and limits: the pool recipe in "Servers".
- **Clustering several images at once** (`getClustering([frames])`), for one palette across an animated GIF or a set of images. Concatenating sampled frames into one image already does it in one line, with the same result. Guides: "Animated GIFs and sets of images".
- **Palette PNG and GIF writers.** fast-png and gifenc do it well; the guides have both recipes, which decode pixel-exactly.
- **Smoothing palettes between video frames.** Each frame is clustered on its own, so palettes flicker; matching each palette to the last and easing towards it cut the flicker about fourfold in the fourth round. It is a dozen lines with app-specific choices (weight, lag, what to do when the colour count changes), so it is a recipe in the guides ("Live video and camera frames"). A built-in would need state across calls, which nothing else here has.
- **An abort check (`isAbortError`) or a code for "this worker is gone, retry elsewhere".** An abort is the signal's own reason, so the caller's `signal.aborted` is the reliable test (API reference: "Cancelling and progress"); `worker-terminated` and `worker-failed` already separate a stopped worker from a crashed one (API reference: "Errors").
- **An idle timeout for workers** (`createWorker({ idleTimeout })`: stop the thread after some idle seconds, start it again on the next call). It would free the memory an idle worker keeps after a large image, but held clusterings live in the thread, so it could only stop with none held, and a restart costs 10 to 70 ms. A dropped worker is now stopped once collected, and `terminate()` frees memory at once; this can come later as an option if long-running services ask for it.
- **Our own error class** (`instanceof AgglomerativeError`). Errors from the worker are rebuilt on the calling side, and errors that cross Electron's IPC or a `postMessage` are plain objects, so `instanceof` would mislead; `isCodedError` works in all three.

## Later, if asked for

- **Palette entries with alpha**, for palette PNGs with translucent colours. A spike (exact Ward in premultiplied RGBA, on the unmerged branch `spike/rgba-4d`) was exact and matched libimagequant on that case, but was 4-6× slower on photos with smooth alpha, needed a second engine and a format change, and lost about 6 dB against today's alpha-weighted clusters with per-pixel alpha for canvas output. Not worth it for 3.0; libimagequant is the better tool for translucent palette PNGs.
- **Very large images.** Memory is capped at 2 GB, and partly transparent images above about 16.8 MP have their weights scaled down. Streaming the histogram in chunks would remove both limits.
