# 3.8 and 4.0: one way to cut a stored clustering, the fixed-palette method, the breaking changes

Date: 2026-11-24. Status: revised after review (builder check, three stewards, `user-advocate`, cold reader), for approval.

## Intent

4.0 should leave the library with one way to do each thing. In 3.x there are two ways to cut or map a stored clustering on the calling thread (`clustering.getPalette(k)` and `getPaletteFromClustering(clustering, k)`), and in the worker entry the `…FromClustering` functions are the only way off the thread. The pre-4.0 recipe review (2026-11-24) also reopened one recipe: choosing N colours from a fixed palette (embroidery threads, paints, bricks), which has been fixed four times in 3.7.x and is about 90 lines in the guides.

The maintainer settled, in this order:

1. The fixed-palette function is built, designed here.
2. A handle made from a clustering, `worker.load(clustering)`, goes in this spec.
3. The built-in worker pool waits for a third ask (ROADMAP "Considered").
4. Option C for `…FromClustering`: on the calling thread the `Clustering` methods, off it handles. `…FromClustering` is deprecated in both entries.
5. Timing A: **3.8 prepares, additively; 4.0 removes.**
6. A `worker.load` handle maps with `quantize(image, k, options?)` and `quantizeToIndices(image, k, options?)`, the `Clustering` methods' shape.
7. The fixed-palette method returns `{ indices, palette }`.
8. `alpha` and `transparent` on formats without alpha: 4.0 rejects only values that ask for something (`transparent: true` or a cutoff); `transparent: false` and either `alpha` value pass. No 3.x warning.
9. The clustering tag key is not versioned (proposed, not objected to).

These are recorded in PRINCIPLES "Settled decisions" and the ROADMAP's 4.0 section (PR #67).

## Goals

- 3.8: users can do everything off the thread without `…FromClustering`, and get the fixed-palette search as one call, on either thread.
- 3.8: every `…FromClustering` function is `@deprecated` in the types, so editors flag it a version ahead; nothing changes at run time.
- 4.0: the removals and the type changes the ROADMAP collects, in one major version.

## Non-goals

- A worker pool (`createPool(n)`): later, on a third ask, built on `worker.load`.
- A function form of the fixed-palette search, in either entry.
- Counting pixels per entry in the library (`countThreads` stays a short recipe on the new result).
- Dithering inside the fixed-palette search (a different, much slower objective).
- A grey image format, a matte colour, `ditherInLight` as a default: unchanged, under "Considered".

## Anti-goals

- A 4.x born with a deprecated family, or two ways to cut a stored clustering.
- A fixed-palette result that looks like counts but isn't (the swatch-weight order was wrong against real counts).
- Any change to clustering, palette or mapping output. `test/golden.test.js` passes unchanged in 3.8 and 4.0, apart from the premultiplied path, which is new input.

## Approaches considered

For `…FromClustering` (decided: C):
- **A. Keep the worker entry's `…FromClustering`.** Smallest, but the entries mirror each other only in part.
- **B. Deprecate in the main entry only.** Weaker against "Both entries behave alike".
- **C. `worker.load(clustering)` and deprecate in both.** Chosen: off the thread, the handle is the answer, as it already is for images.

For timing (decided: A): 3.8 adds and deprecates and 4.0 removes, against doing it all in 4.0 and removing in 5.0. A follows the `get…` precedent (deprecated in 3.4.0) and avoids a 4.x with a deprecated family.

For the loaded handle's mapping (decided: A): `quantize(image, k)` against no mapping methods (mapping to a palette doesn't give the clustering's transparent cutoff and colour space) or `load(clustering, image?)` (two jobs in one call).

For the fixed-palette result (decided: A): `{ indices, palette }` against positions only (users still build the subset palette, the step they got wrong) or positions with estimated shares (look like counts, aren't).

## 3.8 (additive)

### `worker.load(clustering)`

```ts
interface AgglomerativeWorker {
    /** A handle for a stored clustering, kept in the worker: cut it and map images with it without sending it again. */
    load(clustering: Clustering | Uint8Array): Promise<LoadedClusteringHandle>;
}

interface LoadedClusteringHandle {
    getPalette(k: number): Promise<Palette>;
    getSwatches(k: number): Promise<Swatches>;
    getClusteringInfo(): Promise<ClusteringInfo>;
    quantize<I extends ImageLike>(image: I, k: number, options?: MappingOptions): Promise<ImageResult<I>>;
    quantizeToIndices(image: ImageLike, k: number, options?: MappingIndexOptions): Promise<IndexedImage>;
    chooseFrom(palette: PaletteLike, k: number, options?: ChooseOptions): Promise<PaletteChoice>;
    release(): Promise<void>;
    [Symbol.asyncDispose](): Promise<void>;
}
```

- **It validates and takes the bytes before it awaits**, like every call (CLAUDE.md): `readHeader` checks the clustering on the caller's side, so a damaged one, a palette or an image passed by mistake rejects with `invalid-clustering` on `'clustering'` before posting. The bytes are copied, or moved with `transfer: true`, through the same `own`/`take` path as a clustering argument today, and a `load` before the worker has started queues like any call.
- **No `getClustering()`:** the caller passed the clustering in and still has it (`scope-steward`). Adding it later is additive.
- **A wrong-shape call teaches:** `loaded.quantize(4)` (a number where the image goes) rejects with `invalid-argument` on `'image'`: "Invalid image: this handle holds a clustering, not an image (from worker.load); pass the image, then k." `imageHandle.quantize(image, 4)` rejects on `'k'` with the converse. The types catch both too.
- **Results and errors** are exactly those of the `Clustering` methods on the same bytes (`quantize` returns the input's type, its default transparent cutoff and colour space are the clustering's). A test checks byte-identical results against the deprecated function forms for every method, with and without `transparent` and `colorSpace` (`user-advocate`).
- **No `…WithPalette` methods on a loaded handle:** they would only forward the image, and `worker.quantizeWithPalette(image, palette)` already does that. An image handle keeps them because it keeps the pixels.
- **Release, `await using`, garbage collection:** the same as the image handle (`FinalizationRegistry`).
- **The worker side:** `worker-thread.js`'s `handles` map gets entries with no image (`{ clustering }`). The handle methods read the clustering only; the mapping methods take the image as an argument. Wire names: `load`, `handleQuantizeImage`, `handleQuantizeToIndicesImage`, `handleChooseFrom` (builder's call; not API). `optionsIndex` gets the new positions, so `signal` and `onProgress` work on the two mapping methods and `signal` on `chooseFrom`. The cuts take no options and are unchanged.
- **Type name:** the image handle is already called `ClusteringHandle`, so the new one is `LoadedClusteringHandle`. The cold reader and `api-steward` found the pair unclear (the unmarked name holds an image), so the docs say in one line what each holds, with a two-row table: `cluster(image)` keeps the image and maps it with `quantize(k)`; `load(clustering)` keeps only the clustering and maps with `quantize(image, k)`. It is rarely typed by hand. A 4.0 rename (`ImageHandle` for the old one) was suggested and is not taken: it would rename a type for no change in behaviour.

### The fixed-palette method

The search the guides ship as `chooseThreads` plus `improveThreads`, moved into the library. Named **`chooseFrom`**: the cold reader guessed it right from the name alone ("picks 12 entries out of `threads`"), took `chooseColors` for `getPalette(12)`, and found `selectFrom` indistinguishable; `api-steward` agreed. Its doc line says "fixed palette", the words users search for.

```ts
interface Clustering {
    /** Chooses the k entries of `palette` that best represent the clustered image: their positions and colours. */
    chooseFrom(palette: PaletteLike, k: number, options?: ChooseOptions): Promise<PaletteChoice>;
}
interface ChooseOptions {
    /** The space the search measures distance in: 'rgb' (default) or 'oklab'. It doesn't follow the clustering's space. */
    colorSpace?: ColorSpace;
    signal?: AbortSignal;
}
interface PaletteChoice {
    /** Exactly k positions in the palette given, ascending: no ranking (count the mapped pixels for a legend). */
    indices: number[];
    /** The chosen colours, in the order of `indices`: map with it, and index s of the result is entry indices[s]. */
    palette: Palette;
}
```

- **On the main entry** it is a method on `Clustering` (added to `methods` and `methodNames` in `shared.js`, forwarded through the engine slot). **On the worker entry** it is the same method on both handle kinds. **No function form** (PRINCIPLES "Settled decisions", 2026-11-24).
- **Algorithm:** the guides' recipe as of 3.7.2 (docs/guides.md, `chooseThreads` and `improveThreads`). First the snap: cut at k, k+1, … up to 4k, map each cut colour to its nearest entry **in RGB whatever `colorSpace` is** (only the search's space was measured to matter), keep the first k distinct in split order. Then the fast swap pass over the 1024-swatch cut (`getSwatches(1024)`), scoring in `colorSpace`, taking the best strictly better swap (improvement above 1e-9 relative; ties keep the first found, by thread then position) until none is left.
- **Exactly k, a change from the recipe** (`api-steward`, cold reader): when the snap finds fewer than k distinct entries (an image with few colours), the rest are added one at a time, each the entry that most lowers the error (ties to the lower position), before the swap pass. So `indices.length` is always k, and a legend never needs a length check; on an image with fewer colours than k some entries map no pixels, which the counting recipe already drops. Everywhere else the output is identical to the recipe's: `test/recipes.test.js` keeps the recipe's copy as the reference, compared exactly on the 24 Kodak photos at 6, 12, 24 and 40 of 584 and 1000 entries, in both spaces.
- **Where it runs:** in JavaScript (C++ was measured only 1.8× faster), in a module both entries import (builder's call). `clustering.chooseFrom` runs on the calling thread and forwards through the engine slot like the other methods, so with only the worker entry loaded it rejects with `wasm-load-failed` (it calls `getPalette` and `getSwatches`). On a handle of either kind it runs **in the worker thread**, which is what a live thread-count slider needs.
- **`colorSpace`: `'rgb'` unless passed**, whatever the clustering's space (`roadmap-steward` conflict, `user-advocate`). The reopening decision says RGB scoring by default (ROADMAP "Considered"); the scoring space and the clustering space are independent (docs/guides.md: "the gain follows the space the search measures in"); and a user who clusters in OKLab for photo quality shouldn't get the scoring that greyed small vivid areas (ΔE2000 10.74 against 9.85 on the most saturated 8.6% of pixels at 12 of 584 threads, `bench/spikes/fixed-subset-oklab/results-accents.txt`). The draft's "the clustering's own" was the earlier review shape, which the reopening paragraph supersedes.
- **`palette`** is a `PaletteLike`. Errors reuse `invalid-argument` and the existing palette check: empty or not a multiple of 3 on `'palette'`; `k` not a whole number from 1 to the palette's entry count on `'k'`, saying what was received ("Invalid k: 30 is more than the 24 entries in the palette; use 24 or fewer."); a bad `colorSpace` on `'options.colorSpace'`. No new code. A header-only clustering (empty image) gives the first k entries, the only choice with no pixels to fit.
- **The result's `palette`** is tagged `'rgb'` whatever space was scored in, so `quantizeToIndicesWithPalette(image, result.palette)` maps in RGB, as the recipe does; pass `colorSpace` there to map otherwise. (Tagging it with the scored space would make counts after `'oklab'` come from OKLab mapping without saying so; `user-advocate`.)
- **`indices` is `number[]`**, not a typed array: at most a few hundred small numbers, read by position in a legend, and `IndexedImage.indices` is a typed array because it is per pixel.
- **Cancelling, no progress:** `signal` is checked between swap passes and every 64 candidate entries; when it is given, the calling thread yields there (`yieldNow`), so an abort is seen on the main thread and a cancel message in the worker. No `onProgress`: the search takes 17 to 56 ms (84 ms at worst) for 12 to 40 of 584 to 1000 entries<!-- bench/spikes/fixed-subset-oklab/speed.mjs → results-speed.txt -->, a few slices, and its share of the work isn't known in advance (`scope-steward`: the smaller shape). Results with and without a signal are tested identical.
- **Determinism:** the result depends only on the clustering, the palette's bytes, k and `colorSpace`; `test/golden.test.js` gets hashes for it. It is a heuristic, documented as "a good choice, not always the best one". Whether a minor release may improve it is the open question below.

### Deprecations

`@deprecated` in `src/index.d.ts` and `src/worker.d.ts`, with a doc line naming the replacement:

| Deprecated (both entries) | Main thread | Off the thread |
|---|---|---|
| `getPaletteFromClustering(c, k)` | `c.getPalette(k)` | `(await worker.load(c)).getPalette(k)` |
| `getSwatchesFromClustering(c, k)` | `c.getSwatches(k)` | `….getSwatches(k)` |
| `getClusteringInfo(c)` (the function) | `c.getClusteringInfo()` | `….getClusteringInfo()` |
| `quantizeFromClustering(image, c, k)` | `c.quantize(image, k)` | `….quantize(image, k)` |
| `quantizeToIndicesFromClustering(image, c, k)` | `c.quantizeToIndices(image, k)` | `….quantizeToIndices(image, k)` |

- Nothing changes at run time: no warning (PRINCIPLES "Warnings only bridge to an error": deprecated names are not warnings).
- The `Clustering` methods keep forwarding through the engine to the function forms internally. Those become internal in 4.0.
- `docs/api.md`: "Moving existing code to the methods is optional" (line 305) becomes a deprecation note with the table above. The function entries move under a "Deprecated" heading, as the `get…` names did in 3.4.0. `test/api.test.js` keeps checking their `Options:` lists.
- **Guides and recipes move to the methods and handles:** the fixed-palette recipe is replaced by the method; its heading "Choosing N colours from a fixed set" stays, the README's method table gets a row, and `countThreads` is kept, shortened to map with `result.palette`, count, and look up `threads` at `indices[s]` for the chart number, with the dithering and `transparent` notes kept. The docs show the migration cost too: a one-off `worker.getPaletteFromClustering(c, k)` becomes `await using loaded = await worker.load(c)` and a call, one copy of the clustering (`user-advocate`). The guide measures and states the cost of the full-image counting pass for a live slider on a 12 MP photo, and advises downscaling for the live legend if it is slow; `sizeForError`, `rankSwatches`, the frame mapper and the pool recipe use `clustering.…` or a loaded handle. `test/recipes.test.js` follows.

### What 3.8 doesn't change

The wire names of existing calls, the clustering format, output, the default colour space.

## 4.0 (breaking)

Everything in the ROADMAP's 4.0 section, as written there, plus the decisions above. In brief:

1. **Remove the `…FromClustering` functions** in both entries, and their wire names in `worker-thread.js` (handles call internal functions).
2. **Remove the `get…` names that cluster** (`getClustering(image)`, `getPalette(image, k)`, `getSwatches(image, k)`), and rename the worker's wire names to the verb names.
3. **Premultiplied alpha:** `{ data, format, premultiplied: true }` for `'rgba'` and `'bgra'`. Un-premultiplied on read (`min(255, round(c·255/a))`, alpha 0 as black). `quantize*` output is premultiplied again (`round(c·a/255)`). Palettes and clusterings stay straight. The conversion is in C++ (the JS loop cost as much as `quantize`; ROADMAP).
4. **`RawImage` as a union split by `format`**, `premultiplied` only on formats with alpha, and **unknown keys on image objects rejected** (`invalid-argument` on `'image'`, with a near-miss hint for `premultiply`).
5. **Narrowed results:** `RawImage<F>` results with `data: Uint8Array` and the input's `format`, `width`, `height`, for the functions, methods and handles.
6. **The bare-image warnings become errors** (`rgb-as-rgba`, `gray-as-rgba`), rejecting exactly what the last 3.x release warns about, measured again on the corpora in `bench/spikes/bare-rgb/` and `bare-grey/`.
7. **`alpha` and `transparent` on `'rgb'`, `'rgbx'`, `'bgrx'`:** `transparent: true` or a numeric cutoff throws `invalid-argument` on `options.transparent`. `transparent: false`, `alpha: 'weight'` and `alpha: 'ignore'` are accepted and do nothing. (`alpha` never asks for anything on these formats, so no `alpha` value throws.)
8. **The tag key stays** (recorded in PRINCIPLES and the ROADMAP with this spec) `Symbol.for` as in 3.x: 4.0 recognises every 3.x clustering and palette. "Considered: Telling a pre-3.3 clustering from one with methods" is closed as not needed.
9. **`formatVersion` stays 3.** No format change.

Release: `4.0.0-beta.1` on `next` once 1 to 7 are in, an exploratory round on it (Sonnet agents), then 4.0.0. 3.8 ships first and on its own.

## Constraints

- CLAUDE.md "Adding or changing public API": every place listed there, for `load`, the handle type and the method. Also `test/api.test.js` and its snapshots, `test/types/*` (including `@ts-expect-error` for `loaded.quantize(k)` and for an image handle's `quantize(image, k)`), the worker routing and `optionsIndex`.
- Tests on Windows and in the published-package browser job: new browser checks read files from the installed package and are gated by version (memory: 3.7.2 lessons).
- The worker thread must not use top-level await.
- Numbers in the docs carry a sourced comment.

## What gets planned now

**Only 3.8 is planned and built from this spec.** The 4.0 list above points at the ROADMAP's 4.0 section, which is detailed for each item; 4.0 gets its own plan (or one per item: premultiplied with the `RawImage` union and narrowed results, then the removals and errors) after 3.8 ships, and a spec where an item needs one.

## Left to the builder

- Where the search code lives and the wire names.
- Test layout.
- Reading a header without the deprecated `getClusteringInfo(c)`: `new Clustering(bytes)` already validates (`src/shared.js`), and `.getClusteringInfo()` reads it, so 4.0 needs nothing new.

## Open: the maintainer's

- **May a minor release change `chooseFrom`'s choice?** Every result so far is exact (Ward, nearest colour) and fixed for the major version (stability.md). This one is a heuristic: a better search, or a fix to a tie, would change which entries come back. Either it is frozen for 4.x like every other result (any improvement waits for 5.0), or stability.md gets an exception: "`chooseFrom` may choose better in a minor release, noted in the CHANGELOG; its result is always k valid positions" (`scope-steward`).
