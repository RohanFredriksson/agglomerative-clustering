# README for 4.x: design

## Intent

The README is the library's front page, on GitHub and on npm. It dates from 3.0:
- the benchmark table and "about 70 ms" are from 3.0.0-beta.1;
- the size claim is out of date;
- the 4.1 and 4.2 speed-ups on real photos are nowhere;
- there is one static image;
- two paragraphs (the upgrade note, and input formats at line 85) read like reference docs.

The maintainer wants the library to be **a standout choice over more established libraries**, showing that **it brings something to the table**. The audience is broad, not one niche: anyone who works with colour from images, including app, tool, design, hardware and pipeline developers. The maintainer left the choice of what sells to the designer, and picked approach A below.

## Goals

- In the first screen, a reader sees what this library does that others don't. Every palette size comes from one clustering, and the palettes nest.
- Each claim on the page is backed by one visual or one sourced number, and none are padding.
- The use cases are shown, not listed: a gallery of what people build with it.
- All numbers are current (4.2), measured, and sourced (CLAUDE.md "Numbers in the docs have a source").
- All media are generated by a script in the repo from the library itself, so they can be regenerated each release.

## Non-goals

- Changing the API, the docs' content beyond moving README text into them, or the library.
- A website or docs site. The README stays a Markdown file that renders on GitHub and npm.

## Anti-goals: this fails even if it ships, if

- it overclaims: a number without a source, a comparison that is cherry-picked, or a "fastest" the benchmark doesn't support;
- it shows other libraries' images side by side to imply quality wins that the eye can't see. Error differences of 5–8% MSE are invisible at 16–64 colours, so a grid of near-identical images undersells and looks rigged;
- the GIFs make the npm or GitHub page heavy: the hero over about 1.5 MB, or all media together over about 6 MB;
- it hides the honest "better served by something else" section;
- the code examples stop being correct (`test/api.test.js` already checks README names and links).

## Approaches considered

- **A. Visual-first, with a use-case gallery (chosen).** A hero GIF sweeps a photo from 2 to 64 colours over a nested swatch bar. Then a short "why this one" list with a visual or a number per claim, install and three examples, a gallery of six use cases (each a GIF or still with a 3–5 line snippet), a refreshed benchmark table, and the docs links.
- B. Gallery-led: the gallery does the selling. Broader, but the unique point (one clustering, every k) loses emphasis.
- C. A light refresh: numbers, trimmed paragraphs, one GIF. Least work, but it doesn't change how the page sells.

## The page, in order

1. **Title and tagline.** One sentence on what it is, then one on what's different. Keep the badges.
2. **Hero GIF.** A photo animating from 2 to 64 colours, cut from one clustering. Under it, a swatch bar that grows by splitting, so the nesting is visible. Caption: "Every palette size from one clustering, in N ms" (measured).
3. **Why this one.** Five claims, one line each, in this order:
   1. Every size from one pass, and palettes nest, with the **nesting strip** (below).
   2. The lowest error of the libraries benchmarked, with one sourced number.
   3. It knows the image: each colour's share, the error at every size (it can pick a size), and the best fit from a fixed palette.
   4. Real-world input: transparency, premultiplied canvas pixels, BGRA, workers.
   5. Runs everywhere: Node and browsers, about 42 KB gzipped (sourced), no dependencies, deterministic output.
4. **Install**, with the Node and browser support line. The upgrade note shrinks to one line linking to Migrating.
5. **Three examples**: Node with sharp, canvas, and the slider. The current examples, kept short.
6. **Gallery.** Six cards, each a GIF or still plus 3–5 lines of code. Each card links to its guide.
   - **Pixel art and posterising:** a photo at 4, 8 and 16 colours, ordered dither.
   - **E-ink and limited displays:** a photo mapped to a 7-colour e-ink palette with Floyd–Steinberg, against no dither.
   - **Threads, bricks and paint-by-number:** `chooseFrom` picking k colours from a fixed set, for example a thread chart, with the chosen swatches.
   - **GIF and palette PNG output:** `quantizeToIndices` with gifenc. The gallery's own GIFs are made this way, and the card says so.
   - **Swatches for design tools:** `buildSwatches` with share bars.
   - **Animation and live video:** ordered dithering keeping still areas still across frames (a short clip, or frames from a pan over a photo).
7. **Benchmarks.** The refreshed table against the same libraries, at 4.2. Plus one line for large photos (the real-photo numbers from the spikes, or the release check), linking to `bench/COMPARISON.md`.
8. **How it works, in brief.** The one-line pipeline diagram and the "you want / function" table, kept. The verb paragraph and the input-formats paragraph move to `docs/api.md` (Input), with a one-line pointer.
9. **When something else fits better.** Kept, unchanged in substance.
10. **Documentation, Demo, License.** Kept, with the Demo trimmed.

## The nesting strip

The one comparison with another library, chosen because the difference is visible and isn't about error. It has two rows of swatches for k = 4 … 12:
- **color-thief's median cut** (`quantize`, MMCQ, already a dev dependency): swatches reshuffle as k changes;
- **this library:** each step splits one swatch, and the rest stay put.

It uses the same photo, and swatches are ordered by each library's own output order. For MMCQ, order its swatches the way a user would see them (its returned order); state that in the caption. Make it a still image, or a short GIF if the still doesn't read. The caption is factual: "Other quantizers start over for each k; these palettes nest." Name MMCQ in the caption.

## Media

- **Script:** `docs/media/make.mjs` (Node, ESM). It imports `dist/index.mjs` and uses dev dependencies only: sharp to decode and resize, gifenc for GIFs, fast-png for PNGs, and quantize for the strip. No new dependencies.
- **Output:** `docs/media/*.gif` and `*.png`, committed. The README references them by `raw.githubusercontent.com/.../master/docs/media/...` URLs, as it does today, so npm renders them.
- **Size budget:** the hero ≤ 1.5 MB, each card ≤ 800 KB, and the total ≤ 6 MB.
  - Card GIFs show small crops (about 320–480 px wide) at 8–12 fps, and reuse the library's own indexed output.
  - If a GIF can't meet its budget, it becomes a still, or animates fewer frames.
- **Photos:** Kodak (the benchmark set, `fixtures/kodak.js` downloads them) and the freely licensed Commons photos from `bench/spikes/chain-search/sources.txt`. List the credits for any Commons photo in `docs/media/CREDITS.md`, and link it from the README footer. Keep to licences that allow redistribution with attribution (CC0, PD, CC BY, CC BY-SA). For CC BY-SA, note the share-alike in the credits.
- **Captions** state measured times. The script writes them to `docs/media/results.json`, and the README cites it in an HTML comment.

## Numbers

- **Benchmark table:** re-run `bench/run.js` on a quiet machine for the same libraries at k = 64, with "palettes at 16/64/128/256", with this build and `precision: 6`. Then regenerate `bench/COMPARISON.md` from that run.
- **Hero timing:** measured by `make.mjs` (clustering time and the per-k cut time) on the hero photo.
- **Large photos:** one line from `bench/spikes/perf-3/results/results-release.txt`, or a fresh measurement at release.
- **Sizes:** measured from the published `dist/`.
- The run needs a quiet machine. The fourth speed spike is running now, so the benchmark run waits until it ends.

## Constraints

- The page renders on GitHub and npmjs.com: Markdown, images by absolute URL, no HTML that npm strips. Simple `<img width>` and `<table>` are fine on both; check before relying on anything more.
- `test/api.test.js` checks README names, links and anchors. It must pass, so the moved paragraphs keep their link targets, or the test is updated with them.
- Code in the README is correct against 4.2. Snippets in the gallery can be checked by a small test that runs them (`test/readme-snippets.test.js`, extracting fenced blocks with a marker), or by `make.mjs`, which uses the same code. **Builder's call**, but at least one must exist.
- Commits are authored as the maintainer, with no trailers.

## Decisions after the builder check (designer's calls)

1. **Image URLs.** The README keeps absolute `raw.githubusercontent.com/.../master/docs/media/...` URLs. To review before the merge, the maintainer gets a preview page (artifact) with the media embedded, and the branch is checked on GitHub with the URLs pointed at the branch temporarily. The README itself is committed with `master`. npm shows the new README only from the next release; that's expected.
2. **Claims follow the numbers.** Claim 2 says exactly what the 4.2 run shows. If another library wins somewhere, at some k or on the synthetic set, the claim is worded for where ours wins, for example "the lowest average error on the 24 Kodak photos at 16–256 colours". The rewrite doesn't wait for the run: the text is written with placeholders, and the numbers and the claim's wording are filled in from the run before the PR.
3. **Benchmarks.** The whole table is re-run on 4.2 before the PR (`bench/run.js`, a quiet machine, after the fourth spike ends). The fourth spike can only bring speed-only changes with identical output, so it can't invalidate the media. If it ships a speed-up later, only the time figures need refreshing.
4. **Hero caption number.** N is the WebAssembly clustering time plus all 63 cuts (k = 2…64) on the hero photo at its README size. It excludes decoding and resizing, and is the median of 5 on a quiet machine. `results.json` records the machine, the Node version, the settings and the load average. The caption names the photo size, for example "a 768×512 photo".
5. **Photos.** The hero and most cards use Kodak (the standard benchmark set, published for unrestricted use, and already the README's image). Commons photos are used only where Kodak can't show the point (a large photo, a night scene), and only with CC0, PD or CC BY licences. FAL and CC BY-SA photos aren't used, to keep the credits simple. `CREDITS.md` lists the author, the licence and the URL, taken from each Commons file page.
6. **Palettes.**
   - **E-ink:** the 7-colour palette already in `docs/guides.md` ("Fixed palettes").
   - **Threads:** there's no sourced thread chart in the repo, so the card doesn't say "DMC". It uses a fixed palette labelled honestly, "a fixed set of 24 colours (illustrative)", built in `make.mjs` and printed in the card's code.
7. **The animation card** is titled "Animation: ordered dithering keeps still areas still". It shows a synthetic pan or zoom over a Kodak photo. It doesn't say "live video" unless it shows real video.
8. **Size budget.** The total of 6 MB wins. The hero is ≤ 1.5 MB and the cards average ≤ 700 KB. A card may be a still where a still shows the point (swatches, the nesting strip). At least the hero and three cards are animated.
9. **Snippets.** `test/readme-snippets.test.js` extracts the gallery snippets, marked `<!-- snippet -->` before each fence, and runs them against `dist/` on a small synthetic image, asserting that they don't throw and return the documented shape. They mustn't depend on network or Kodak, so they use in-memory images. `make.mjs` uses the same snippet text where it can.
10. **Moved paragraphs.** Before moving anything, grep `docs/`, `CHANGELOG.md` and the tests for links to README anchors. Moved text goes to `docs/api.md` under the existing Input section and a new "Naming" subsection. README links point there. `test/api.test.js` is updated only if a name list in it must move.

## Left to the builder

- The exact photos for each card, crops, frame counts and fps, within the budget.
- The wording, within the claims above and the anti-goals.
- Card layout: a two-column `<table>` of images with code below, or one card per subsection. Choose what renders well on both GitHub and npm, and check it on npm with a preview: `npm pack`, or a markdown preview that strips HTML like npm does.
- Whether the nesting strip is a still or a GIF.

## Process

1. Build the media script and the media, and publish a preview page (artifact) for the maintainer to react to, before the README rewrite.
2. The README rewrite, plus the moved paragraphs in `docs/api.md`.
3. The benchmark re-run and `bench/COMPARISON.md`, once the machine is quiet.
4. Review: `api-steward` (docs promises) and a cold-read user agent who knows only the new README, asked what it would choose this library for and what it doesn't believe. Then the PR.
